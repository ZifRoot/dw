# Архитектура общего исходного кода (Shared)

## Назначение

Этот документ описывает используемый в DW архитектурный паттерн **Shared source layer**: существует одна каноническая копия исходного кода, которую напрямую используют несколько приложений, при этом каждый потребитель сохраняет собственный контекст компиляции TypeScript и собственные предположения о среде выполнения.

Речь идёт не просто о каталоге с названием `shared`. Это архитектурное решение, определяющее **владение исходным кодом, компиляцию, границы сред выполнения и разрешение зависимостей**.

Паттерн полезен, когда в репозитории находятся разнородные приложения — например, браузерный клиент и сервер Node.js. Им требуется повторно использовать часть кода, но при этом у них могут различаться конфигурации TypeScript, доступные API среды выполнения, формат модулей и граф зависимостей.

## Какую проблему решает этот паттерн

Обычный общий модуль или пакет часто собирается как самостоятельная единица. Это может быть правильным решением, но тогда возникает вопрос: **для какой среды предназначен общий пакет?**

Разным потребителям могут требоваться разные настройки:

- браузерному коду нужны типы библиотек `DOM` и `DOM.Iterable`;
- серверному коду нужны типы Node.js и серверные API;
- потребители могут использовать разные значения `module` и `moduleResolution`;
- один потребитель может собирать исходники через Vite, а другой — генерировать CommonJS или использовать другую среду выполнения;
- у клиента, сервера и тестового запуска могут различаться версии среды выполнения и доступные API.

Если общий исходный код компилируется один раз в рамках конфигурации отдельного пакета, эта конфигурация становится дополнительным архитектурным контрактом. Для общего пакета могут понадобиться результаты сборки, публичная точка входа, решения о формате модулей, генерация деклараций и правила зависимостей. Также может потребоваться поддержка пересечения возможностей всех потребительских сред.

Иногда это именно то, что нужно. Но в DW выбрано другое требование: общий производственный код должен оставаться исходным кодом, а **контекст компиляции должен задаваться потребителем**.

## Основная модель

DW хранит единственную каноническую копию общего исходного кода в `packages/shared/src`. Клиент и сервер предоставляют этот код внутри собственных деревьев исходников с помощью файловых ссылок.

```text
                         packages/shared/src
                         канонический исходный код
                                  |
                    +-------------+-------------+
                    |                           |
                    v                           v
       packages/client/src/shared   packages/server/src/shared
            symlink/junction              symlink/junction
                    |                           |
                    v                           v
           Проект TypeScript клиента    Проект TypeScript сервера
           DOM / ESNext / bundler       Типы Node / CommonJS
           инструменты клиента          инструменты сервера
```

Ссылки не создают копий файлов. Оба потребителя обращаются к одним и тем же каноническим файлам. Поэтому изменение в `packages/shared/src` становится доступно обоим потребителям без копирования или публикации пакета.

Клиент и сервер по-прежнему компилируют эти файлы в рамках собственных проектов TypeScript. У общего производственного исходного кода **нет отдельной конфигурации проекта TypeScript**.

## Почему используются файловые ссылки

Ссылка позволяет представить одно и то же дерево исходников по пути, ожидаемому каждым потребителем, не дублируя файлы.

Это обеспечивает несколько свойств:

1. **Единый источник истины.** Для каждой общей реализации существует одна редактируемая копия.
2. **Компиляция на стороне потребителя.** Клиент и сервер включают исходники в собственные проекты TypeScript.
3. **Собственные предположения потребителя о среде выполнения.** Общий код проверяется в каждом контексте потребителя, а не принудительно проходит одну общую сборку.
4. **Минимум упаковочной инфраструктуры.** Не требуется поддерживать отдельную сборку Shared-пакета, выходные JavaScript-файлы, конвейер генерации деклараций или карту экспортов пакета.
5. **Немедленное распространение изменений.** Добавление или изменение файла в каноническом каталоге отражается через ссылки.

Ссылки создаются локально и не коммитятся как обычные каталоги с исходным кодом. В DW файл `.gitignore` исключает `packages/client/src/shared/*` и `packages/server/src/shared/*`. Поэтому после нового клонирования репозитория ссылки необходимо создать до проверки типов или сборки.

### Создание ссылок в DW

Канонический каталог исходников:

```text
packages/shared/src
```

Пути потребителей:

```text
packages/client/src/shared  -> packages/shared/src
packages/server/src/shared  -> packages/shared/src
```

В репозитории есть скрипты для создания ссылок:

- `scripts/link-shared.sh` создаёт символические ссылки в Unix-подобных средах.
- `scripts/link-shared.cmd` создаёт junction-каталоги в Windows.

В корневом `package.json` сейчас определено:

```json
{
  "scripts": {
    "link:shared": "bash ./scripts/link-shared.sh"
  }
}
```

После нового клонирования выполните `npm run link:shared` до запуска команд, которым требуется разрешать импорты Shared. Обратите внимание на текущую особенность переносимости: корневая npm-команда запускает Bash, хотя существует реализация для Windows в формате `.cmd`. В Windows без Bash может потребоваться вызвать Windows-скрипт напрямую. Это известная несогласованность точки входа, а не причина менять саму архитектуру общего слоя исходников.

Скрипты рассчитаны на запуск из корня репозитория. Unix-скрипт определяет корень относительно собственного расположения; Windows-скрипт в текущей реализации использует текущий рабочий каталог.

## Конфигурация TypeScript принадлежит потребителю

Общий исходный код намеренно не является самостоятельным проектом TypeScript. В этой архитектуре важно различать:

- **общий исходный код** — повторно используемая реализация;
- **проект компиляции потребителя** — конфигурация TypeScript, которая включает и проверяет этот код;
- **тестовый проект** — отдельная среда, в которой выполняются тесты.

В DW есть корневой `tsconfig.base.json` с общими параметрами компилятора, но нет корневого `tsconfig.json`, который превращал бы корень репозитория в самостоятельный проект TypeScript. У самого общего исходного кода нет файла `packages/shared/tsconfig.json`.

Текущая конфигурация отражает принцип компиляции на стороне потребителя:

- **Клиент:** `packages/client/tsconfig.base.json` указывает библиотеки, включая `DOM` и `DOM.Iterable`, использует `module: "ESNext"` и `moduleResolution: "bundler"`, а также настраивает клиентские алиасы.
- **Сервер:** `packages/server/tsconfig.base.json` наследует корневую базовую конфигурацию, объявляет типы Node и серверные библиотеки, использует `module: "commonjs"` и настраивает серверные алиасы.
- **Общий исходный код** включается через дерево `src` каждого потребителя и проверяется в его контексте.

Поэтому не нужно добавлять отдельный `tsconfig.json` для Shared только потому, что в общем каталоге лежат файлы TypeScript. Такая конфигурация создаст отдельный проект лишь в том случае, если она действительно используется как самостоятельный проект компиляции; она не заменит проверки клиента и сервера. Более того, отдельный контекст компиляции потребует явного выбора целевой среды и может случайно ограничить исходный код одним набором API или семантикой модулей.

### Общий исходный код должен быть нейтрален к среде

Архитектура общего слоя не означает, что любой код безопасно использовать совместно. Код, предназначенный для клиента и сервера, не должен зависеть от API, доступных только в одной среде, если эта зависимость не изолирована явной границей.

Например, утилита, используемая в обеих средах, не должна без необходимости обращаться к `window`, классам DOM или глобальным объектам, доступным только в Node. Адаптеры, специфичные для конкретного потребителя, следует оставлять в его коде. Проверка типов в каждом потребителе помогает убедиться, что общая реализация подходит обеим средам.

## Алиасы импорта отражают смысл, а не физическое расположение

В DW для импортов общих утилит используется алиас `@utils/*`. Алиас `@shared/*` намеренно **не используется**.

Причина в том, что импорт должен описывать роль зависимости, а не раскрывать физическую структуру каталогов репозитория. Каталог `packages/shared/src` — деталь реализации; `@utils/*) — стабильное семантическое имя, которым пользуются потребители.

Алиас настроен в конфигурации TypeScript каждого потребителя:

- Клиент: `@utils/*` сопоставляется с `src/shared/utils/*`.
- Сервер: `@utils/*` сопоставляется с `src/shared/utils/*`.

Среда сборки или выполнения также должна понимать этот алиас. В DW клиент использует `vite-tsconfig-paths`; при сборке серверной версии используется `tsc-alias`, поскольку TypeScript сам по себе не переписывает алиасы путей в сгенерированном JavaScript.

Добавляя новый алиас, настройте его у соответствующих потребителей и в необходимых средствах разрешения импортов при сборке или запуске. Не вводите `@shared/*) как второе имя для тех же утилит.

## Тесты — отдельная среда

Распространённое заблуждение состоит в том, что если общий производственный исходный код не должен иметь собственного контекста компиляции, то и его тесты нужно принудительно запускать в контексте клиента или сервера. Это не так.

Тесты — исполняемый код со своими потребностями: тестовым раннером, API тестирования, тестовыми зависимостями и выбранной версией среды выполнения. Поэтому в DW тесты общего кода рассматриваются как отдельный проект TypeScript.

Текущая структура:

```text
                         tsconfig.base.json
                                  |
                   +--------------+--------------+
                   |              |              |
                   v              v              v
             Проект клиента Проект сервера test/tsconfig.json
                   |              |              |
                   v              v              v
                 Клиент         Сервер       Общие тесты
```

Тесты общих утилит находятся в корневом каталоге `test/` и используют `test/tsconfig.json`. Эта конфигурация напрямую наследует корневую базовую конфигурацию, а не проект клиента или сервера. Тесты клиента и сервера также имеют собственные конфигурации внутри соответствующих пакетов.

Этот тестовый контекст — не третье производственное приложение. Это отдельный контекст компиляции и выполнения для проверки общего кода. Версия Node.js в нём не обязана совпадать с версией на сервере: она должна быть совместима с тестовым раннером, тестовыми API и поддерживаемыми средами CI.

В DW тесты запускаются через встроенный тестовый раннер Node.js командой `tsx --test`. В текущем workflow GitHub Actions используется Node.js 22. Среда CI сама по себе не является проектом TypeScript: она предоставляет среду выполнения, в которой запускаются тесты.

## Границы зависимостей

Каталог общего исходного кода должен содержать код, который действительно могут использовать все предполагаемые потребители.

Перед добавлением модуля в Shared проверьте:

1. Зависит ли он от API, доступных только в браузере или только в Node?
2. Импортирует ли он зависимость, установленную только у одного потребителя?
3. Предполагает ли он конкретный формат модулей или определённый сборщик?
4. Требует ли он конфигурации или сервисов, принадлежащих конкретному приложению?
5. Могут ли проверки типов обоих потребителей проверить этот код?
6. Выполняются ли его тесты в выбранной среде без импорта runtime-зависимостей, специфичных для приложения?

Если обнаружена зависимость от конкретного потребителя, оставьте код в этом потребителе или введите небольшую явную абстракцию. Не исправляйте несовместимость сред бездумным добавлением типов DOM на сервер или типов Node в клиент: это может скрыть неправильную границу зависимостей.

## Настройка и проверка

Для нового клонирования репозитория или новой среды:

1. Установите зависимости обычной для репозитория командой.
2. Создайте файловые ссылки командой `npm run link:shared` в среде, где настроенный скрипт может выполняться.
3. Запустите проверку типов клиента.
4. Запустите проверку типов сервера.
5. Запустите тестовый проект Shared и тестовые проекты клиента и сервера.
6. Выполните обычные проверки сборки и CI.

В DW корневые команды включают `npm run typecheck`, `npm run typecheck:tests` и тестовые скрипты. Используйте команды, определённые в текущем корневом `package.json). Этот документ описывает архитектурные роли, а не заменяет определения команд.

Главный принцип проверки: общий код должен быть проверен **в контексте каждого предполагаемого потребителя**. Успешный запуск только общих тестов не доказывает, что клиент и сервер могут скомпилировать и собрать этот код.

## Компромиссы и типичные проблемы

Этот паттерн сознательно обменивает часть пакетной инфраструктуры и переносимости на прямое повторное использование исходников и независимую компиляцию потребителей.

### Преимущества

- единое каноническое дерево исходников;
- отсутствие дубликатов исходного кода и отдельных артефактов сборки пакета;
- независимые настройки компилятора у клиента и сервера;
- проверка общего кода с учётом ограничений каждого потребителя;
- нет необходимости подгонять общий код под заранее выбранную единую цель сборки или формат модулей.

### Издержки и риски

- после клонирования и в каждой подходящей среде нужно создавать ссылки;
- скрипты должны корректно учитывать различия операционных систем;
- редактор и разрешение путей TypeScript должны одинаково корректно работать со ссылками;
- потребитель может случайно импортировать API, недоступный другому потребителю;
- общий код не является независимо версионируемым или публикуемым пакетом;
- объявления зависимостей и публичных экспортов не контролируются отдельным `package.json` общего пакета;
- изменение может сломать одного потребителя, даже если у другого компиляция проходит успешно, поэтому проверять нужно обоих.

Аудиты репозитория выявили ручную настройку ссылок и зависимость корневого скрипта от Bash как операционные слабые места. Это реальные издержки текущей реализации, которые следует учитывать при переносе паттерна в другой проект.

## Почему не использовать npm workspace package?

Пакет в workspace — полноценная альтернатива, а не заведомо неправильный дизайн. Он предпочтительнее, когда общему коду нужны собственная идентичность пакета, объявленные зависимости, публичные экспорты, независимое версионирование, генерируемые декларации, артефакты сборки или стабильный публичный API.

Однако в этом случае всё равно нужно явно решить, как пакет собирается и используется. Если клиенту и серверу нужны разные контексты компиляции одного исходного кода TypeScript, подход с пакетом должен осознанно сохранять это требование — например, через экспорты исходников и компиляцию на стороне потребителей — либо вводить отдельный контракт сборки. Простое добавление `packages/shared/package.json` само по себе не решает вопрос целевой среды.

В DW архитектура общего слоя исходников выбрана намеренно: производственный Shared-код компилируется его потребителями. Независимый аудит также фиксирует обратную сторону этого решения: ручные ссылки делают новое клонирование и настройку на разных операционных системах более хрупкими. Эти обстоятельства следует взвешивать, а не считать символические ссылки или workspace-пакеты универсально лучшим решением.

## Применение концепции в другом проекте

При адаптации паттерна используйте следующий список проверки:

- [ ] Определите предполагаемых потребителей и различия их сред выполнения и компиляторов.
- [ ] Создайте один канонический каталог общего исходного кода.
- [ ] Подключите его к дереву исходников каждого потребителя файловыми ссылками или эквивалентным механизмом разрешения исходников.
- [ ] Сохраните независимые конфигурации TypeScript каждого потребителя.
- [ ] Настройте семантический алиас импорта у каждого потребителя и в его средствах сборки/разрешения импортов при запуске.
- [ ] Оставьте браузерные, серверные и специфичные для приложения адаптеры за пределами общего слоя.
- [ ] Настройте для общих тестов собственный явный контекст TypeScript и среды выполнения, чтобы случайно не наследовать конфигурацию приложения.
- [ ] Обеспечьте воспроизводимое создание ссылок во всех поддерживаемых операционных системах и выполняйте его в CI после клонирования.
- [ ] Проверяйте типы и сборку каждого потребителя, а также запускайте общие тесты.
- [ ] Документируйте компромиссы: ссылки — часть операционной инфраструктуры, а не закоммиченные копии исходников и не граница пакета.
