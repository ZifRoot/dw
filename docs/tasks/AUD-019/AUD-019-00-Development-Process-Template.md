# Development Process Template

> Универсальный шаблон операционного процесса разработки.  
> Скопируй этот документ в новый проект и замени placeholders конкретными значениями проекта.

## 1. Параметры процесса

- **Проект:** `<PROJECT_NAME>`
- **Исходный каталог:** `<SOURCE_DIRECTORY>`
- **Inventory:** `<INVENTORY_DOCUMENT>`
- **Каталог тестов:** `<TEST_DIRECTORY>`
- **Рабочий план:** `<PROJECT_MANAGER_PLAN>`
- **Основной документ процесса:** `<PROCESS_DOCUMENT>`

## 2. Команда

Процесс использует четыре роли:

- **Researcher** — дешёвая поверхностная инвентаризация;
- **Expert** — глубокий анализ, проектирование и code review;
- **Project Manager** — планирование ограниченных рабочих блоков;
- **Implementer** — реализация запланированных изменений.

Основной документ процесса задаёт общие правила. Конкретные действия каждой роли находятся в отдельных императивных инструкциях.

## 3. Исследователь

Исследователь быстро просматривает `<SOURCE_DIRECTORY>` и поддерживает `<INVENTORY_DOCUMENT>`.

Он:

1. находит новые и изменённые файлы;
2. находит классы, методы и функции;
3. заносит их в Inventory;
4. отмечает наличие связанных тестов;
5. фиксирует очевидные расхождения между Inventory и фактическим тестом.

Исследователь не определяет применимость сложных категорий тестирования и не выполняет глубокий анализ поведения.

## 4. Эксперт

Эксперт выполняет глубокий технический анализ.

Он:

1. определяет observable behavior;
2. проектирует необходимые сценарии;
3. оценивает сложность;
4. определяет unit/integration подход и зависимости;
5. выполняет code review;
6. подтверждает, что реализация соответствует заявленной сути.

Эксперт является наиболее дорогим ресурсом процесса.

## 5. Project Manager

Project Manager читает Inventory и экспертные решения и формирует `<PROJECT_MANAGER_PLAN>`.

Он:

1. выбирает приоритет;
2. оценивает объём;
3. учитывает стоимость ролей;
4. учитывает лимит рабочего блока;
5. разбивает крупные задачи;
6. не пытается включить весь Inventory в один план.

При оценке учитывай относительную стоимость ресурсов:

`Researcher < Implementer < Expert`

Не передавай эксперту работу, которую можно надёжно выполнить исследователем или исполнителем.

## 6. Исполнитель

Исполнитель берёт только задачи из текущего плана.

Он:

1. реализует задачу;
2. не меняет её смысл без экспертного решения;
3. запускает проверки;
4. обновляет Inventory;
5. передаёт результат на проверку.

## 7. Цикл

`Researcher → Inventory → Expert → Project Manager → Implementer → Expert Review → Researcher`

Цикл повторяется после изменения исходного кода.

## 8. Актуальность Inventory

Каждая запись Inventory должна позволять автоматизированно определить, устарел ли экспертный анализ.

Используй как минимум:

- `Source Commit`;
- `Last Modified`;
- `Expert Reviewed`;
- `Expert Review Commit`.

Если текущий commit/hash или дата исходного элемента не совпадает с зафиксированным состоянием экспертной проверки, запись считается требующей повторного Expert Review.

## 9. Критерий завершения

Элемент считается завершённым только после:

1. актуального Inventory;
2. экспертного анализа;
3. реализации;
4. code review;
5. проверки исследователем.

## 10. Ссылка на инструкции ролей

Конкретный проект должен предоставить отдельные документы:

- `<RESEARCHER_INSTRUCTIONS>`;
- `<EXPERT_INSTRUCTIONS>`;
- `<PROJECT_MANAGER_INSTRUCTIONS>`;
- `<IMPLEMENTER_INSTRUCTIONS>`.

Каждая инструкция должна ссылаться на этот основной документ.

## 11. Правило масштабирования

Не привязывай процесс к конкретному языку, test runner или структуре каталогов, если это не является требованием проекта.

Для нового проекта замени placeholders и создай проектные инструкции ролей.
