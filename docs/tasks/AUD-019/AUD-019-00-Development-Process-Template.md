# 1. Назначение процесса

Цель процесса — создать управляемый цикл работы с программным кодом:

- исследование текущего состояния проекта;
- фиксация структуры кода;
- экспертный анализ;
- планирование работ;
- реализация изменений;
- проверка результата.

Процесс предназначен не только для тестирования.

Он применяется для любых задач, где необходимо:

- понять существующую систему;
- уменьшить риск изменений;
- сохранить знания о проекте;
- разделить работу между ролями с разной стоимостью и квалификацией.

---

# 2. Конфигурация проекта

После генерации документа placeholders должны быть заменены конкретными значениями.

| Placeholder            | Назначение               |
| ---------------------- | ------------------------ |
| `<PROJECT_NAME>`       | название проекта         |
| `<SOURCE_DIRECTORY>`   | каталог исходного кода   |
| `<TEST_DIRECTORY>`     | каталог тестов           |
| `<INVENTORY_DOCUMENT>` | документ Inventory       |
| `<PLAN_DOCUMENT>`      | план Project Manager     |
| `<TEST_RUNNER>`        | используемый test runner |
| `<LANGUAGE>`           | язык программирования    |
| `<PROCESS_OWNER>`      | владелец процесса        |

---

# 3. Основные принципы

## 3.1 Inventory является источником состояния

Inventory отвечает на вопрос:

> Что существует в проекте сейчас?

Inventory не является списком задач.

В нём фиксируется:

- какие элементы существуют;
- где они находятся;
- какие проверки существуют;
- когда выполнялся анализ;
- кем подтверждено состояние.

---

## 3.2 План является отдельной сущностью

План Project Manager отвечает на вопрос:

> Что нужно сделать сейчас?

Inventory может содержать тысячи элементов.

План должен содержать только тот объём работы, который реально может быть выполнен.

---

## 3.3 Глубина анализа зависит от роли

Не все участники должны одинаково глубоко изучать систему.

Процесс специально разделяет:

- дешёвую поверхностную работу;
- дорогую экспертную работу;
- выполнение конкретных изменений.

---

# 4. Команда процесса

Процесс использует четыре основные роли:

1. Researcher
2. Expert
3. Project Manager
4. Implementer

---

# 5. Researcher

## Назначение роли

Researcher выполняет дешёвую инвентаризацию.

Его задача:

> Понять, что существует.

---

## Researcher выполняет

- просмотр исходного кода;
- поиск файлов;
- поиск классов;
- поиск методов;
- поиск функций;
- фиксацию структуры в Inventory;
- проверку наличия тестов.

---

## Researcher НЕ выполняет

Researcher не:

- проектирует тесты;
- определяет категории тестирования;
- оценивает архитектурные решения;
- делает глубокий code review;
- определяет правильность реализации.

---

## Результат работы Researcher

После работы должен быть ответ:

```

Какие элементы существуют?
Какие тесты существуют?
Где есть очевидные несоответствия?

```

---

# 6. Expert

## Назначение роли

Expert выполняет глубокий технический анализ.

Это самый дорогой ресурс процесса.

---

## Expert выполняет

- анализ поведения системы;
- определение требований к проверке;
- выбор стратегии тестирования;
- оценку сложности;
- анализ зависимостей;
- проектирование решений;
- code review.

---

## Expert отвечает на вопросы

```

Что должен делать этот элемент?

Как это правильно проверить?

Какие существуют риски?

Соответствует ли текущая реализация назначению?

```

---

## Expert Review

Expert обязан подтвердить:

- что элемент понят;
- что решение соответствует назначению;
- что реализация соответствует ожиданиям.

После проверки устанавливается:

```

Expert Reviewed = true

```

и фиксируется:

- commit;
- дата;
- версия исходного состояния.

---

# 7. Implementer

## Назначение роли

Implementer реализует конкретные задачи.

---

## Implementer выполняет

- создание тестов;
- изменение кода;
- исправление ошибок;
- запуск проверок;
- обновление Inventory.

---

## Implementer НЕ выполняет

Implementer не должен:

- самостоятельно менять требования;
- расширять задачу;
- заменять экспертный анализ собственным предположением.

---

# 8. Project Manager

## Назначение роли

Project Manager превращает состояние проекта в рабочий план.

---

## Project Manager анализирует

Источники:

- Inventory;
- замечания Researcher;
- решения Expert.

---

## Project Manager определяет

- приоритет;
- размер задачи;
- исполнителя;
- необходимость Expert Review.

---

## Стоимость ролей

При планировании учитывать:

```

Researcher < Implementer < Expert

```

Researcher — самый дешёвый.

Implementer — средняя стоимость.

Expert — самый дорогой.

---

## Ограничение размера задачи

Project Manager не должен создавать огромные задачи.

Каждая задача должна иметь:

- понятную цель;
- ограниченный объём;
- измеримый результат.

---

# 9. Жизненный цикл элемента

Элемент проходит следующие состояния:

```

DISCOVERED -> ANALYZED -> IMPLEMENTED -> EXPERT REVIEWED -> VERIFIED

```

---

# 10. Проверка актуальности

Каждый элемент Inventory должен содержать:

```

Source Commit
Last Modified
Expert Reviewed
Expert Review Commit

```

Если исходный код изменился:

```

Source Commit != Expert Review Commit

```

то требуется повторная экспертная проверка.

---

# 11. Тестирование

## Категории проверок

Эксперт определяет применимость:

- Success
- Edge Case
- Failure
- Exception
- Async
- State
- Concurrency
- Side Effect
- Dependency

---

## Принцип тестов

Тесты должны проверять:

```

что делает система

```

а не:

```

как именно реализована система внутри

```

---

# 12. Архитектура тестов

Проект задаёт:

```

<TEST_DIRECTORY>

```

Пример:

```

tests/
├── unit/
└── integration/

```

Тесты должны быть отделены от production-кода.

---

# 13. Расхождения

Researcher может обнаружить:

- отсутствующий тест;
- новый метод;
- удалённый метод;
- очевидное несоответствие названия теста.

Он фиксирует факт.

Он НЕ исправляет проблему.

---

# 14. Автоматизация

Процесс допускает автоматизацию:

- генерация документов;
- проверка актуальности commit;
- поиск новых файлов;
- проверка Inventory;
- создание задач.

---

# 15. Масштабирование

Этот процесс не зависит от:

- языка программирования;
- проекта;
- типа тестов;
- структуры каталогов.

Для нового проекта необходимо:

1. скопировать шаблон;
2. заполнить placeholders;
3. создать проектные инструкции ролей;
4. создать Inventory.

---

# 16. Критерий завершения процесса

Работа считается завершённой когда:

- Inventory актуален;
- Expert подтвердил анализ;
- изменения реализованы;
- выполнен Expert Review;
- Researcher подтвердил соответствие.
