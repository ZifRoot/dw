# AUD-019-02 — Инвентаризация и организация тестирования shared

## Родительская задача

AUD-019 — архитектура тестирования проекта dw

## Цель

Создать управляемый процесс полного анализа и последующего тестирования кода:

packages/shared/src/

Работа выполняется командой из четырёх ролей:

1. **Исследователь** — устанавливает, что существует в shared, и проверяет соответствие Inventory реальному коду и тестам.
2. **Эксперт** — проектирует корректные сценарии тестирования и способ их реализации.
3. **Исполнитель** — реализует конкретные тестовые задачи.
4. **Project Manager** — превращает состояние Inventory в ограниченный по объёму план работы для исполнителей.

Результат состоит из основного описательного документа и рабочих документов ролей:

- AUD-019-02-Shared-Tests.md — знакомство с командой, общие правила и границы процесса;
- AUD-019-02-Shared-Test-Researcher.md — императивная инструкция исследователю;
- AUD-019-02-Shared-Test-Expert.md — императивная инструкция эксперту;
- AUD-019-02-Shared-Test-Implementer.md — императивная инструкция исполнителю;
- AUD-019-02-Shared-Test-Project-Manager.md — императивная инструкция Project Manager;
- AUD-019-02-Shared-Test-Inventory.md — изменяемая карта исходного кода, тестов и выявленных расхождений.

Inventory и план Project Manager являются рабочими документами и изменяются по мере выполнения работы. Основной файл после согласования процесса не используется как рабочая таблица.

---

# 1. Команда

## 1.1 Исследователь

Исследователь отвечает за фактическую картину проекта.

Он исследует packages/shared/src, поддерживает Inventory в соответствии с production-кодом и проверяет, что заявленное покрытие действительно существует в тестах.

Отдельная ответственность исследователя — контроль качества уже написанных тестов. Исследователь не ограничивается проверкой наличия тестового файла: он сопоставляет заявленную в Inventory категорию с фактическим содержимым теста.

Например, если в Inventory указано Exception = [x], но тест проверяет только успешный результат, исследователь фиксирует это как расхождение.

Исследователь не обязан самостоятельно исправлять плохой тест и не обязан составлять для него план реализации.

---

## 1.2 Эксперт

Эксперт отвечает за техническое проектирование тестирования.

Он определяет observable behavior, необходимые сценарии, применимые категории тестов, unit/integration подход, зависимости, test doubles, сложность и ограничения реализации.

Эксперт также определяет, как корректно проверить сложное поведение, если простой тест неочевиден или невозможен.

---

## 1.3 Исполнитель

Исполнитель отвечает за написание тестов.

Он получает конкретную ограниченную задачу из плана Project Manager, изучает соответствующее решение эксперта и реализует тест.

Исполнитель не формирует глобальный порядок работ и не должен самостоятельно превращать весь Inventory в бесконечный список задач.

---

## 1.4 Project Manager

Project Manager отвечает за планирование работы исполнителей.

Он читает Inventory, включая накопленные исследователем расхождения, учитывает решения эксперта и формирует отдельный ограниченный план.

Project Manager не обязан добиваться полного заполнения Inventory за один проход.

Его задача — выбрать следующий объём работы, который исполнитель может реально выполнить за заданный рабочий объём.

Размер задачи ограничивается оценкой трудозатрат. При оценке учитываются сложность теста, объём необходимого контекста, предполагаемое количество работы и доступный исполнителю лимит. В проекте этот лимит может выражаться в токенах/объёме контекста, времени работы или другой принятой единице.

Project Manager должен избегать задач, которые настолько велики, что исполнитель не сможет качественно завершить их за один рабочий блок.

Если Inventory содержит замечание исследователя о некорректном существующем тесте, Project Manager рассматривает это замечание как источник отдельной задачи и включает исправление в план, не пытаясь исправить Inventory вместо исследователя.

---

# 2. Как взаимодействуют роли

Основной цикл:

Исследователь → Inventory → Эксперт → Project Manager → Исполнитель → Tests → Исследователь

После реализации исследователь снова проверяет:

Inventory ↔ production code ↔ test code.

Если исследователь обнаруживает новое расхождение, он фиксирует его в Inventory. Project Manager видит это расхождение при следующем планировании и решает, когда включить его исправление в рабочий план.

Таким образом:

- исследователь сообщает фактическое состояние;
- эксперт определяет техническое решение;
- Project Manager определяет порядок и размер рабочих задач;
- исполнитель реализует выбранную задачу.

---

# 3. Рабочие документы

## Inventory

Inventory отвечает на вопрос:

> Что существует в shared, что для него требуется проверить, что уже проверено и какие расхождения обнаружены?

Inventory является изменяемым документом.

## Project Manager

Файл Project Manager отвечает на вопрос:

> Какие конкретные небольшие задачи нужно выполнять следующими и в каком порядке?

Он не обязан содержать весь Inventory. Это рабочий план ближайшего объёма работ.

## Документы ролей

Документы Researcher, Expert, Implementer и Project Manager содержат императивные инструкции соответствующей роли.

Они определяют действия роли, входные данные, результаты и критерии завершения.

---

# 4. Источник истины

Источник исходного кода:

packages/shared/src/

Необходимо рассматривать:

- все TypeScript-файлы;
- экспортируемые классы;
- методы;
- свободные функции;
- фабрики;
- декораторы;
- async-функции и методы;
- callback/event behavior;
- stateful-компоненты;
- побочные эффекты;
- зависимости от времени;
- randomness;
- global/process state;
- filesystem;
- network и другие внешние ресурсы;
- runtime-поведение объектов, enum и констант, если оно существует.

Типы и интерфейсы без собственного runtime-поведения не нужно искусственно превращать в тестовые единицы.

---

# 5. Test runner и архитектура тестов

Основной test runner — Jest.

Используются стандартные Jest API:

- describe;
- it / test;
- expect;
- beforeEach / afterEach;
- beforeAll / afterAll;
- Jest mocks, spies и timers только при необходимости.

Не смешивать API разных test runners в одном тестовом файле.

## Структура

tests/
- unit/
  - shared/
    - структура, соответствующая packages/shared/src/
    - module.test.ts
- integration/
  - shared/
    - module.test.ts

Production-код остаётся в packages/shared/src. Тесты не размещаются внутри production-кода.

По возможности структура tests/unit/shared повторяет packages/shared/src.

Пример:

packages/shared/src/utils/single-runner.ts

должен иметь соответствующий тест:

tests/unit/shared/utils/single-runner.test.ts

Integration-тесты находятся в tests/integration/shared.

## Naming

Используется суффикс .test.ts.

Название файла соответствует production-модулю.

Внутри файла describe и it должны описывать observable behavior, а не внутреннюю реализацию.

# 6. Категории тестовых сценариев

Для каждой тестируемой единицы определить применимые категории:

- success — нормальный успешный сценарий;
- edge — граничные и особые значения;
- failure — предусмотренный неуспешный результат;
- exception — предусмотренное исключение;
- async — асинхронное поведение;
- state — состояние до/после вызова;
- concurrency — конкурентные или повторные вызовы;
- side-effect — наблюдаемые побочные эффекты;
- dependency — взаимодействие с зависимостями.

Failure и exception различаются:

- failure — метод возвращает предусмотренный неуспешный результат;
- exception — метод выбрасывает исключение.

Не все категории применимы к каждому элементу.

---

# 7. Переход от простого теста к полному тестированию

Нельзя использовать правило «написан один зелёный success-тест — метод готов».

Для каждого элемента:

1. исследователь фиксирует элемент и его фактическое состояние;
2. эксперт определяет полный набор применимых сценариев;
3. Project Manager выбирает ограниченный рабочий объём;
4. исполнитель реализует выбранные сценарии;
5. исследователь проверяет фактический результат.

При этом Project Manager должен смотреть на незавершённую работу глобально. Нельзя бесконечно углублять один метод, пока другие элементы вообще не получили базового покрытия.

---

# 8. Критерии планирования

Project Manager учитывает:

1. отсутствие теста;
2. отсутствие базового success-теста;
3. важное непокрытое observable behavior;
4. критичные failure/exception сценарии;
5. существенные edge cases;
6. async/state/concurrency/side-effect/dependency сценарии;
7. исправление расхождений, обнаруженных исследователем;
8. техническую готовность задачи;
9. оценку трудозатрат и доступный лимит рабочего блока.

При равной необходимости предпочтение отдаётся задаче, которую можно полностью и качественно завершить в одном рабочем блоке.

Большая задача должна быть разделена на несколько последовательных задач.

---

# 9. Критерий завершения элемента

Элемент считается завершённым только когда:

- определено observable behavior;
- определены применимые категории;
- необходимые сценарии реализованы;
- неприменимые категории отмечены N/A;
- тесты проходят;
- исследователь подтвердил соответствие Inventory и фактических тестов;
- отсутствуют незакрытые расхождения по этому элементу.

Если сценарий невозможно корректно реализовать, он не помечается выполненным. Причина фиксируется в Inventory, а при необходимости создаётся отдельная задача.

---

# 10. Production code

Production-код не изменяется только ради удобства тестирования.

Если обнаружено препятствие:

1. зафиксировать его в Inventory;
2. описать observable behavior;
3. определить способ тестирования без изменения production-кода;
4. если корректное тестирование невозможно — явно отметить это;
5. потенциальный refactoring вынести в отдельную задачу.

Нельзя искусственным тестом создавать видимость проверки поведения.

---

# 11. Главное правило

Исследователь отвечает:

> Что у нас есть и действительно ли Inventory соответствует репозиторию и тестам?

Эксперт отвечает:

> Что именно необходимо проверить и как это корректно сделать?

Project Manager отвечает:

> Что конкретно делать следующим и какой объём работы можно отдать исполнителю сейчас?

Исполнитель отвечает:

> Как реализовать конкретную задачу из текущего плана?

Только согласованная работа всех четырёх ролей превращает найденный элемент в завершённый тестовый элемент.
