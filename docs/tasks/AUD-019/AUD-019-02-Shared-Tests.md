# AUD-019-02 — Тесты для shared

## Родительская задача

**AUD-019 — архитектура тестирования проекта `dw`**

## Цель

Создать первую полноценную коллекцию тестов проекта — для общего кода `shared`.

Тесты должны находиться в отдельной root-level папке:

```
dw/
├── tests/
│   ├── unit/
│   ├── integration/
│   └── ...
│
├── packages/
│   ├── shared/
│   ├── client/
│   └── server/
```

В рамках этой задачи необходимо не просто показать работу Jest, а **системно пройти весь код `packages/shared/src` и покрыть тестами его доступное поведение**.

Это первая содержательная тестовая задача после создания базовой CI-инфраструктуры.

---

## Главная учебная цель

Задача предназначена прежде всего для обучения.

Нужно на реальном коде `shared` научиться:

- находить тестируемые единицы;
- определять границы unit-теста;
- проектировать test cases;
- проверять normal / edge / error cases;
- использовать mocks, stubs и fakes там, где они действительно нужны;
- тестировать асинхронный код;
- тестировать классы и функции;
- тестировать декораторы;
- тестировать состояние и побочные эффекты;
- понимать, что именно проверяет тест;
- видеть связь между тестами и coverage;
- организовывать тесты в понятную структуру.

**Тесты не должны создаваться ради формального достижения процента coverage.**

Coverage является дополнительным инструментом анализа. Основная задача — научиться правильно тестировать существующий код.

---

# 1. Область тестирования

Источник истины:

```
packages/shared/src/
```

Необходимо провести полный inventory этого каталога.

Перед написанием тестов нужно определить:

- все файлы TypeScript;
- все экспортируемые функции;
- все экспортируемые классы;
- публичные методы;
- публичные свойства, если их поведение имеет значение;
- декораторы;
- фабрики;
- утилиты;
- типы/enum/константы, если они содержат исполняемое или проверяемое поведение;
- асинхронные операции;
- функции с побочными эффектами;
- функции, зависящие от времени, случайности или внешнего состояния.

### Важно

Нельзя составлять список тестов только по уже известным файлам.

Во время выполнения задачи необходимо **заново просмотреть весь `packages/shared/src`**, чтобы не пропустить новые или редко используемые методы.

Результатом inventory должен быть явный список того, что было проверено.

---

# 2. Требование «все методы»

Под «протестировать все методы» понимается не механическое выполнение каждой строки.

Для каждой тестируемой единицы необходимо определить её наблюдаемое поведение.

Минимально должны быть рассмотрены:

1. основной успешный сценарий;
2. граничные значения;
3. некорректные входные данные, если они допустимы на уровне runtime;
4. ошибки и исключения;
5. асинхронные сценарии;
6. повторные вызовы;
7. состояние до/после вызова;
8. побочные эффекты;
9. взаимодействие с зависимостями.

Не каждый пункт применим к каждому методу.

Если конкретное поведение неприменимо, это должно быть очевидно из природы метода.

---

# 3. Примеры

Тесты должны быть содержательными.

Примитивные проверки вида:

```ts
expect(2 + 2).toBe(4);
```

не являются основным результатом этой задачи.

Нужно использовать реальные компоненты `shared`.

Например, для utility-функции:

```
input
  ↓
shared function
  ↓
result
  ↓
assertion
```

Для класса:

```
create instance
      ↓
configure state
      ↓
invoke method
      ↓
observe result/state/effect
```

Для асинхронного компонента:

```
start operation
      ↓
await result
      ↓
assert result
      ↓
assert state/effects
```

Для компонента с зависимостями:

```
System under test
      |
      +---- mock/stub/fake dependency
      |
      v
observable behavior
```

---

# 4. Mock / Stub / Fake

В процессе выполнения задачи необходимо использовать реальные примеры разных видов test doubles там, где это имеет смысл.

Нужно зафиксировать в документации теста:

- почему зависимость изолируется;
- почему выбран mock/stub/fake;
- что именно проверяется;
- почему тест не должен проверять реализацию зависимости.

Не следует мокать всё подряд.

Если зависимость проста и безопасна для использования напрямую, предпочтительно использовать реальную зависимость.

---

# 5. Особые случаи

Особое внимание уделить компонентам, поведение которых сложнее обычной чистой функции.

В частности, необходимо отдельно проверить существующие механизмы вроде:

- `SingleExecution` / `single-runner`;
- throttling/decorator behavior, если соответствующий код находится в `shared`;
- асинхронные utility;
- обработку ошибок;
- stateful utilities;
- функции, работающие с временем;
- функции, работающие с коллекциями;
- функции с callback/event behavior.

Для асинхронных механизмов необходимо проверить не только результат, но и соответствующее поведение при конкурентных/повторных вызовах, если это является частью контракта.

Например, для механизма single execution важно проверить сценарий:

```
call A ────────────────┐
                       ├── same execution
call B ────────────────┘
```

а не только одиночный успешный вызов.

---

# 6. Организация каталогов

Предпочтительная структура:

```
tests/
├── unit/
│   ├── <area>/
│   │   ├── <module>.test.ts
│   │   └── ...
│   └── ...
│
├── integration/
│   └── ...
│
└── ...
```

Конкретное разбиение должно следовать структуре `packages/shared/src`, а не создавать искусственные категории.

Основная масса тестов `shared` ожидается в `tests/unit`.

Integration-тесты создаются только там, где действительно проверяется взаимодействие нескольких компонентов.

Не создавать integration test только ради количества.

---

# 7. Связь с production code

Production-код `packages/shared/src` не должен изменяться только для того, чтобы сделать его удобнее тестировать.

Допустимы изменения production-кода только если в процессе обнаружена реальная ошибка, дефект архитектуры или другая отдельная причина.

Если для тестирования обнаруживается неудобный API, сначала необходимо проверить, можно ли корректно протестировать существующее публичное поведение.

Если обнаружена потенциальная проблема production-кода:

1. не скрывать её изменением теста;
2. зафиксировать наблюдение;
3. при необходимости создать отдельную AUD-задачу.

---

# 8. Что делать с кодом, который трудно тестировать

Если метод зависит от:

- filesystem;
- network;
- timers;
- global state;
- process environment;
- randomness;
- browser API;
- других внешних ресурсов,

не следует сразу переписывать production-код.

Сначала определить:

- что является его observable behavior;
- какую часть можно проверить напрямую;
- какую зависимость можно изолировать;
- какой test double подходит;
- требуется ли integration test вместо unit test.

Если полноценный тест невозможен без существенного production refactoring — это необходимо явно зафиксировать, а не маскировать искусственным тестом.

---

# 9. Coverage

После создания тестов необходимо посмотреть coverage `shared`.

Coverage используется как **исследовательский инструмент**.

Нужно проверить:

- какие файлы оказались покрыты;
- какие функции не были затронуты;
- какие branches остались непокрыты;
- какие участки кода трудно покрыть;
- соответствует ли coverage фактической полноте тестирования.

Не устанавливать обязательный threshold в рамках этой задачи.

Особенно важно найти случаи:

```
100% coverage
      ≠
100% качества тестов
```

Если coverage показывает неожиданно высокий или низкий результат, необходимо разобраться почему.

---

# 10. Inventory результата

В рамках задачи создать или дополнить документ, содержащий результат анализа `shared`.

Например:

```
docs/tasks/AUD-019/
    shared-test-inventory.md
```

В нём для каждого тестируемого модуля желательно иметь:

| Module | Unit | Integration | Important cases | Status |
|---|---|---|---|---|
| ... | ... | ... | ... | ... |

Для каждого метода/функции, где это необходимо, указать основные проверяемые сценарии.

Документ должен позволять ответить:

> «Мы действительно прошли весь `shared` или какие-то методы забыли?»

---

# 11. Naming

Использовать согласованное соглашение из AUD-019.

Предпочтительно:

```
*.test.ts
```

Название теста должно описывать поведение:

```ts
it("returns the same promise for concurrent execution", ...)
```

а не внутреннюю реализацию:

```ts
it("calls private field currentPromise", ...)
```

---

# 12. Проверка CI

После создания тестов необходимо убедиться, что добавленные файлы не ломают уже созданный базовый CI.

Минимально проверить:

```bash
npm run typecheck
```

Если Jest уже подключён в рамках AUD-019-01 к моменту выполнения этой задачи, также проверить соответствующий test command.

---

# 13. Что НЕ входит в задачу

Не входит:

- тестирование client;
- тестирование server;
- PostgreSQL integration tests;
- полноценные E2E;
- настройка GitHub Actions;
- настройка GitLab CI;
- достижение заданного coverage percentage;
- массовый production refactoring;
- исправление всех обнаруженных production defects.

Если тестирование выявляет реальный дефект `shared`, он должен быть зафиксирован отдельно.

- [ ] Запущены тесты.

# 15. Ожидаемый результат

После выполнения задачи должно существовать:

```
dw/
├── tests/
│   ├── unit/
│   │   └── ...
│   ├── integration/
│   │   └── ...
│   └── ...
│
├── packages/
│   └── shared/
│       └── src/
│           └── ...
│
└── docs/
    └── tasks/
        └── AUD-019/
            ├── AUD-019.md
            ├── AUD-019-01-GitHub-Typecheck-CI.md
            └── shared-test-inventory.md
```

Главный результат — не просто набор зелёных тестов.

Главный результат:

> **получить на реальном `shared` практический опыт полного цикла: inventory → выбор типа теста → test design → mocks/stubs/fakes → assertions → coverage → анализ непокрытого поведения.**
