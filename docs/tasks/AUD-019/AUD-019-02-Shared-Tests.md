# AUD-019-02 — Инвентаризация и организация тестирования shared

## Родительская задача

AUD-019 — архитектура тестирования проекта dw

## Универсальная основа

Этот документ является проектной специализацией универсального процесса:

[AUD-019-00 Development Process Template](./AUD-019-00-Development-Process-Template.md)

Для других проектов процесс должен использовать шаблон с заменой project-specific placeholders.

## Цель

Создать управляемый процесс полного анализа и последующего тестирования кода:

`packages/shared/src/`

Работа выполняется командой из четырёх ролей:

1. **Исследователь** — дешёвая поверхностная инвентаризация;
2. **Эксперт** — глубокий анализ, проектирование и code review;
3. **Исполнитель** — реализация конкретных задач;
4. **Project Manager** — планирование ограниченных по объёму рабочих блоков.

## Основной цикл

Исследователь → Inventory → Expert Review → Project Manager → Исполнитель → Expert Code Review → Researcher Verification

Project Manager может запускать Expert Review отдельно от реализации, если Inventory содержит элементы без актуальной экспертной проверки.

## Стоимость ролей

При оценке рабочего плана Project Manager учитывает относительную стоимость ресурсов:

`Researcher < Implementer < Expert`

Исследователь используется для дешёвой поверхностной инвентаризации. Исполнитель реализует подготовленные задачи. Эксперт подключается для глубокого анализа и code review и поэтому является наиболее дорогим ресурсом.

## Источник исходного кода

`packages/shared/src/`

Необходимо инвентаризировать:

- TypeScript-файлы;
- классы;
- методы;
- свободные функции;
- фабрики;
- декораторы;
- другие элементы с runtime-поведением.

Не требуется искусственно создавать тестовые единицы для типов и интерфейсов без собственного runtime-поведения.

## Test runner и архитектура

Основной test runner — Jest.

Тесты располагаются вне production-кода:

`tests/unit/shared/`  
`tests/integration/shared/`

Название тестового файла заканчивается на `.test.ts`.

Тесты проверяют observable behavior, а не внутреннюю реализацию.

## Категории тестов

Эксперт определяет применимость:

- success;
- edge;
- failure;
- exception;
- async;
- state;
- concurrency;
- side-effect;
- dependency.

Failure и exception различаются: failure — предусмотренный неуспешный результат, exception — выброшенное исключение.

## Inventory и актуальность экспертной проверки

Для каждого элемента Inventory хранит:

- Source Commit;
- Last Modified;
- Expert Reviewed;
- Expert Review Commit.

Если исходный код изменился после экспертной проверки, элемент снова требует Expert Review.

## Expert Review

Эксперт не ограничивается проектированием теста. Он выполняет code review существующей реализации и тестов, когда они уже присутствуют.

Он подтверждает, что код соответствует заявленной сути элемента и что результаты проверки Inventory не противоречат фактической реализации.

## Ограничение рабочего объёма

Project Manager не должен пытаться закрыть весь Inventory одним планом.

Он оценивает стоимость в принятой системе проекта: story points, токены, время или другую единицу.

Большие задачи разбиваются на рабочие блоки.

## Критерий завершения

Элемент считается завершённым после:

1. актуального Inventory;
2. Expert Review;
3. реализации, если она требуется;
4. Expert Code Review;
5. Researcher Verification.

Производственный код не изменяется только ради удобства тестирования.

## Главное правило

Исследователь сообщает:

> Что существует?

Эксперт определяет:

> Что это означает, что нужно проверить и соответствует ли реализация заявленной сути?

Project Manager определяет:

> Что делать сейчас и какой объём можно поручить?

Исполнитель реализует:

> Как выполнить конкретную задачу?
