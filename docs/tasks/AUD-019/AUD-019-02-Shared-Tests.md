# AUD-019-02 — Инвентаризация и организация тестирования shared

## Родительская задача

AUD-019 — архитектура тестирования проекта dw

## Цель

Создать управляемый процесс полного анализа и последующего тестирования кода:

packages/shared/src/

Работа разделяется на три вида:

1. исследование — определить, что существует в shared и что именно необходимо проверить;
2. экспертиза — определить, как корректно тестировать каждый элемент и насколько это сложно;
3. реализация — создавать конкретные тесты по подготовленному плану.

Результат состоит из трёх связанных документов:

- AUD-019-02-Shared-Tests.md — эта спецификация, read-only после начала выполнения;
- AUD-019-02-Shared-Test-Inventory.md — изменяемая карта исходного кода и состояния тестов;
- AUD-019-02-Shared-Test-Priority.md — изменяемый план приоритетов реализации.

Основной файл задачи не используется как рабочая таблица.

---

# 1. Роли

## 1.1 Исследователь

Исследователь отвечает за соответствие Inventory реальному репозиторию.

Он:

- проходит весь packages/shared/src;
- находит новые, удалённые или изменённые классы, методы и функции;
- добавляет отсутствующие элементы в Inventory;
- проверяет, что существующие строки соответствуют текущему коду;
- проверяет наличие тестовых файлов;
- сопоставляет заявленные в Inventory сценарии с фактическим содержимым тестов;
- выявляет расхождения между Inventory и тестами.

Исследователь не обязан писать тесты.

Особенно важно: исследователь проверяет не только наличие тестового файла, но и его смысл.

Если в Inventory указано Exception = [x], исследователь обязан убедиться, что тест действительно проверяет исключение. Тест, проверяющий только успешный сценарий, не может быть отмечен как exception-тест.

Главный результат исследователя:

> Inventory соответствует текущему состоянию репозитория, а отметки о реализованных сценариях подтверждены реальными тестами.

---

## 1.2 Эксперт

Эксперт отвечает за проектирование теста.

Он определяет:

- observable behavior;
- необходимые сценарии;
- обязательность success, failure и exception;
- необходимость edge, async, state, concurrency, side-effect и dependency тестов;
- unit или integration;
- зависимости и test doubles;
- сложность;
- возможность немедленной реализации;
- необходимость дополнительного исследования или отдельной задачи.

Эксперт не обязан писать тест, если его роль ограничена проектированием.

Главный результат:

> Для каждого элемента понятно, что именно необходимо проверить и каким способом это корректно сделать.

---

## 1.3 Исполнитель

Исполнитель отвечает за реализацию.

Он:

- берёт приоритетные элементы из AUD-019-02-Shared-Test-Priority.md;
- читает соответствующую строку Inventory;
- реализует тесты согласно решению эксперта;
- создаёт тестовый файл в правильном каталоге;
- обновляет Inventory;
- отмечает конкретные реализованные категории;
- запускает тесты и typecheck.

Исполнитель не отмечает сценарий как выполненный, пока соответствующий тест действительно не существует и не проходит.

Если решение эксперта оказалось невозможным или неверным, исполнитель не должен молча менять смысл задачи. Он обновляет комментарий в Inventory и передаёт элемент на повторное экспертное решение.

---

# 2. Основной цикл

Работа выполняется циклом:

Исследователь → Inventory → Эксперт → Priority → Исполнитель → Tests → Исследователь

Исследователь после реализации проверяет соответствие:

Inventory ↔ production code ↔ test code.

Наличие success-теста не означает завершение тестирования метода.

---

# 3. Источник истины

Источник исходного кода:

packages/shared/src/

Необходимо рассмотреть:

- все TypeScript-файлы;
- экспортируемые классы;
- методы;
- свободные функции;
- фабрики;
- декораторы;
- async-функции и методы;
- callback/event behavior;
- stateful-компоненты;
- побочные эффекты;
- зависимости от времени;
- randomness;
- global/process state;
- filesystem;
- network и другие внешние ресурсы;
- runtime-поведение объектов, enum и констант, если оно существует.

Типы и интерфейсы без собственного runtime-поведения не нужно искусственно превращать в тестовые единицы.

---

# 4. Полнота инвентаризации

Инвентаризация считается полной только когда:

- каждый релевантный исходный файл рассмотрен;
- каждый класс рассмотрен;
- каждый тестируемый метод рассмотрен;
- каждая свободная функция рассмотрена;
- фабрики и декораторы рассмотрены;
- для каждого элемента определено, нужен ли автоматический тест;
- для каждого элемента определён дальнейший путь: тестировать, исследовать дополнительно или вынести в отдельную задачу.

После изменений в packages/shared/src исследователь повторно синхронизирует Inventory.

---

# 5. Test runner и архитектура тестов

Основной test runner — Jest.

Используются стандартные Jest API:

- describe;
- it / test;
- expect;
- beforeEach / afterEach;
- beforeAll / afterAll;
- Jest mocks, spies и timers только при необходимости.

Не смешивать API разных test runners в одном тестовом файле.

## Структура

tests/
- unit/
  - shared/
    - структура, соответствующая packages/shared/src/
    - module.test.ts
- integration/
  - shared/
    - module.test.ts

Production-код остаётся в packages/shared/src. Тесты не размещаются внутри production-кода.

По возможности структура tests/unit/shared повторяет packages/shared/src.

Пример:

packages/shared/src/utils/single-runner.ts

должен иметь соответствующий тест:

tests/unit/shared/utils/single-runner.test.ts

Integration-тесты находятся в tests/integration/shared.

## Naming

Используется суффикс .test.ts.

Название файла соответствует production-модулю.

Внутри файла describe и it должны описывать observable behavior, а не внутреннюю реализацию.

Хорошие примеры:

- executes the operation successfully;
- throws when the operation fails;
- returns the same promise for concurrent calls;
- does not execute the operation twice.

Плохие примеры:

- calls private field;
- sets internal flag;
- calls helper method.

# 6. Категории тестовых сценариев

Для каждой тестируемой единицы определить применимые категории:

- success — нормальный успешный сценарий;
- edge — граничные и особые значения;
- failure — предусмотренный неуспешный результат;
- exception — предусмотренное исключение;
- async — асинхронное поведение;
- state — состояние до/после вызова;
- concurrency — конкурентные или повторные вызовы;
- side-effect — наблюдаемые побочные эффекты;
- dependency — взаимодействие с зависимостями.

Failure и exception различаются:

- failure — метод возвращает предусмотренный неуспешный результат;
- exception — метод выбрасывает исключение.

Не все категории применимы к каждому элементу.

---

# 7. Переход от простого теста к полному тестированию

Нельзя использовать правило «написан один зелёный success-тест — метод готов».

Для каждого элемента:

### Этап A — базовое поведение

Определить основной success-сценарий.

Если его можно быстро и корректно реализовать — исполнитель создаёт тест.

### Этап B — расширение сценариев

Эксперт определяет, нужны ли:

- edge;
- failure;
- exception;
- async;
- state;
- concurrency;
- side-effect;
- dependency.

### Этап C — глобальная приоритизация

Сравниваются все незавершённые элементы, а не только текущий метод.

Например:

| Метод | Success | Edge | Exception |
|---|---|---|---|
| A | [x] | [x] | [ ] |
| B | [ ] | [ ] | [ ] |
| C | [x] | [x] | [ ] |

Если exception для A не является критичным, а B вообще не имеет базового теста, Priority должен рассмотреть B раньше углубления A.

---

# 8. Критерии приоритизации

Основные критерии:

1. элемент вообще не имеет тестов — высокий приоритет;
2. отсутствует базовый success-тест — высокий приоритет;
3. важное observable behavior не покрыто — высокий приоритет;
4. отсутствует критичный failure/exception сценарий;
5. отсутствуют существенные edge cases;
6. async/state/concurrency/side-effect/dependency сценарии;
7. дополнительные сценарии уже хорошо покрытых элементов.

При равном приоритете предпочтение отдаётся:

- более простому тесту;
- тесту, снимающему существенную неопределённость;
- тесту, блокирующему понимание поведения;
- тесту, покрывающему значимую часть observable behavior.

Количество уже написанных тестов само по себе не является основанием понижать приоритет.

---

# 9. Состояния тестируемого элемента

Используются состояния:

DISCOVERED → ANALYZED → READY → BASE TESTED → SCENARIOS EXPANDED → VERIFIED

DISCOVERED — элемент найден.

ANALYZED — определены тип, сложность, observable behavior, категории и зависимости.

READY — экспертное решение достаточно конкретно для исполнителя.

BASE TESTED — существует корректный базовый тест. Это не означает завершение.

SCENARIOS EXPANDED — реализованы необходимые дополнительные сценарии.

VERIFIED — исследователь подтвердил соответствие Inventory, исходному коду и тестам.

---

# 10. Критерий остановки

Метод считается завершённым только когда:

- определено observable behavior;
- определены применимые категории;
- success проверен, если применим;
- edge проверены, если существенны;
- failure проверен, если предусмотрен;
- exception проверен, если предусмотрен;
- async проверен, если применим;
- state проверен, если состояние является частью поведения;
- concurrency проверен, если является частью контракта;
- side-effect проверен, если является частью поведения;
- dependency проверен, если взаимодействие является частью контракта;
- неприменимые категории отмечены N/A;
- исследователь подтвердил соответствие Inventory и тестов.

Если применимый сценарий не реализован, элемент не считается VERIFIED.

Если сценарий невозможно корректно реализовать, он не помечается выполненным. Причина фиксируется в Inventory, а при необходимости создаётся отдельная задача.

---

# 11. Сложные тесты

Если даже success-тест сложен:

1. эксперт описывает способ реализации;
2. указывает зависимости и инфраструктуру;
3. оценивает риски;
4. определяет unit или integration;
5. при необходимости выделяет отдельную задачу;
6. исполнитель реализует тест после получения достаточного решения.

Сложность не является основанием просто пропустить тест.

---

# 12. Production code

Production-код не изменяется только ради удобства тестирования.

Если обнаружено препятствие:

1. зафиксировать его в Inventory;
2. описать observable behavior;
3. определить способ тестирования без изменения production-кода;
4. если корректное тестирование невозможно — явно отметить это;
5. потенциальный refactoring вынести в отдельную задачу.

Нельзя искусственным тестом создавать видимость проверки поведения.

---

# 15. Главное правило

Исследователь отвечает:

> Что у нас есть и действительно ли Inventory соответствует репозиторию и тестам?

Эксперт отвечает:

> Что именно необходимо проверить и как это корректно сделать?

Исполнитель отвечает:

> Как реализовать конкретный тест из текущего Priority?

Только прохождение всех трёх этапов превращает найденный метод в завершённый тестовый элемент.
