# AUD-019-02 — Инвентаризация тестируемого кода `shared`

## Родительская задача

**AUD-019 — архитектура тестирования проекта `dw`**

## Цель

Подготовить полный перечень кода `shared`, который необходимо рассмотреть с точки зрения автоматического тестирования.

На этом этапе **не требуется написать все тесты**. Основной результат задачи — качественный inventory, который станет основой для последующих задач по реализации тестов.

Источник анализа:

```
packages/shared/src/
```

Разработчик должен последовательно пройти весь каталог, найти классы, методы, функции и другие элементы с исполняемым поведением и занести результаты анализа в таблицу ниже.

---

# 1. Результат задачи

В результате должен появиться заполненный раздел **«Inventory»** в этом файле.

Для каждого найденного класса/модуля необходимо:

1. добавить его в таблицу;
2. перечислить методы и функции, которые необходимо рассмотреть для тестирования;
3. оценить сложность тестирования;
4. предложить способ тестирования;
5. зафиксировать зависимости, ограничения и проблемы;
6. указать, требуется ли для него unit-, integration- или другой тип теста;
7. при необходимости отметить, что полноценное тестирование без изменения production-кода затруднительно или невозможно.

Этот документ должен позволять в дальнейшем взять любой элемент `shared` и понять:

> Что именно нужно тестировать, насколько это сложно и каким способом это предполагается сделать?

# 2. Что необходимо исследовать

Необходимо полностью просмотреть:

```
packages/shared/src/
```

Нельзя ограничиваться несколькими очевидными utility-классами.

Необходимо найти и рассмотреть:

- все TypeScript-файлы;
- экспортируемые классы;
- методы классов;
- функции;
- фабрики;
- декораторы;
- async-функции и async-методы;
- функции с callback/event behavior;
- stateful-компоненты;
- компоненты с побочными эффектами;
- функции, зависящие от времени;
- функции, зависящие от случайности;
- функции, зависящие от глобального состояния;
- компоненты, работающие с файловой системой;
- компоненты, взаимодействующие с другими внешними ресурсами;
- runtime-поведение enum/констант/объектов, если такое поведение действительно есть.

Типы, интерфейсы и другие элементы, не содержащие собственного исполняемого поведения, не требуется искусственно превращать в тестовые единицы.

# 3. Важный принцип: сначала анализ, потом реализация

На этом этапе разработчик **не обязан сразу писать тест** для каждого найденного метода.

Для каждого элемента возможны разные результаты анализа.

Например:

### Вариант A — легко тестируется

```
Class: StringParser
Method: parse

Сложность: низкая
Тип: unit
Подход: прямой вызов метода и проверка результата
Комментарий: внешних зависимостей нет
```

### Вариант B — требуется test double

```
Class: FileLoader
Method: load

Сложность: средняя
Тип: unit
Подход: изолировать файловую систему через test double
Комментарий: отдельно проверить успешное чтение и ошибки файловой системы
```

### Вариант C — нужен integration test

```
Class: Repository
Method: save

Сложность: высокая
Тип: integration
Подход: реальная инфраструктурная зависимость
Комментарий: unit-тест не проверит фактическое взаимодействие с хранилищем
```

### Вариант D — тестирование существенно затруднено

```
Class: SomeComponent
Method: execute

Сложность: очень высокая
Тип: определить после анализа
Подход: требует дополнительного исследования
Комментарий: сильная связь с global state / process / filesystem
```

Если разработчик считает, что компонент практически невозможно корректно протестировать без изменения production-кода, это необходимо **зафиксировать в таблице**, а не скрывать проблему искусственным тестом.

### Правила заполнения

**Файл / модуль**

Указать конкретный файл или модуль из `packages/shared/src`.

**Класс / функция**

Указать конкретный класс или свободную функцию.

**Метод / операция**

Указать конкретный метод класса либо саму функцию.

Если у класса есть несколько тестируемых методов, рекомендуется добавлять отдельную строку для каждого метода.

**Тип теста**

Предварительно определить наиболее подходящий тип:

- `unit`;
- `integration`;
- `e2e`, если действительно применимо;
- `n/a`, если автоматический тест для данного элемента не имеет смысла.

**Сложность тестирования**

Оценка именно сложности создания корректного теста:

- **низкая** — метод можно непосредственно вызвать и проверить результат;
- **средняя** — требуется изолировать одну или несколько зависимостей;
- **высокая** — есть сложные состояния, async/concurrency, внешние ресурсы или существенное количество зависимостей;
- **очень высокая** — тестирование требует существенной инфраструктуры либо потенциального изменения production-кода.

Это оценка сложности тестирования, а не оценка качества production-кода.

**Предполагаемый способ тестирования**

Кратко описать, как предполагается проверять поведение.

Например:

- прямой вызов;
- parametrized test;
- mock зависимости;
- stub;
- fake;
- временная файловая система;
- integration test;
- проверка конкурентного поведения;
- проверка состояния до/после;
- проверка callback/event;
- комбинация нескольких подходов.

**Зависимости / test doubles**

Указать зависимости, которые потребуется контролировать при тестировании:

- filesystem;
- network;
- timer;
- random;
- process environment;
- global state;
- другие классы;
- callback;
- event emitter;
- внешние сервисы и т. п.

Если предполагается mock/stub/fake — указать это здесь.

**Комментарии и ограничения**

Здесь необходимо фиксировать всё, что важно для последующей реализации:

- почему тестировать сложно;
- какая часть поведения является наблюдаемой;
- какие сценарии особенно важны;
- какие зависимости мешают unit-тесту;
- нужен ли integration test;
- есть ли подозрение на проблему production-кода;
- требуется ли отдельная задача;
- что именно необходимо дополнительно исследовать.

**Статус**

Использовать один из понятных статусов:

- `не анализировался`;
- `анализируется`;
- `готов к тесту`;
- `тест написан`;
- `отдельная задача`;
- `тестирование не требуется`.

# 6. Что обязательно анализировать при оценке метода

Для каждого метода необходимо как минимум подумать о следующих вопросах.

### Входные данные

- Какие значения являются нормальными?
- Есть ли граничные значения?
- Есть ли runtime-некорректные значения, которые реально могут попасть в метод?
- Что происходит с пустыми коллекциями / строками / объектами?
- Что происходит при повторном вызове?

### Результат

- Что является observable result?
- Нужно ли проверять не только значение, но и состояние объекта?
- Есть ли несколько возможных результатов?

### Ошибки

- Может ли метод бросить исключение?
- Какие ошибки являются частью контракта?
- Какие ошибки возникают из-за внешних зависимостей?

### Состояние

- Меняется ли состояние объекта?
- Что происходит до и после вызова?
- Влияют ли предыдущие вызовы на последующие?

### Асинхронность

Если метод асинхронный:

- что происходит при успешном завершении;
- что происходит при ошибке;
- что происходит при повторном вызове;
- есть ли конкурентные вызовы;
- имеет ли значение порядок завершения операций.

### Зависимости

- Можно ли использовать реальную зависимость?
- Нужно ли её изолировать?
- Какой test double потребуется?
- Действительно ли unit-тест является подходящим вариантом?

# 7. Особое внимание сложным компонентам

Необходимо отдельно проанализировать компоненты, которые потенциально требуют более сложной тестовой инфраструктуры.

В частности:

- `SingleExecution` / `single-runner`;
- throttling/decorator behavior;
- async utilities;
- stateful utilities;
- concurrent operations;
- filesystem-dependent code;
- timer-dependent code;
- code using process/global state;
- callback/event-based code;
- код с внешними зависимостями.

Для таких компонентов в таблице обязательно должно быть указано, **каким предполагается путь тестирования**.

Например:

```
direct unit test
mock dependency
fake dependency
integration test
special test fixture
timer control
concurrency test
```

# 8. Production code

Эта задача не предполагает изменения production-кода только ради составления inventory.

Если при анализе выясняется, что некоторый класс или метод неудобен для тестирования:

1. сначала зафиксировать проблему в таблице;
2. описать причину;
3. определить возможный способ тестирования без изменения production-кода;
4. если без изменения production-кода корректное тестирование невозможно — явно это отметить;
5. потенциальный production refactoring вынести в отдельную задачу.

Нельзя изменять production-код только для того, чтобы искусственно улучшить результат inventory.

---

# 9. Что НЕ входит в эту задачу

В эту задачу **не входит обязательная реализация тестов для всех найденных методов**.

Не входит:

- написание полного набора unit-тестов;
- написание integration-тестов;
- написание E2E-тестов;
- достижение определённого coverage;
- настройка CI;
- массовый production refactoring;
- исправление всех найденных production defects.

Это будет выполняться следующими задачами на основании полученного inventory.

При этом разработчик может написать отдельный тест в процессе анализа, если это позволяет быстро подтвердить выбранный подход. Такой тест не должен заменять полный inventory.

# 11. Ожидаемый результат

После выполнения этой задачи документ должен содержать не абстрактное описание тестирования, а **конкретную карту `packages/shared/src`**.

Пример итогового фрагмента:

| Файл / модуль | Класс / функция | Метод / операция | Тип теста | Сложность тестирования | Предполагаемый способ тестирования | Зависимости / test doubles | Комментарии и ограничения | Статус |
|---|---|---|---|---|---|---|---|---|
| `utils/foo.ts` | `Foo` | `execute` | unit | низкая | прямой вызов | — | чистая логика | готов к тесту |
| `utils/bar.ts` | `Bar` | `load` | unit | средняя | изолировать filesystem | fake filesystem | проверить ошибки чтения | готов к тесту |
| `repository/baz.ts` | `Baz` | `save` | integration | высокая | реальное хранилище | test fixture | unit недостаточен | отдельно |
| `async/qux.ts` | `Qux` | `run` | unit | высокая | concurrency test | controlled dependency | проверить повторные вызовы | готов к тесту |
| `...` | `...` | `...` | `...` | `...` | `...` | `...` | `...` | `...` |

Итоговый документ должен отвечать на три вопроса:

1. **Что именно есть в `shared` и что необходимо проверить?**
2. **Как предполагается тестировать каждый элемент?**
3. **Какие элементы требуют отдельного решения из-за сложности или ограничений тестируемости?**

Следующие задачи по реализации тестов должны опираться на этот inventory, а не заново проводить исследование `shared`.
