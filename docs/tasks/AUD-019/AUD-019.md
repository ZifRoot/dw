# AUD-019 — Архитектура тестирования проекта dw

## Тип

**Epic / исследовательско-учебная задача**

AUD-019 определяет архитектуру и инфраструктуру тестирования проекта `dw`. Конкретные содержательные тесты отдельных компонентов выполняются в последующих задачах внутри `docs/tasks/AUD-019/`.

---

## 1. Контекст и цель

Проект `dw` имеет в первую очередь **исследовательско-учебную ценность**. Production-ценность проекта вторична: значительная часть проекта существует для исследования embeddings, структуризации данных, графов, архитектуры и инженерных подходов.

Поэтому тестовая инфраструктура также рассматривается не только как средство проверки уже работающего production-кода, но и как **учебная лаборатория по тестированию**.

Главная цель AUD-019:

> Создать полноценную, расширяемую и понятную архитектуру тестирования, на которой можно изучать unit, integration и E2E testing, mocks/stubs/fakes, coverage, lint и CI/CD, не изменяя production-код только ради его тестируемости.

Ключевой критерий ценности задачи — не количество написанных тестов и не высокий процент coverage, а возможность на реальном проекте разобраться:

- как организуется тестовый код;
- как выбирается test runner;
- как изолируются зависимости;
- чем отличаются unit, integration и E2E tests;
- как работают mocks/stubs/fakes;
- что такое code coverage и какие метрики он показывает;
- что такое lint и какую информацию он даёт;
- как локальная тестовая инфраструктура связывается с CI;
- чем отличаются GitHub Actions и GitLab CI;
- как создавать новые тесты без изобретения структуры заново.

---

## 2. Принцип «production code не знает о тестах»

AUD-019 не должен требовать изменения production-кода только ради возможности тестирования.

Тест должен работать по принципу:

```
test
  |
  | import
  v
production module
  |
  | function call
  v
result
  |
  v
assertion
```

Production-код не должен содержать специальную логику вида:

```ts
if (process.env.NODE_ENV === "test") {
    // специальное поведение
}
```

Тестовая инфраструктура должна адаптироваться к существующему коду, а не наоборот.

При этом технические настройки Jest или CI могут иметь собственное тестовое окружение. Это инфраструктурная деталь и не должна превращаться в зависимость production-кода от факта запуска тестов.

## 3. Общая архитектура тестов

Тесты разделяются по принадлежности к части проекта.

### Shared

Поскольку текущий `shared` не является обычным самостоятельным workspace package, его не следует искусственно превращать в такой package в рамках AUD-019.

Для него создаётся отдельный root-level каталог:

```
dw/
├── tests/
│   ├── unit/
│   ├── integration/
│   └── e2e/
│
├── shared/
├── packages/
│   ├── client/
│   │   └── tests/
│   │       ├── unit/
│   │       ├── integration/
│   │       └── e2e/
│   │
│   └── server/
│       └── tests/
│           ├── unit/
│           ├── integration/
│           └── e2e/
```

Root-level `tests/` в данном случае относится к тестированию `shared`.

### Client и Server

Тесты client и server находятся внутри соответствующих проектов.

Это позволяет запускать и развивать тестовые пространства независимо.

---

## 4. Типы тестов

Архитектура сразу предусматривает три уровня:

### Unit

Проверяет отдельную небольшую единицу поведения в изоляции.

Пример:

```
Service
  |
  +-- Repository mock
  +-- External API mock
  |
  v
assertions
```

### Integration

Проверяет взаимодействие нескольких реальных компонентов системы.

На первом этапе не требуется реальная PostgreSQL.

Для учебных примеров допускаются in-memory/fake реализации зависимостей.

### E2E

Проверяет пользовательский или системный сценарий через максимально приближённый к реальному путь выполнения.

В AUD-019 основной целью E2E является **архитектура и обучение**, а не полноценное покрытие приложения.

Должно быть понятно:

- куда помещать E2E tests;
- где хранить fixtures;
- где хранить helpers;
- где размещать page objects или аналогичный слой;
- как конфигурируется E2E runner;
- как запускать E2E локально;
- как в будущем добавить реальный сценарий.

---

## 5. Test runner

Основной test runner:

**Jest**

Конфигурация должна иметь root-level точку входа и поддерживать независимое тестирование частей repository.

Базовая конфигурация должна быть общей, а package-specific особенности допускаются там, где они действительно нужны.

## 6. Test utilities

Предусмотреть общий слой `test-utils` для будущих:

- fixtures;
- factories;
- mocks;
- stubs;
- fakes;
- test helpers;
- общего test setup.

Не следует заранее заполнять его большим количеством абстракций без необходимости. AUD-019 должен показать назначение этого слоя и дать несколько учебных примеров.

---

## 7. Учебные примеры

Примеры тестов должны быть сложнее примитивного `2 + 2 = 4`.

Основной учебный пример должен демонстрировать взаимодействие нескольких систем.

Например:

```
System 1
   |
   v
Service
   |
   +------> Repository mock
   |
   +------> External API mock
                    |
                    v
                 System 2
```

Тест должен показывать:

- входные данные;
- вызов системы;
- взаимодействие с зависимостями;
- mock/stub/fake;
- проверку результата;
- проверку вызовов зависимостей;
- обработку ошибки;
- несколько вариантов поведения.

При этом учебные системы могут быть искусственными. Их задача — служить reusable шаблонами для будущих тестов проекта.

---

## 8. Coverage

AUD-019 должен не просто включить coverage, а использовать его как учебный материал.

Необходимо показать:

- что такое code coverage;
- Statements;
- Lines;
- Functions;
- Branches;
- как меняются показатели при добавлении тестов;
- почему высокий coverage не гарантирует качество тестов.

На первом этапе **не вводится обязательный процент coverage**.

Цель — научиться измерять и интерпретировать coverage.

### Сравнение инструментов

Необходимо провести практический эксперимент минимум с двумя механизмами/инструментами coverage, чтобы увидеть различия в:

- собираемой статистике;
- формате отчёта;
- локальном использовании;
- пригодности для CI.

После сравнения один подход может быть выбран как основной для CI.

## 9. Lint

AUD-019 должен создать полноценную lint-инфраструктуру.

Lint также рассматривается как учебный инструмент.

Необходимо:

- выбрать и подключить lint tool;
- создать конфигурацию;
- показать, какие категории проблем он обнаруживает;
- получить реальные примеры результатов;
- объяснить отличие lint от test и coverage.

При наличии ценности допускается сравнить несколько инструментов/режимов перед выбором основного CI-варианта.

---

## 10. CI

Должна существовать единая локальная команда:

```bash
npm run ci
```

Она должна выполнять тот же концептуальный набор проверок, который требуется CI.

Общие команды должны находиться в npm scripts, чтобы GitHub и GitLab не содержали две независимые реализации одной и той же логики.

Целевая модель:

```
                  npm scripts
                 /           \
                /             \
       GitHub Actions       GitLab CI
                \             /
                 \           /
                  CI contract
```

CI YAML является orchestration layer, а не местом дублирования всей логики проекта.

---

## 11. GitHub Actions

Создать реальный workflow в:

```
.github/workflows/
```

Workflow должен демонстрировать полный жизненный цикл проверки проекта:

```
install
  ↓
typecheck
  ↓
test
  ↓
coverage
  ↓
lint
  ↓
build
```

Конкретный набор шагов должен быть согласован с фактическими npm scripts и текущей архитектурой repository.

Запуск:

- push;
- pull request.

Использовать одну фиксированную версию Node.js и Ubuntu runner.

---

## 12. GitLab CI

Создать реальный:

```
.gitlab-ci.yml
```

Он должен выполнять тот же общий CI-контракт.

При этом документация должна отдельно показать различия между GitHub Actions и GitLab CI:

- jobs;
- stages;
- runners;
- cache;
- artifacts;
- conditions/rules;
- dependencies;
- environment variables.

Цель — получить возможность не только иметь два YAML-файла, но и изучить две модели CI.

---

## 13. CI как учебный материал

AUD-019 должен позволять запускать проверки:

### Локально

```bash
npm test
npm run lint
npm run coverage
npm run ci
```

### В GitHub

Через GitHub Actions.

### В GitLab

Через GitLab CI.

Таким образом, одна и та же проверка проходит через три среды:

```
local
  |
  +--> GitHub Actions
  |
  +--> GitLab CI
```

## 14. Поведение при отсутствии тестов

`npm test` должен ожидать существование предусмотренной тестовой структуры.

Правило:

- если ожидаемая структура тестов отсутствует — это ошибка конфигурации;
- если структура существует, но конкретных тестов пока нет — отсутствие тестов само по себе не является ошибкой.

Это важно, поскольку содержательные тесты будут добавляться отдельными AUD-задачами.

## 16. Требования к будущим тестам

AUD-019 должен зафиксировать обязательные правила для последующих задач.

В частности:

- тест должен быть deterministic;
- тест не должен зависеть от внешней сети без явного архитектурного обоснования;
- unit-тесты должны изолировать внешние зависимости;
- mocks/stubs/fakes использовать осознанно;
- тест должен быть запускаем локально;
- тест должен быть совместим с CI;
- тест не должен изменять production state без необходимости;
- тест должен находиться в соответствующем каталоге;
- имя теста должно соответствовать принятому соглашению;
- тест должен проверять поведение, а не внутреннюю реализацию без необходимости.

## 19. Definition of Done для эпика

Эпик считается архитектурно завершённым, когда:

- существует согласованная структура тестовых каталогов;
- Jest работает локально;
- package-level тестовые пространства запускаются независимо;
- существует общий слой test utilities;
- существуют учебные unit/integration/E2E примеры;
- coverage можно запустить и изучить;
- результаты coverage документированы;
- lint можно запустить и изучить;
- существует локальная команда `npm run ci`;
- существует GitHub Actions workflow;
- существует GitLab CI configuration;
- локальный и CI-процессы используют общий набор npm-команд;
- `docs/testing.md` содержит архитектуру и практические примеры;
- зафиксированы правила добавления будущих тестов;
- production-код не был изменён только ради тестирования;
- дальнейшие задачи могут добавлять содержательные тесты, не пересматривая базовую архитектуру.
