# AUD-019-02 — Shared Test Priority

Рабочий документ. Этот файл определяет, какие тесты создавать следующими.

Источник данных: AUD-019-02-Shared-Test-Inventory.md.

Правила формирования приоритетов определены в AUD-019-02-Shared-Tests.md.

## 1. Назначение

Inventory отвечает:

> Что существует и что покрыто?

Priority отвечает:

> Что разработчику тестов делать следующим?

Priority регулярно пересматривается после изменения Inventory.

## 2. Правила приоритизации

Базовая последовательность:

1. элементы без какого-либо теста;
2. элементы без success-теста;
3. важное observable behavior без теста;
4. критичные failure/exception сценарии;
5. существенные edge cases;
6. async/state/concurrency/side-effect/dependency сценарии;
7. дополнительные сценарии уже хорошо покрытых элементов.

При равном приоритете сначала выбирать:

- более простой тест;
- тест, снимающий существенную неопределённость;
- тест, блокирующий дальнейшее понимание поведения;
- тест, покрывающий значимую часть observable behavior.

Количество уже написанных тестов само по себе не является причиной понижать приоритет.

## 3. Баланс между методами

Нельзя бесконечно углубляться в один метод.

Например:

| Метод | Success | Edge | Exception |
|---|---|---|---|
| A | [x] | [x] | [ ] |
| B | [ ] | [ ] | [ ] |
| C | [x] | [x] | [ ] |

Если exception для A не является критичным, а B вообще не имеет success-теста, Priority должен рассмотреть B раньше углубления A.

Таким образом, план управляет распределением усилий по всей системе.

## 4. Формат задач

| Priority | Файл / модуль | Класс / функция | Метод / сценарий | Категория | Почему сейчас | Сложность | Предварительное решение | Статус |
|---|---|---|---|---|---|---|---|---|
| P1 | <file> | <class/function> | <method> | success | нет ни одного теста | low | direct unit test | TODO |
| P2 | <file> | <class/function> | <method> | exception | важное поведение не покрыто | medium | Jest exception assertion + dependency stub | TODO |
| P3 | <file> | <class/function> | <method> | concurrency | часть контракта | high | controlled concurrent calls | TODO |

Статусы:

TODO
READY
IN PROGRESS
DONE
BLOCKED
REPLAN

## 5. Формирование нового Priority

После изменения Inventory:

1. исследователь фиксирует изменения;
2. эксперт пересматривает применимые сценарии;
3. незавершённые сценарии сравниваются между собой;
4. формируется новый порядок;
5. устаревшие задачи переводятся в DONE, REPLAN или удаляются из текущего плана;
6. новые элементы получают приоритет.

Priority должен отражать текущее состояние Inventory, а не исторический порядок обнаружения методов.

## 6. Критерий READY

Элемент можно передавать исполнителю как READY, если в Inventory достаточно информации:

- конкретный метод/сценарий;
- категория;
- observable behavior;
- тип теста;
- способ тестирования;
- существенные зависимости;
- test doubles, если нужны;
- ограничения.

Если данных недостаточно, задача не передаётся исполнителю как READY.

## 7. Критерий завершения текущего Priority

Текущий блок Priority считается выполненным, когда:

- у всех элементов с более высоким приоритетом есть решение;
- нет необоснованно пропущенного элемента без базового success-теста;
- критичные failure/exception сценарии не отложены без причины;
- каждый следующий элемент имеет понятный способ реализации;
- после выполнения блока Priority пересмотрен по актуальному Inventory.
