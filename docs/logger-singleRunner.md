# Single-Runner и Логер: идеология, архитектура, комбинирование

> Документ фиксирует договорённости по модулям `single-runner` и `logger`:
> зачем они существуют, какие задачи решают, какие — сознательно не решают,
> и как их правильно комбинировать.

---

## Часть 1. Логер

### 1.1. Идеология

Логер — это **конвейер обработчиков событий**, а не «обёртка для console.log».

Каждая стадия конвейера (декоратор) получает на вход событие (старт / финиш / ошибка) и решает две независимые задачи:

1. **Доставить событие получателю.** Сейчас — `console`. Дальше — файл, БД, что угодно. Набор получателей конфигурируется.
2. **Решить, что делать с событием дальше.** Пропустить следующей стадии или остановить поток.

Декораторы навешиваются **каскадом**. Один метод может быть обёрнут несколькими логерами:

```
@LogToFile
@LogToDb
@LogToConsole
@Safe
method() {}
```

Первый пишет в файл и пропускает дальше, второй — в БД и пропускает, третий — в консоль и пропускает, четвёртый — поглощает и **завершает цепочку**. Как `next()` в Express, которого не вызвали.

### 1.2. Ключевой тезис

`Safe` в имени `LogSafe` — это **не «сломанное логирование»**. Это стадия конвейера, играющая роль **терминатора**: событие дошло до неё, было доставлено во все получатели выше по стеку — и дальше не идёт.

Логирование и обработка ошибок — **два ортогональных измерения**:

- Логировать можно с пробросом ошибки и с её подавлением.
- Выбор — за вызывающим кодом, через имя декоратора.

### 1.3. Семантика декораторов

| Декоратор | Пишет в лог | Пробрасывает исключение |
|---|---|---|
| `Log` | да | **да** |
| `LogParam` | да (+аргументы) | да |
| `LogExecutionName(label)` | да (свой label) | да |
| `LogSafe` | да | **нет** (возвращает `null`) |
| `LogParamSafe` | да (+аргументы) | нет |
| `Safe` | нет (только `console.error`) | нет |

Правило именования: **`Safe` в имени = «ошибка не пробрасывается»**. Отсутствие `Safe` = «пробрасывается».

### 1.4. Когда что использовать

- Обычные операции, где ошибка = ошибка → `Log` / `LogParam`.
- Атомарные операции внутри батча (`Promise.all` по тысяче элементов), где падение одного элемента не должно валить весь батч → `*Safe`.
- Просто «проглотить и забыть», без логов → `Safe`.

### 1.5. Разделение ответственности

- **Logger отвечает за:** куда ошибка попадает, проглотить её или пробросить, как её увидит вызывающий код.
- **Runner отвечает за:** как рейсы группируются, когда открывается новый, когда ошибка залипает / уничтожается.

**Никогда наоборот.** Runner не пишет в консоль. Logger не управляет состоянием рейсов.

## Часть 2. Single-Runner

### 2.1. Идеология

Есть долгие тяжёлые операции (минуты). Желающих получить результат — много. Полноценное решение — **таски**: создать задачу, вернуть id, поллить статус. Это инфраструктурно дорого.

Single-runner — **лёгкая аппроксимация тасок без их инфраструктуры**.

Метафора: **автобус**. Первый пассажир открывает рейс. Кто пришёл, пока автобус едет, — едет вместе со всеми и выходит на той же остановке. Когда рейс приземлился — слот освобождён.

Это:

- **НЕ мемоизация** — результат не кэшируется.
- **НЕ очередь** — никто не ждёт своей очереди, все прилипают к текущему.
- **НЕ ограничитель параллелизма** — гарантирует лишь, что в один момент для одного автомата идёт не более одного рейса.

### 2.2. Чего single-runner НЕ делает

**Single-runner НЕ обрабатывает ошибки.**

У него нет доступа к получателям (консоль, файл, БД) и не должно быть. Куда положить ошибку, кому её показать, проглотить её или пробросить — это всегда решение **логера**.

Раннер, получив ошибку, имеет право только на одно действие: **изменить своё собственное состояние**. Всё остальное — вне его зоны ответственности.

Если в системе нет логера — это вопрос к тому, кто собрал систему без логера, а не к раннеру.

### 2.3. Автомат состояний

```
IDLE     — рейса нет, ошибки нет.
RUNNING  — рейс в воздухе, есть Promise.
FAILED   — рейса нет, есть залипшая ошибка (+ timestamp для TTL).
```

Переходы:

```
IDLE    → RUNNING   при первом пассажире
RUNNING → IDLE      при успехе
RUNNING → ???       при ошибке — зависит от поведения
FAILED  → RUNNING   при снятии залипания
```

### 2.4. Поведение при ошибке: два измерения

**Измерение 1 — что делать с ошибкой.**

- **RETRY** — слот освобождается, следующий пассажир открывает новый рейс. Состояние FAILED не используется.
- **STICKY** — ошибка залипает. Все приходящие получают тот же reject, пока залипание не снято.

**Измерение 2 — как снимается залипание** (актуально только для STICKY).

- **По времени (TTL).** У залипшей ошибки есть «срок годности». После истечения следующий пассажир открывает новый рейс.
- **Внешним сбросом.** Кто-то извне (сосед-метод на общем guard'е или явный `guard.reset()`) снимает залипание.

Отсюда три практических режима:

| Режим | Что это |
|---|---|
| `retry` | RETRY |
| `ttl` | STICKY + снятие по времени |
| `strict` | STICKY + снятие внешним сбросом |

### 2.5. Почему strict без guard'а не существует

Strict без guard'а — это клетка, в которой **снятия залипания нет вообще**. Не «редкий режим», а отсутствие механизма восстановления. Если упало — упало навсегда, до конца жизни процесса.

Такое поведение **не должно быть выразимо** через single-runner. Если реально нужно «раз упало, значит навсегда» — это доменная логика (флаг в БД, состояние в бизнес-объекте), а не забота раннера.

Поэтому `strict` доступен **только на общем внешнем guard'е**, где есть сосед-метод или явный `reset()`. Без guard'а — только `retry` и `ttl`.

### 2.6. Две независимые оси API

**Ось 1 — где живёт автомат (guard).**

- **Внутренний.** Guard создаётся декоратором по символу внутри экземпляра (для методов) или в замыкании (для свободных функций). Один метод/функция = один автомат. Сброс снаружи невозможен.
- **Внешний.** Guard передаётся снаружи. Может быть общим для нескольких методов. Даёт доступ к `reset()` и позволяет `strict`.

**Ось 2 — поведение при ошибке.**

- Внутренний автомат: `retry` или `ttl`.
- Внешний автомат: `retry`, `ttl` или `strict`.

### 2.7. Таблица API

**Свободные функции.** В TypeScript декораторов на функциях нет — только HOF-применение.

| Фабрика | Режим | Автомат |
|---|---|---|
| `createSingleRunner(fn)` | retry | свой, в замыкании |
| `createSingleRunnerTTL(fn, ms)` | ttl | свой, в замыкании |

**Методы класса, внутренний автомат** (символ на экземпляре).

| Декоратор | Режим | Скобки |
|---|---|---|
| `@SingleExecution` | retry | без скобок |
| `@SingleExecutionTTL(ms)` | ttl | со скобками |

**Методы класса, общий внешний автомат** (передаётся guard).

| Декоратор | Режим | Скобки |
|---|---|---|
| `@SingleGuardedRetry(guard)` | retry | со скобками |
| `@SingleGuardedStrict(guard)` | strict | со скобками |
| `@SingleGuardedTTL(guard, ms)` | ttl | со скобками |

Правило: **скобки появляются, только если декоратору что-то нужно передать** (guard или ms). Если передавать нечего — декоратор без скобок.

### 2.8. Использование SingleRunner для свободных функций

для свободных функций это — **HOF-обёртка**:

```ts
const fetchUsers = createSingleRunner(rawFetchUsers);
const fetchFeed  = createSingleRunnerTTL(rawFetchFeed, 30_000);
```

Guard живёт в **замыкании обёртки**. Поделиться автоматом с другой функцией через эти фабрики нельзя. Если нужно — заводится общий `ExecutionGuard` и передаётся в соответствующие фабрики/декораторы явно.

**Почему не другие места для guard'а:**

- Глобальный реестр по имени (`Map<string, Guard>`) — **service locator**. Глобальное мутабельное состояние, невидимое из сигнатур, коллизии имён, утечки между тестами. Не надо.
- `WeakMap<Function, Guard>` — магия: «дважды обернул ту же функцию → общий автомат». Редко то, что нужно, легко запутаться.
- Свойство на самой функции — то же, что WeakMap, но с порчей оригинальной функции.
- Один глобальный guard на всё — антипаттерн: одна упавшая функция залипает всех.

**Здоровое правило:** если хочешь шарить автомат — передай guard явно. Если не передаёшь — автомат должен быть свой, локальный, запертый в замыкании.

### 2.9. Strict и retry на одном автомате

Strict и retry могут сосуществовать на **одном** автомате, если повесить их на общий внешний guard разными декораторами:

```ts
const syncGuard = new ExecutionGuard();

@SingleGuardedStrict(syncGuard)
fetchStrict() { ... }

@SingleGuardedRetry(syncGuard)
fetchRetry() { ... }
```

Сценарий:

```
t0: fetchStrict() → RUNNING
t1: рейс упал → FAILED (E)
t2: fetchStrict() → получает E (FAILED → FAILED)
t3: fetchStrict() → получает E (FAILED → FAILED)
t4: fetchRetry()  → E уничтожена, слот очищен, открыт новый рейс
t5: fetchStrict() → прилипает к новому рейсу (RUNNING)
```

**RETRY при входе в FAILED-состояние УНИЧТОЖАЕТ залипшую ошибку.** Это не побочный эффект, а осознанная семантика. RETRY говорит: «я не верю, что эта ошибка окончательна, я открываю новый рейс».

Strict-пассажир в цикле «ждёт попутчика» — дожидается, пока кто-то другой проявит инициативу. Явный сброс strict'у не нужен.

**Важно:** Это реализуется **только через внешний guard**, не через параметры метода. Параметры метода не должны знать о режимах — это захламляет бизнес-логику.

### 2.10. Явный сброс

У `ExecutionGuard` есть метод `reset()`. Он сбрасывает залипшую ошибку (состояние FAILED). На идущий рейс (RUNNING) не влияет.

Актуален только для `strict`/`ttl` на внешнем guard'е. Внутренние декораторы сбросить нельзя — там guard спрятан и недоступен снаружи.

## Часть 3. Комбинирование логера и single-runner

### 3.1. Порядок декораторов

Применение — снизу вверх: `@A @B @C method()` = `A(B(C(method)))`.
Вызов — сверху вниз: `A → B → C → method`.
Возврат — обратно: `method → C → B → A`.

**Верхний декоратор** — ближний к вызывающему коду.
**Нижний декоратор** — ближний к телу метода.

### 3.2. Логер снаружи, раннер внутри: `@L @S M`

Аналогия: логер — вахтёр на проходной, отмечает каждого вошедшего. Раннер — диспетчер, решает, нужен ли ещё один рабочий день или все присоединяются к текущей смене.

```
Вызов пассажира
  → L логирует «запустилась»       ← пассажир виден логу
  → S решает:
      • если рейс идёт — возвращает его же, M не вызывается;
      • если рейса нет — открывает новый, вызывает M.
  → L логирует «завершилась» или «ошибка».
```

**Логер видит:** каждый вызов, включая присоединившихся.
**Логер не видит:** какие вызовы были реальными запусками, а какие — прилипли.

**Пример трассировки при 3 конкурентных вызовах, где реально выполнился один:**

```
[search] запустилась
[search] запустилась
[search] запустилась
[search] завершилась (1234.56ms)
[search] завершилась (1234.58ms)
[search] завершилась (1234.59ms)
```

Длительность примерно одна — это выдаёт, что реально был один запуск.

### 3.3. Раннер снаружи, логер внутри: `@S @L M`

Аналогия: раннер — вахтёр, пропускает внутрь только первого в смену. Остальные ждут снаружи и получают тот же результат, но внутрь (к логеру) не заходят.

```
Вызов пассажира
  → S решает:
      • если рейс идёт — возвращает его же. M и L НЕ вызываются;
      • если рейса нет — открывает новый, только теперь:
          → L логирует «запустилась»
          → M выполняется
          → L логирует «завершилась» / «ошибка».
```

**Логер видит:** только реальные запуски. Присоединившиеся невидимы.
**Логер не видит:** сколько всего было вызовов.

**Пример трассировки при тех же 3 конкурентных вызовах:**

```
[search] запустилась
[search] завершилась (1234.56ms)
```

Одна пара строк. Пассажиры 2 и 3 не оставили следов.

**Это критично, когда логер пишет не в консоль, а в файл или БД:** N одинаковых записей об одной ошибке — мусор.

### 3.4. Бургер: `@L @S @L M`

Логер → раннер → логер. Два разных логера с разными префиксами.

Идея: внешний логер отвечает на вопрос **«кто дёрнул метод»**, внутренний — на вопрос **«что реально выполнилось»**.

- Внешний L видит **нагрузку**: сколько раз метод дёрнули.
- Внутренний L видит **исполнение**: сколько реальных запусков было.
- Разница между ними — **мера того, насколько хорошо single-runner экономит работу**.

**Пример при 3 конкурентных вызовах, где реально выполнился один:**

```
[call: search] запустилась
[call: search] запустилась
[call: search] запустилась
[exec: search] запустилась
[exec: search] завершилась (1234ms)
[call: search] завершилась (1234ms)
[call: search] завершилась (1234ms)
[call: search] завершилась (1234ms)
```

Читается так: «три клиента позвали, но реально работал один».

### 3.5. Бургер на ошибке — четыре подварианта

При ошибке в `M` семантика зависит от того, какой именно логер стоит на каждой позиции.

**3.5.1. `@Log @S @Log M` — оба пробрасывают.**

```
[call] запустилась
[exec] запустилась
[exec] ошибка через 1234ms   ← внутренний L записал
[call] ошибка через 1234ms   ← внешний L записал ТУ ЖЕ ошибку
```

Ошибка проходит насквозь. Вызывающий получит reject.
**Применение:** нужен и взгляд на звонящего, и взгляд на исполнителя, и ошибка должна дойти до клиента.

**3.5.2. `@LogSafe @S @Log M` — внешний глотает, внутренний пробрасывает.**

```
[call] запустилась
[exec] запустилась
[exec] ошибка через 1234ms   ← внутренний L записал и пробросил
[call] ошибка через 1234ms   ← внешний L записал и проглотил
```

Ошибка оседает во внешнем `LogSafe`. Вызывающий получит `null`.
**Применение:** клиент хочет best-effort — «если не получилось, покажи пустоту, я сам разберусь».

**3.5.3. `@Log @S @LogSafe M` — внутренний глотает, внешний не видит ошибки.**

```
[call] запустилась
[exec] запустилась
[exec] ошибка через 1234ms   ← внутренний L записал и проглотил
[call] завершилась (1234ms)  ← внешний L видит УСПЕХ
```

Внешний логер не подозревает, что что-то упало. Для него метод завершился успешно.
**Применение:** редко и осознанно. Обычно такое поведение **маскирует проблемы**.

**3.5.4. `@LogSafe @S @LogSafe M` — оба глотают.**

```
[call] запустилась
[exec] запустилась
[exec] ошибка через 1234ms   ← внутренний L записал и проглотил
[call] завершилась (1234ms)  ← внешний L видит УСПЕХ
```

По факту работает как 3.5.3, но с более явной записью «мы тут не падаем».

### 3.6. Итоговая таблица

| Задача | Комбинация |
|---|---|
| Видеть в логе каждый вызов (включая присоединившихся) | `@L @S M` |
| Видеть только реальные запуски (без шума от пассажиров) | `@S @L M` |
| Видеть и то, и другое: нагрузку и исполнение | `@L @S @L M` (бургер) |
| Ошибка должна дойти до клиента | внешний и внутренний L — оба `Log` |
| Ошибка оседает в логе, клиент получает `null` | внешний L = `LogSafe` |
| Много повторных вызовов (strict-цикл, ttl-опрос) | логер **под** раннером, иначе лог заполнится повторами одной ошибки |
| Экономия работы важна — хочу её видеть в цифрах | бургер, разница между `call` и `exec` покажет коэффициент склейки |

### 3.7. Золотое правило

> **Логер снаружи — про нагрузку** (кто звал).
> **Логер внутри — про исполнение** (что делалось).
> **Runner между ними — про склейку** (кто с кем летел).
>
> При ошибке каждый логер пишет свою запись со своим префиксом.
> Захотел один префикс — ставь один логер.
> Захотел два разных взгляда на одну ошибку — бургер.
>
> **Пробрасывать или глотать — решает ТОЛЬКО логер.**
> **Runner на семантику ошибки не влияет и не имеет права влиять.**

## Часть 4. Контекст: зачем всё это

### 4.1. Аудит и его замечания

Сторонний аудит системы сформулировал два замечания (AUD-002, AUD-003), с которыми было решено не согласиться по существу. Разбор замечаний привёл к формулировке идеологии, изложенной в этом документе.

### 4.2. AUD-002 — «Ошибки бизнес-операций скрываются»

**Замечание:** `LogSafe` и `Safe` возвращают `null` вместо проброса исключения. Возможен сценарий: sync падает, ошибка скрывается, HTTP всё равно сообщает OK.

**Позиция:**

1. **Логирование ≠ глотание.** В модуле есть `Log`/`LogParam`, которые логируют и **пробрасывают** исключение, и `LogSafe`/`Safe`/`LogParamSafe`, которые логируют и **сознательно** возвращают `null`. Это разные инструменты с разной семантикой, а не «логирование, которое случайно ломает исключения».

2. **`@Safe`/`@LogSafe` используются в батч-контексте.** `ExecUsers` и `FilesUser` делают `Promise.all` по пользователям и файлам. Падение одного элемента **не должно** валить весь батч — иначе одна битая сессия из тысячи останавливает синк. Ошибка при этом пишется в `console.error` — то есть не «скрывается», а попадает в лог.

3. **HTTP 200 — вопрос контракта, а не «скрытия».** Если эндпоинт `/update` задуман как best-effort sync («запусти, обработай что можно, остальное залогируй») — 200 корректен. Если требуется атомарность — это отдельное продуктовое решение, а не дефект системы логирования.

### 4.3. AUD-003 — «SingleExecution может создавать unhandled rejection»

**Замечание:** в `createSingleCallGuard` и `ExecutionGuard` результат `Promise.finally()` игнорируется. При rejection производный Promise тоже rejected и потенциально становится источником `unhandledRejection`.

**Позиция:**

1. **Технически верно как наблюдение о паттерне.** `.finally()` действительно создаёт производную промису, которая при реджекте тоже реджектится.

2. **В текущей кодовой базе сценарий не воспроизводится.** `@SingleExecution` применяется поверх `@LogSafe`, а `LogSafe` не пробрасывает исключения — исходная промиса никогда не реджектится.

3. **Это зависимость от порядка декораторов — хрупкая.** Правильное решение — не полагаться на соседа, а сделать `SingleExecution` агностиком по ошибкам: `.then(cleanup, cleanup)` вместо `.finally(cleanup)`. Это снимает AUD-003 по существу.

4. **Severity — Low/Medium, не High.** Это не найденный баг, а замечание о паттерне.

### 4.4. Что принято из аудита

- **Явный контракт поведения при ошибке.** Раньше семантика single-runner при ошибке была неявной («после ошибки слот освобождается»). Теперь это оформлено как режимы `retry` / `ttl` / `strict`, каждый с явной диаграммой переходов.
- **Отказ от `.finally()` в пользу `.then(onSuccess, onError)`.** Обе ветки обрабатываются, unhandled rejection не возникает — независимо от того, что лежит под декоратором.
- **`ExecutionGuard.reset()`.** Появился явный API сброса залипшей ошибки.

### 4.5. Что не принято

- Переклассификация системы как дефектной на основе AUD-002/AUD-003.
- Утверждение «логирование не должно менять семантику исключения» применительно к `*Safe`-декораторам — это не «логирование», а конвейерные стадии с явной терминальной семантикой.
- Требование менять HTTP-контракт эндпоинта `/update` без обсуждения самого контракта.

## Приложение. Быстрый справочник

### Логер — выбор декоратора

| Ситуация | Декоратор |
|---|---|
| Обычная операция, ошибка = ошибка | `Log` |
| Хочу видеть аргументы в логе | `LogParam` |
| Хочу свой label в логе | `LogExecutionName("my-label")` |
| Атомарная операция в батче | `LogSafe` / `Safe` |
| Просто проглотить, без логов | `Safe` |

### Single-runner — выбор API

| Ситуация | API |
|---|---|
| Свободная функция, свой автомат | `createSingleRunner(fn)` |
| Свободная функция, ttl | `createSingleRunnerTTL(fn, ms)` |
| Метод, свой автомат, retry | `@SingleExecution` |
| Метод, свой автомат, ttl | `@SingleExecutionTTL(ms)` |
| Метод, общий автомат, retry | `@SingleGuardedRetry(guard)` |
| Метод, общий автомат, strict | `@SingleGuardedStrict(guard)` |
| Метод, общий автомат, ttl | `@SingleGuardedTTL(guard, ms)` |

### Single-runner — выбор режима

| Ситуация | Режим |
|---|---|
| Транзиентные ошибки (сеть, таймаут), повтор осмыслен | `retry` |
| Транзиентная ошибка + «период остывания» | `ttl(ms)` |
| Ошибка окончательная, есть кому снять залипание | `strict` + guard |

### Комбинирование с логером

| Хочу | Порядок |
|---|---|
| В логе — каждый вызов | `@L @S M` |
| В логе — только реальные запуски | `@S @L M` |
| В логе — и нагрузка, и исполнение | `@L @S @L M` |
