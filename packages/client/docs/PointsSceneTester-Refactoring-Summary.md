# Резюме рефакторинга PointsSceneTester

## Зачем проводился рефакторинг

Основная цель рефакторинга была **не в том, чтобы добавить тестовый режим в `dev`**, а в том, чтобы очистить архитектуру графовой части клиента и подготовить её к дальнейшим форкам проекта.

Изначальная задача состояла в разделении:
- общего механизма работы с графом;
- источника/потока данных, который этот граф наполняет;
- логики, специфичной именно для embeddings.

В результате `PointGraphManager` стал общей точкой управления графом, не зависящей от конкретного способа получения данных. Это позволяет в будущем заменить один поток данных другим, не переделывая `PointsScene`, `EdgesScene`, физические алгоритмы и остальную графовую инфраструктуру.

**Важно:** в текущей ветке `dev` сохранено первоначальное поведение приложения (`dw`). `PointsSceneTester` был нужен для отдельной ветки/сценария тестирования и не является новым основным режимом работы `dev`.

## Что было сделано

### 1. Выделен общий `PointGraphManager`

`PointGraphManager` отвечает за жизненный цикл точек и графовых рёбер:
- добавление точек;
- удаление точек;
- обновление набора точек;
- создание и удаление рёбер;
- хранение графа через `NeighborGraph`;
- получение точек и рёбер для представлений и алгоритмов.

При этом менеджер работает с базовыми `Point` и `Edge` и не знает об embeddings.

Это принципиально: общий графовый слой не должен зависеть от конкретной модели данных, используемой одним из потоков.

### 2. Отделена embedding-специфичная логика

`PointModel` и `EdgeModel` используются там, где действительно нужны embeddings.
`ModelManager` продолжает заниматься embedding-логикой и оптимизацией, но общая графовая инфраструктура больше не должна быть привязана к ней концептуально.

Получилась граница:

```text
Point
  ↑
PointModel + embeddings

Edge
  ↑
EdgeModel + embedding-specific data
```

Общий граф работает на уровне `Point` / `Edge`, а embedding-логика расширяет его при необходимости.

### 3. `PointsScene` и `EdgesScene` отвязаны от embeddings

Графовые сцены работают с базовыми сущностями:
- `PointsScene` — с `Point`;
- `EdgesScene` — с `Edge`.

Благодаря этому визуализация графа не требует наличия embedding-моделей.

Это делает её пригодной для будущих потоков данных, которым embeddings вообще не нужны.

### 4. `PointsSceneTester` стал отдельным источником данных

`PointsSceneTester` использовался как самостоятельный сценарий генерации и изменения данных для проверки графовой сцены.

Он отвечает за:
- генерацию тестовых точек;
- изменение существующих точек;
- формирование тестовых связей;
- нагрузочное/динамическое изменение графа.

При этом изменение количества точек передано владельцу жизненного цикла — `PointGraphManager`.

То есть тестер может изменить `x`, `y`, `text` у существующей точки, но добавление и удаление точек выполняется через `PointGraphManager`.

```text
PointsSceneTester
      ↓
PointGraphManager
```

### 5. Убрано дублирование состояния графа

`PointGraphManager` не создаёт отдельную копию коллекции рёбер.
Граф хранится в `NeighborGraph`, а менеджер предоставляет к нему необходимый интерфейс.

Тем самым уменьшается количество мест, которые могут содержать расходящееся состояние.

### 6. Уточнена ответственность `NeighborGraph`

`NeighborGraph` является владельцем графовых связей и их связности.
`PointGraphManager` выступает уровнем управления жизненным циклом сущностей, а не альтернативным хранилищем графа.

### 7. Жизненный цикл точек проходит через одного владельца

Особенно важным результатом стало правило:

> **Количество точек меняет `PointGraphManager`.**

Внешние компоненты могут менять свойства уже существующих точек, но добавление/удаление сущностей должно проходить через менеджер.

Такой контракт важен для будущих форков: новый источник данных должен подключаться к существующему механизму управления графом, а не получать возможность напрямую менять его внутренние коллекции.

### 8. `AnimationEngine` выделен как отдельный владелец анимационного цикла

В ходе рефакторинга была закреплена отдельная ответственность `AnimationEngine` за `requestAnimationFrame`.
Это отделяет механизм запуска кадров от алгоритмов и моделей.

## Что получилось архитектурно

Основной принцип выглядит так:

```text
             источник данных
              /           \
             /             \
       DataManager     PointsSceneTester
             \             /
              \           /
               PointGraphManager
                       |
                NeighborGraph
                  /         \
             PointsScene   EdgesScene
                  |
             Graph/Physics
```

При этом embedding-специфичная часть остаётся отдельной веткой:

```text
ModelManager
     |
 PointModel / EdgeModel
     |
 embeddings / optimization
```

То есть задача рефакторинга заключалась в том, чтобы **граф перестал быть частью конкретного data-flow**.

## Почему это важно для форков

Предполагаемый следующий шаг развития проекта — создание форков с другими источниками данных.

Например, текущий поток:

```text
DW data flow
     ↓
PointGraphManager
```

может быть заменён на:

```text
Other data flow
     ↓
PointGraphManager
```

или:

```text
File / API / generated data / another model
                    ↓
             PointGraphManager
```

При этом существующие `PointsScene`, `EdgesScene`, `NeighborGraph`, `GraphAlgorithm`, `RepulsionAlgorithm` и `ZDapperAlgorithm` не должны переписывать свою логику только потому, что изменился источник данных.

Именно это является главным архитектурным результатом работы.

## Что осталось в `dev`

Текущий `dev` сохраняет первоначальный рабочий сценарий:

```text
index.ts
   ↓
DW()
   ↓
ModelManager
   ↓
PointGraphManager
   ↓
PointsScene / EdgesScene / physics
```

Тестовый сценарий `PointsSceneTester` существует отдельно и не подменяет исходное поведение `dev`.

В `index.ts` тестер при этом оставлен как отдельный альтернативный путь запуска, но выбранным режимом остаётся:

```text
PointGraphManager("dw", mediator, animationEngine)
```

## Итоговая идея

Рефакторинг был сделан не ради самого `PointsSceneTester`.
`PointsSceneTester` был инструментом, на котором удалось проверить и проявить правильную границу ответственности.

Главная идея:

> **Графовая инфраструктура должна быть независима от конкретного источника данных.**

Источник данных создаёт/изменяет `Point`, а `PointGraphManager` отвечает за их жизненный цикл и превращение этих данных в управляемый граф.

Благодаря этому дальнейший форк проекта может заменить `DW` на другой поток данных, сохранив большую часть графовой инфраструктуры без копирования и переписывания её внутренней логики.
