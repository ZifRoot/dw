# AnimationEngine

## Основные идеи

AnimationEngine — инфраструктурный планировщик покадровой работы клиентского приложения.

1. **Единый владелец `requestAnimationFrame`.** Только AnimationEngine управляет animation loop.
2. **Максимальное использование времени кадра.** Планировщик старается выполнить максимум зарегистрированной работы в доступном времени текущего кадра.
3. **Перенос невыполненной работы на следующие кадры.** Не помещающаяся работа продолжается в следующих кадрах.
4. **AnimationEngine не знает смысла работы.** Callback для него — абстрактная функция.
5. **Работа представляется последовательностью шагов.** Большая задача должна быть разделена вызывающей стороной на отдельные callback-операции.
6. **Последовательность может предоставляться callback'ом или группой callback'ов.** Текущий API предоставляет `addCallback` и `addCallbacks`.

AnimationEngine отвечает за **время выполнения и планирование**, а смысл работы остаётся у потребителя.

## Единый requestAnimationFrame

### Почему несколько RAF создают проблему

Разные подсистемы могут самостоятельно создавать циклы `requestAnimationFrame`. Они конкурируют за одно и то же время кадра, не имеют общего бюджета и усложняют согласованное планирование и остановку.

### Почему нужен единый планировщик

AnimationEngine — единственная точка доступа подсистем к animation loop:

    ModelManager ───────┐
    LevenshteinManager ─┼──→ AnimationEngine ──→ requestAnimationFrame
    EnginePipeline ─────┘

Потребители регистрируют работу, а AnimationEngine решает, когда её выполнять.

## Представление работы

### `addCallback`

`addCallback(callback)` регистрирует один самостоятельный callback и возвращает disposer для его удаления.

### `addCallbacks`

`addCallbacks(callbacks)` принимает массив callback'ов и возвращает один disposer для всей группы.

Каждый элемент массива всё равно становится отдельным callback'ом планировщика. Поэтому `addCallbacks` не создаёт отдельный механизм выполнения коллекции: фактически он последовательно регистрирует элементы через `addCallback` и объединяет disposer'ы.

Порядок регистрации сохраняется.

## Планирование

Планирование — это процесс, который определяет, **какие зарегистрированные callback'и будут выполнены в текущем кадре, а какие продолжат выполнение в следующем**.

AnimationEngine хранит callback'и в порядке регистрации и использует cursor, указывающий на следующий callback, с которого нужно продолжить проход.

На каждом animation frame происходит примерно следующее:

    requestAnimationFrame
            │
            ▼
       начало кадра
            │
            ├── определить deltaTime
            │
            ├── определить начало вычислительного бюджета
            │
            ├── выполнить callback
            │
            ├── перейти к следующему callback
            │
            ├── выполнить callback
            │
            ├── ...
            │
            └── бюджет исчерпан
                    │
                    ▼
             следующий кадр

Планировщик не пытается выполнить «одну большую коллекцию» как неделимую операцию. Каждый callback является отдельным шагом, между которыми AnimationEngine может остановить текущий проход и продолжить его на следующем кадре.

### Порядок выполнения

Если зарегистрированы:

    A
    B
    C

то обычный порядок выполнения будет:

    кадр 1: A → B → C
    кадр 2: A → B → C
    кадр 3: A → B → C
    ...

Если все три callback'а помещаются в бюджет кадра, они выполняются последовательно в одном кадре.

Cursor используется для случая, когда все callback'и не помещаются в один кадр.

### Пять отдельных вызовов `addCallback`

Рассмотрим:

```ts
engine.addCallback(A);
engine.addCallback(B);
engine.addCallback(C);
engine.addCallback(D);
engine.addCallback(E);
```

После регистрации планировщик имеет пять отдельных элементов работы:

| Позиция | Callback | Отдельный элемент планирования |
|---:|---|---|
| 0 | A | да |
| 1 | B | да |
| 2 | C | да |
| 3 | D | да |
| 4 | E | да |

Если disposer каждого вызова сохранить отдельно, каждый callback можно удалить независимо:

```ts
const disposeA = engine.addCallback(A);
const disposeB = engine.addCallback(B);
const disposeC = engine.addCallback(C);
const disposeD = engine.addCallback(D);
const disposeE = engine.addCallback(E);
```

Например, вызов `disposeC()` удалит только C. Остальные callback'и продолжат участвовать в планировании.

### Один вызов `addCallbacks`

Теперь рассмотрим:

```ts
engine.addCallbacks([A, B, C, D, E]);
```

С точки зрения выполнения планировщика результат тот же:

| Позиция | Callback | Отдельный элемент планирования |
|---:|---|---|
| 0 | A | да |
| 1 | B | да |
| 2 | C | да |
| 3 | D | да |
| 4 | E | да |

Поэтому **разницы в порядке и способе выполнения A, B, C, D, E нет**.

Главное различие находится не в планировании, а в управлении временем жизни:

| Способ регистрации | Callback'ов | Disposer'ов | Можно удалить один элемент |
|---|---:|---:|---|
| 5 × `addCallback` | 5 | 5 | да |
| 1 × `addCallbacks([A,B,C,D,E])` | 5 | 1 | нет, через общий disposer |

То есть `addCallbacks` — это удобный способ **сгруппировать регистрацию и удаление**, а не способ заставить AnimationEngine выполнять массив как одну операцию.

### Если все callback'и помещаются в один кадр

Предположим, AnimationEngine получил:

    A → B → C → D → E

и текущего бюджета достаточно для всех пяти callback'ов.

Тогда выполнение выглядит так:

    Кадр 1
    ┌──────────────────────────────────────────────┐
    │ A │ B │ C │ D │ E                            │
    └──────────────────────────────────────────────┘
      начало                         конец бюджета

Все пять callback'ов выполняются последовательно в рамках одного кадра.

После завершения прохода AnimationEngine планирует следующий `requestAnimationFrame`, чтобы продолжить обслуживание зарегистрированных callback'ов.

### Если коллекция не помещается в один кадр

Теперь предположим, что времени кадра хватает только примерно на три callback'а.

Важно: **AnimationEngine не прерывает callback посередине выполнения**.

Если начался callback C, он должен завершиться. Проверка бюджета используется между callback'ами.

Например:

    Кадр 1
    ┌──────────────────────────────────────────────┐
    │ A │ B │ C │
    └───────────────────────┬──────────────────────┘
                            │ бюджет закончился
                            ▼

    Кадр 2
    ┌──────────────────────────────────────────────┐
    │ D │ E │ A │
    └──────────────────────────────────────────────┘

    Кадр 3
    ┌──────────────────────────────────────────────┐
    │ B │ C │ D │
    └──────────────────────────────────────────────┘

Здесь показан принцип продолжения работы, а не фиксированное количество callback'ов на кадр: фактическое число зависит от продолжительности их выполнения и текущего вычислительного бюджета.

После выполнения C cursor уже указывает на D. Поэтому следующий кадр не начинает последовательность снова с A, а продолжает её с D.

### Как работает перенос на следующий кадр

Для последовательности:

    A → B → C → D → E

пусть первый кадр успел выполнить только:

    A → B → C

После C планировщик обнаруживает, что продолжать текущий проход уже не следует.

Состояние логически выглядит так:

    выполнено:
        A B C

    осталось в текущем проходе:
        D E

    следующий callback:
        D

Следующий `requestAnimationFrame` продолжает выполнение с D:

    кадр 2:
        D → E → A → ...

Таким образом, работа не теряется и не начинается каждый раз с первого callback.

### Cursor и циклический порядок

AnimationEngine использует циклический порядок callback'ов.

Для пяти callback'ов:

    A → B → C → D → E

cursor может последовательно указывать:

    A → B → C → D → E → A → B → ...

Если кадр закончился после C:

    кадр 1: A → B → C
                    │
                    ▼
                  cursor
                    │
                    ▼
                    D

то следующий кадр начинается с D:

    кадр 2: D → E → A → B → ...

Это позволяет распределять работу между кадрами без постоянного возврата к началу списка.

### Один callback — одна неделимая единица планирования

AnimationEngine может перенести **следующий callback** на другой кадр, но не может остановить текущий callback в середине.

Например:

```ts
engine.addCallbacks([
    A,
    B,
    C,
]);
```

Если C внутри себя выполняет долгую синхронную операцию:

```ts
const C = () => {
    // очень долгая синхронная работа
};
```

AnimationEngine не сможет сделать:

    C ──┬── половина C → следующий кадр
        └── вторая половина C

Для планировщика C — одна неделимая операция:

    A → B → C
             │
             └── C должен завершиться целиком

Если C необходимо распределить между кадрами, сама задача должна быть разделена вызывающей стороной:

    C1 → C2 → C3 → C4

Тогда AnimationEngine сможет планировать:

    кадр 1: A → B → C1
    кадр 2: C2 → C3 → D
    кадр 3: C4 → E → A
    ...

### Ограничение одного прохода

В одном кадре AnimationEngine не должен бесконечно выполнять один и тот же callback.

Поэтому для текущего кадра фиксируется количество зарегистрированных callback'ов в начале прохода.

Если зарегистрировано пять callback'ов:

    A → B → C → D → E

то один проход кадра рассматривает максимум эти пять позиций.

Это позволяет избежать ситуации, когда один callback постоянно выполняется снова и не оставляет времени остальным зарегистрированным работам.

### Использование времени кадра

У кадра есть вычислительный бюджет. AnimationEngine автоматически оценивает длительность кадров и использует часть этого времени для выполнения callback'ов.

Упрощённо:

    начало кадра
          │
          ▼
    ┌───────────────────────────────────────┐
    │       доступный бюджет кадра           │
    │                                       │
    │ A │ B │ C │ D │ ...                   │
    │             │                         │
    │             └── бюджет закончился     │
    └───────────────────────────────────────┘
                          │
                          ▼
                    следующий кадр

При этом проверка бюджета происходит **между callback'ами**, а не во время выполнения callback.

Поэтому AnimationEngine гарантирует не то, что каждый кадр будет занимать ровно заданное количество миллисекунд, а то, что он старается не начинать следующую работу после исчерпания доступного бюджета.

### Продолжение длинной последовательности

Рассмотрим десять шагов:

    A → B → C → D → E → F → G → H → I → J

Если в каждом кадре успевает выполняться только часть последовательности, она распределяется по нескольким кадрам:

| Кадр | Выполненные шаги | Следующий шаг |
|---:|---|---|
| 1 | A → B → C | D |
| 2 | D → E → F | G |
| 3 | G → H → I | J |
| 4 | J | следующий проход начинается с A |

Количество шагов в таблице является только примером. В реальной работе оно определяется фактическим временем выполнения callback'ов и измеренным бюджетом кадра.

### Что происходит при удалении callback'а

Callback может быть удалён между кадрами или во время выполнения другого callback.

Например, было:

    A → B → C → D → E

и C удаляет D.

После удаления очередь становится:

    A → B → C → E

AnimationEngine корректирует cursor, чтобы продолжить работу с существующим элементом очереди.

Поэтому удалённый callback не будет выполнен в следующем проходе.

### Конкуренция нескольких регистраций

Важно рассмотреть не только два способа регистрации одной последовательности, но и ситуацию, когда **несколько потребителей одновременно добавляют работу**.

AnimationEngine не создаёт отдельную очередь для каждого вызова `addCallback` или `addCallbacks`. Все callback'и попадают в **один общий порядок выполнения**.

Поэтому эти варианты:

```ts
engine.addCallback(A);
engine.addCallback(B);
engine.addCallback(C);
engine.addCallback(D);
engine.addCallback(E);
```

и:

```ts
engine.addCallbacks([A, B, C, D, E]);
```

дают один и тот же порядок:

    A → B → C → D → E

Разница только в disposer'ах.

#### Два потребителя: один callback против группы

Предположим, есть два потребителя:

- потребитель X регистрирует пять отдельных callback'ов: `A1 ... A5`;
- потребитель Y регистрирует одну группу из трёх callback'ов: `B1 ... B3`.

Регистрация:

```ts
engine.addCallback(A1);
engine.addCallback(A2);
engine.addCallback(A3);
engine.addCallback(A4);
engine.addCallback(A5);

engine.addCallbacks([B1, B2, B3]);
```

Общая очередь AnimationEngine:

    A1 → A2 → A3 → A4 → A5 → B1 → B2 → B3

Здесь **нет понятия «потребитель X получает пять слотов, а потребитель Y один слот»**. Каждый зарегистрированный callback — самостоятельный элемент общей очереди.

Если все восемь callback'ов помещаются в кадр:

| Порядок | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Кадр 1 | A1 | A2 | A3 | A4 | A5 | B1 | B2 | B3 |

На следующем кадре очередь снова проходит циклически:

| Порядок | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Кадр 2 | A1 | A2 | A3 | A4 | A5 | B1 | B2 | B3 |

#### Если времени кадра хватает только на часть общей очереди

Предположим, восемь callback'ов не помещаются в один кадр, а текущий бюджет позволяет выполнить только три.

Тогда первый кадр:

    Кадр 1

    A1 → A2 → A3
              │
              └── бюджет закончился

Cursor уже находится на A4.

Следующий кадр продолжает **общую очередь**, а не начинает заново группу B:

    Кадр 2

    A4 → A5 → B1
              │
              └── бюджет закончился

Следующий:

    Кадр 3

    B2 → B3 → A1
              │
              └── бюджет закончился

И далее:

    Кадр 4

    A2 → A3 → A4
              │
              └── ...

Таким образом, группа из трёх `B` и пять отдельных `A` **не конкурируют как две группы**. Конкурируют восемь отдельных callback'ов.

Схематично:

    Потребитель X
        A1 ─┐
        A2  │
        A3  │
        A4  ├──→ общий scheduler AnimationEngine
        A5  │
            │
    Потребитель Y
        B1  │
        B2  │
        B3 ─┘

После регистрации AnimationEngine видит:

    [A1][A2][A3][A4][A5][B1][B2][B3]

#### Два вызова `addCallbacks`

Теперь рассмотрим более симметричный случай:

```ts
engine.addCallbacks([A1, A2, A3]);
engine.addCallbacks([B1, B2, B3, B4, B5]);
```

Получается одна общая очередь:

    A1 → A2 → A3 → B1 → B2 → B3 → B4 → B5

Для планировщика нет различия между границами групп:

    [ A1 A2 A3 ] [ B1 B2 B3 B4 B5 ]
          │               │
          └──── одна общая очередь ────┘

Если в кадр помещается только четыре callback'а:

| Кадр | Выполненные callback'и | Следующий |
|---:|---|---|
| 1 | A1 → A2 → A3 → B1 | B2 |
| 2 | B2 → B3 → B4 → B5 | A1 |
| 3 | A1 → A2 → A3 → B1 | B2 |

Обратите внимание: **вторая группа не ждёт завершения первой как атомарной группы**. Она начинает выполняться сразу после своего первого элемента в общем порядке.

#### Если регистрации чередуются

Порядок определяется не размером групп, а **моментом регистрации**.

Например:

```ts
engine.addCallback(A1);
engine.addCallbacks([B1, B2, B3]);
engine.addCallback(A2);
engine.addCallbacks([C1, C2]);
```

Общая очередь будет:

    A1 → B1 → B2 → B3 → A2 → C1 → C2

А не:

    A1 → A2 → B1 → B2 → B3 → C1 → C2

и не:

    [A] → [B1,B2,B3] → [C1,C2]

То есть `addCallbacks` сохраняет порядок элементов **в момент их добавления в общий scheduler**.

#### Что на самом деле означает «конкуренция»

В AnimationEngine нет приоритетов между регистрациями.

Если есть:

    A1 A2 A3 A4 A5
    B1 B2 B3

то планировщик не знает, что первые пять принадлежат одному потребителю, а следующие три — другому.

Для него существует только:

    A1 → A2 → A3 → A4 → A5 → B1 → B2 → B3

Каждый callback получает возможность выполниться, когда cursor доходит до него.

Поэтому:

- `addCallback(A)` добавляет **один элемент** общей очереди;
- `addCallbacks([A,B,C])` добавляет **три элемента** общей очереди;
- размер группы не является приоритетом;
- группа не является атомарной;
- один длинный callback не может быть прерван AnimationEngine;
- если текущего бюджета недостаточно, оставшиеся callback'и продолжаются с cursor в следующем кадре.

Именно поэтому `addCallbacks` следует понимать как **удобный способ массовой регистрации и последующего массового удаления**, а не как отдельную очередь или отдельную задачу планировщика.

### Остановка

Удаление последнего callback останавливает дальнейшее планирование `requestAnimationFrame`.

`clear()` удаляет все callback'и, сбрасывает cursor и останавливает engine.

## Автоматическая оценка времени кадра

AnimationEngine не получает фиксированный `frameBudgetMs`.

Перед началом работы он измеряет реальные интервалы между кадрами и определяет доступный вычислительный бюджет.

Детали калибровки являются внутренней реализацией. Важно, что бюджет:

- определяется автоматически;
- зависит от фактической частоты кадров;
- используется при выборе количества работы текущего кадра.

## deltaTime

Каждый callback получает `deltaTime` — время между текущим и предыдущим animation frame.

Первый кадр после запуска не имеет предыдущего timestamp, поэтому `deltaTime` равен `0`.

## Текущие пользователи

| Пользователь | Назначение |
|---|---|
| `ModelManager` | Выполнение собственной фоновой работы порциями |
| `LevenshteinManager` | Постепенное выполнение вычислений Levenshtein |
| `EnginePipeline` | Регистрация группы callback'ов для physics algorithms |

AnimationEngine не зависит от предметного смысла этих задач.

## Дальнейшее развитие

### Generator

Generator может стать источником последовательных шагов, выдавая следующий callback по мере необходимости.

    Generator
        │
        ├── callback #1
        ├── callback #2
        ├── callback #3
        └── callback #4
                │
                ▼
        AnimationEngine

#### Что представляет Generator

Generator представляет последовательный источник работы. В отличие от `addCallbacks`, он может формировать следующие шаги динамически.

#### Как выдаются следующие шаги

Следующий callback выдаётся после обработки предыдущего шага, когда планировщик готов продолжить последовательность.

#### Как AnimationEngine решает, когда получить следующий шаг

AnimationEngine остаётся владельцем времени. Он определяет, когда текущего бюджета достаточно для продолжения последовательности.

    Generator
        │
        │ следующий шаг
        ▼
    AnimationEngine
        │
        ├── есть бюджет → выполнить
        └── бюджета нет → продолжить в следующем кадре

#### Пример последовательности

    загрузить часть данных
          ↓
    построить часть индекса
          ↓
    обработать следующую часть
          ↓
    обновить результат
          ↓
    завершить

AnimationEngine не знает назначения этих шагов. Он планирует только время их выполнения.
