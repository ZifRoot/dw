# AnimationEngine

## Основные идеи

AnimationEngine — инфраструктурный планировщик покадровой работы клиентского приложения.

1. **Единый владелец `requestAnimationFrame`.** Только AnimationEngine управляет animation loop.
2. **Максимальное использование времени кадра.** Планировщик старается выполнить максимум зарегистрированной работы в доступном времени текущего кадра.
3. **Перенос невыполненной работы на следующие кадры.** Не помещающаяся работа продолжается в следующих кадрах.
4. **AnimationEngine не знает смысла работы.** Callback для него — абстрактная функция.
5. **Работа представляется последовательностью шагов.** Большая задача должна быть разделена вызывающей стороной на отдельные callback-операции.
6. **Последовательность может предоставляться callback'ом, группой callback'ов, Generator или фабрикой Generator.** Все эти варианты являются источниками одной и той же группы и подчиняются общим правилам планирования.

AnimationEngine отвечает за **время выполнения и планирование**, а смысл работы остаётся у потребителя.

## Единый requestAnimationFrame

### Почему несколько RAF создают проблему

Разные подсистемы могут самостоятельно создавать циклы `requestAnimationFrame`. Они конкурируют за одно и то же время кадра, не имеют общего бюджета и усложняют согласованное планирование и остановку.

### Почему нужен единый планировщик

AnimationEngine — единственная точка доступа подсистем к animation loop:

    ModelManager ───────┐
    LevenshteinManager ─┼──→ AnimationEngine ──→ requestAnimationFrame
    EnginePipeline ─────┘

Потребители регистрируют работу, а AnimationEngine решает, когда её выполнять.

## Представление работы

### `addCallback`

`addCallback(callback)` добавляет параллельную группу, состоящую из одного callback'а, и возвращает disposer этой группы.

### `addCallbacks`

`addCallbacks(callbacks)` добавляет параллельную группу из нескольких callback'ов и возвращает один disposer для всей группы.

Группа представляет собой **последовательность отдельных callback-операций**. Источник этой последовательности может быть массивом callback'ов, Generator или функцией, создающей Generator. Порядок элементов внутри одной группы сохраняется: если зарегистрировано `[A, B, C]`, то эта группа проходит позиции в порядке:

    A → B → C

Но группа **не является атомарной**. Между двумя callback'ами одной группы AnimationEngine может выполнить callback другой группы. Поэтому контракт не требует `A → B → C` как непрерывного участка одного кадра или одного прохода без вмешательства других групп.

Для разных групп планировщик выбирает **группу как единицу конкуренции**. Сначала обслуживаются группы, которые ещё ни разу не запускались, в порядке регистрации. После первого выполнения группы конкурируют по времени последнего завершения callback. Поэтому одна длинная группа не получает приоритет только из-за более раннего старта.

Таким образом, `addCallback(A)` является частным случаем `addCallbacks([A])`.

## Планирование

Планирование — это процесс, который определяет, **какие зарегистрированные callback'и будут выполнены в текущем кадре, а какие продолжат выполнение в следующем**.

AnimationEngine хранит состояние нескольких параллельных групп и использует Sequence для получения следующего callback.

На каждом animation frame происходит примерно следующее:

    requestAnimationFrame
            │
            ▼
       начало кадра
            │
            ├── определить начало вычислительного бюджета
            │
            ├── выбрать следующую группу
            │
            ├── выполнить следующий callback этой группы
            │
            ├── проверить бюджет
            │
            ├── выбрать следующую работу
            │
            └── бюджет исчерпан
                    │
                    ▼
             следующий кадр

Планировщик не пытается выполнить «одну большую коллекцию» как неделимую операцию. Ни массив callback'ов, ни Generator, ни функция, создающая Generator, не являются атомарной единицей планирования. Каждый callback, полученный из любого из этих источников, является отдельным шагом. Между двумя такими шагами AnimationEngine может выполнить работу другой группы или остановить текущий проход и продолжить его на следующем кадре.

### Порядок выполнения внутри группы

Если зарегистрирована группа:

    A → B → C

то cursor определяет следующий callback этой группы:

    A → B → C → A → B → C → ...

При этом сама группа не получает эксклюзивный участок времени. Между A и B может быть выполнен callback другой группы.

### Параллельные группы

Рассмотрим три независимые последовательности:

    Group A: A1 → A2 → A3
    Group B: B1 → B2
    Group C: C1

Глобальная конкуренция происходит **между группами**, а не между отдельными callback'ами:

    Group A
    Group B
    Group C

Если AnimationEngine выбирает Group A, она выполняет только следующий callback своей последовательности — например, A1. После этого cursor Group A перемещается на A2, а timestamp последнего завершения группы обновляется после выполнения callback.

Поэтому возможна последовательность:

    A1 → B1 → C1 → A2 → B2 → A3 → ...

При этом порядок внутри каждой группы никогда не нарушается.

### `addCallback` как группа из одного элемента

Вызов:

```ts
engine.addCallback(A);
```

семантически соответствует:

```ts
engine.addCallbacks([A]);
```

В обоих случаях создаётся группа с одной последовательной позицией:

    Group: A

### Несколько `addCallbacks`

Например:

```ts
engine.addCallbacks([A1, B1, C1]);
engine.addCallbacks([A2, B2, C2]);
```

создаёт:

    Group 1: A1 → B1 → C1
    Group 2: A2 → B2 → C2

Это не означает выполнение первой группы целиком перед второй. Планировщик выбирает группы независимо, сохраняя последовательность callback'ов внутри каждой группы.

### Граница одного прохода

Один вызов планировщика (`step()`) не должен бесконечно повторять одну и ту же группу только потому, что в ней закончилась последовательность.

Если группа:

    A → B

и в текущем кадре успели выполниться оба callback'а:

    A → B

то достижение B означает завершение доступной на этот момент последовательности этой группы. Это не даёт группе специального права немедленно начать новый проход: следующий callback выбирается по тем же общим правилам планирования, что и любой другой callback.

Даже если после B в кадре осталось время, AnimationEngine не должен немедленно начинать новый проход:

    A → B → A → ...

Следующий проход этой группы может начаться только согласно политике планирования следующей работы.

### Пример с переносом между кадрами

Пусть группа `A → B`, а A оказался настолько долгим, что B не поместился в оставшийся бюджет. Это правило одинаково для любого источника группы: массива callback'ов, Generator или фабрики Generator. Сам факт получения callback'а из Generator не делает всю последовательность одной неделимой операцией.

Тогда возможно:

    кадр 1: A
    кадр 2: B
    кадр 3: A
    кадр 4: B
    ...

Если B в кадре 2 выполняется быстро, AnimationEngine не должен из-за этого нарушать общие правила планирования и немедленно выполнять следующий A только потому, что в текущем кадре осталось время.

### Ограничение одного прохода и новые callback'и

В начале `step()` фиксируется набор позиций, который участвует в текущем проходе. Callback, добавленный во время выполнения текущего callback, не должен автоматически получать дополнительный слот в том же проходе.

Например:

    начало:
        A → B → C

    A добавляет D

    текущий проход:
        A → B → C

    следующий проход:
        A → B → C → D

Новый callback не должен изменять уже начатый проход задним числом.

### Удаление callback'ов

Callback может удалить себя или другой callback во время выполнения.

Например, если:

    A → B → C → D

и C удаляет D, то D больше не должен выполняться.

Если B удаляет самого себя:

    A → B → C

то оставшаяся последовательность продолжается без B:

    A → C

AnimationEngine корректирует внутреннее состояние планирования так, чтобы удалённый callback не был повторно выбран cursor.

### Один callback — одна неделимая единица планирования

AnimationEngine может перенести **следующий callback** на другой кадр, но не может остановить текущий callback в середине.

Например:

```ts
engine.addCallbacks([A, B, C]);
```

Если C внутри себя выполняет долгую синхронную операцию, AnimationEngine не сможет разделить C между кадрами.

Для планировщика C — одна неделимая операция:

    A → B → C
             │
             └── C должен завершиться целиком

Если C необходимо распределить между кадрами, сама задача должна быть разделена вызывающей стороной:

    C1 → C2 → C3 → C4

### Использование времени кадра

У кадра есть вычислительный бюджет. AnimationEngine автоматически оценивает длительность кадров и использует часть этого времени для выполнения callback'ов.

При этом проверка бюджета происходит **между callback'ами**, а не во время выполнения callback.

Поэтому бюджет следует понимать как **разрешённое время на запуск следующей работы**. AnimationEngine старается не начинать следующий callback после исчерпания бюджета текущего кадра.

Если один callback сам по себе занимает больше доступного бюджета, он всё равно выполняется целиком. Планировщик не может прервать синхронный JavaScript-код. Бюджет ограничивает начало **следующего** callback, а не длительность уже начатого.

### Безопасный запуск callback

Ошибка одного callback не должна останавливать общий планировщик. AnimationEngine выполняет каждый callback через защитную оболочку `safe`: исключение перехватывается и записывается через `console.error`, после чего планировщик продолжает работу со следующей доступной позицией.

Это не означает, что ошибка исправлена или что состояние предметной подсистемы после исключения корректно. `safe` защищает именно жизненный цикл AnimationEngine.

### deltaTime

deltaTime является свойством **группы**, а не animation frame.

Для последовательности:

    A1 → A2 → A3

если:

    A1 завершился в t1
    A2 запускается в t2

то:

    A2 получает deltaTime = t2 - t1

Первый запуск группы получает deltaTime = 0.

| `LevenshteinManager` | Постепенное выполнение вычислений Levenshtein |

AnimationEngine не зависит от предметного смысла этих задач.

## Модель планирования

Глобальная единица конкуренции — **группа**, а не отдельный callback.

Группа содержит Sequence и участвует в общем планировании. AnimationEngine выбирает одну группу и выполняет только один следующий callback этой группы. После завершения callback группа снова становится доступной для планирования.

### Приоритет групп

Группа, которая ещё ни разу не выполнялась, получает первый запуск в порядке регистрации.

После первого завершённого callback группа получает время последнего завершения. При последующем выборе приоритет получает группа, которая дольше других ждёт после своего последнего завершения.

Это позволяет распределять работу между независимыми группами и не отдавать приоритет группе только потому, что она была зарегистрирована раньше.

### Бюджет

Бюджет кадра проверяется между callback'ами.

Если следующий callback является первой работой кадра, он запускается даже при уже исчерпанном бюджете: синхронный callback нельзя прервать.

После завершения callback AnimationEngine проверяет бюджет перед запуском следующей работы.

Следовательно, frameBudgetMs — это разрешённое время на запуск **следующей** работы, а не жёсткий лимит длительности callback.

### Изменения во время step

Группа, добавленная во время выполнения текущего step(), не получает возможность выполнить callback в уже начатом шаге планировщика.

Удаление группы прекращает её дальнейшее участие в планировании. Если callback удаляет себя или другой callback из ArraySequence, удалённый callback не должен быть выбран снова.

### Безопасность callback

Каждый callback выполняется через безопасную оболочку. Исключение перехватывается и передаётся в console.error, после чего AnimationEngine продолжает планирование доступной работы.

Безопасная оболочка защищает жизненный цикл AnimationEngine, но не отменяет изменения состояния, которые callback успел выполнить до исключения.

## Generator API

Generator не является отдельным планировщиком. Это источник следующего callback для уже существующей группы.

Публичный API:

~~~ts
export type AnimationGenerator = Iterator<AnimationCallback>;
export type AnimationGeneratorFactory = () => AnimationGenerator;

addGenerator(generator: AnimationGenerator): () => void;
addGeneratorFactory(factory: AnimationGeneratorFactory): () => void;
~~~

### `addGenerator`

`addGenerator(generator)` регистрирует уже созданный Generator как группу.

Например:

~~~ts
engine.addGenerator((function* () {
    yield stepA;
    yield stepB;
    yield stepC;
})());
~~~

Каждый `yield` является отдельным callback. Generator может быть конечным или бесконечным.

Для конечного Generator:

~~~
A → B → C → done
~~~

после `done` группа больше не может быть перезапущена и удаляется.

### `addGeneratorFactory`

`addGeneratorFactory(factory)` регистрирует группу, которая получает новый Generator после завершения предыдущего.

Фабрика не вызывается при каждом выборе группы. Пока текущий Generator не завершился, AnimationEngine продолжает использовать именно его.

После завершения одного Generator следующий запуск создаёт новый Generator:

~~~
Generator #1 → done
       ↓
следующий запуск
       ↓
Generator #2 → A1 → B1 → ...
~~~

Новый Generator не начинает выполняться в том же запуске последовательности, в котором предыдущий достиг `done`.

Если фабрика или `generator.next()` выбрасывает исключение, ошибка перехватывается через тот же безопасный механизм.

### `addCallbacks` и Sequence

`addCallbacks([A, B, C])` создаёт последовательность:

~~~
A → B → C
~~~

После завершения последовательности повторяемый источник может начать следующий запуск согласно общим правилам планирования.

`addCallback(A)` является частным случаем `addCallbacks([A])`.

`removeCallback()` работает с группами, созданными через `addCallback()` / `addCallbacks()`. Для Generator-групп используется disposer, возвращаемый `addGenerator()` или `addGeneratorFactory()`.

### Общие правила для источников

Независимо от источника действует одна и та же схема:

~~~
выбрать группу
    ↓
получить один callback из Sequence
    ↓
выполнить callback
    ↓
зафиксировать завершение callback
    ↓
продолжить планирование
~~~

Поэтому:

- массив callback'ов не является атомарной операцией;
- Generator не является атомарной операцией;
- функция, создающая Generator, не является атомарной операцией;
- отдельный callback является минимальной неделимой единицей синхронного выполнения;
- между двумя callback'ами одной группы может быть выбран другой источник;
- бюджет кадра проверяется между callback'ами;
- callback, который уже начал выполняться, выполняется целиком.

### `deltaTime`

`deltaTime` является свойством группы, независимо от источника callback'а.

Для:

~~~
A1 → A2 → A3
~~~

если:

~~~
A1 завершился в t1
A2 запускается в t2
~~~

то:

~~~
deltaTime(A2) = t2 - t1
~~~

Первый callback группы получает:

~~~
deltaTime = 0
~~~

Для асинхронного callback моментом завершения считается разрешение его Promise.

## Модель Sequence

Источники последовательностей унифицированы через специальную абстракцию Sequence.

### Единая абстракция последовательности

AnimationEngine не должен знать, является ли источник массивом callback'ов, одним callback'ом, Generator или функцией, создающей Generator.

Текущий контракт:

~~~ts
interface Sequence<T> extends Iterator<T> {
  reset(): boolean;
}
~~~

Sequence расширяет стандартный JavaScript Iterator операцией reset().

- next() предоставляет следующий элемент текущего запуска.
- reset() возвращает true, если возможен следующий запуск.
- reset() возвращает false, если последовательность больше запускаться не может.

Таким образом, AnimationEngine работает только с жизненным циклом Sequence и не зависит от конкретного способа её создания.

### Четыре формы последовательности

Публично последовательность может задаваться четырьмя способами:

1. **Один callback.**
2. **Массив callback'ов.**
3. **Уже созданный Generator.**
4. **Функция-генератор (Generator Factory).**

Один callback концептуально является последовательностью из одного элемента:

~~~
[A]
~~~

Массив:

~~~
[A, B, C]
~~~

Generator предоставляет уже созданную последовательность:

~~~
A → B → C → END
~~~

Функция-генератор является источником новых последовательностей:

~~~
factory()
    ↓
Sequence #1 → END
    ↓
factory()
    ↓
Sequence #2 → END
    ↓
...
~~~

### One-shot как политика запуска

Для callback, массива и функции-генератора по умолчанию предполагается повторяемая последовательность.

oneShot не является отдельным типом последовательности. Это дополнительная политика, запрещающая следующий запуск:

~~~
sequence → END
             ↓
          oneShot
             ↓
        reset() === false
~~~

Для повторяемой последовательности:

~~~
sequence → END
             ↓
          reset()
             ↓
        reset() === true
~~~

reset() определяет только возможность следующего запуска. Новый запуск не должен начинаться немедленно в том же кадре.

### Пустая последовательность и внутреннее состояние реализации

Публичный контракт Sequence не содержит метода `isEmpty()` и не должен раскрывать внутреннее состояние конкретной реализации.

Например, ArraySequence может удалить callback через внутреннюю операцию `remove()`. Если после удаления массив callback'ов пуст, это не передаётся AnimationEngine отдельным признаком. При следующем завершении текущего прохода `reset()` возвращает `false`:

~~~
ArraySequence
    ↓
callbacks = []
    ↓
reset() === false
    ↓
AnimationEngine удаляет Group
~~~

Таким образом, `reset() === false` является единым протоколом окончания жизненного цикла последовательности. AnimationEngine не знает, почему следующий запуск невозможен: последовательность могла быть one-shot, могла быть уже созданным Generator, либо конкретная реализация могла стать пустой.

Это принципиально отличается от проверки вида `sequence.isEmpty()`: такая проверка вынуждала бы владельца знать внутреннее состояние конкретной реализации Sequence и расширяла бы общий интерфейс деталями ArraySequence.

Внутреннее состояние реализации остаётся внутренним. Sequence сообщает AnimationEngine только результат своего протокола `next() → done` и `reset() → true/false`.

### Generator как естественный one-shot источник

Уже созданный Generator отличается тем, что его нельзя запустить заново:

~~~
Generator
    ↓
A → B → C → END
    ↓
reset() === false
~~~

Это не отдельный флаг oneShot, а естественное свойство уже созданного Generator.

Функция-генератор, напротив, может создавать новый Generator:

~~~
GeneratorFactory
    ↓
Generator #1 → END
    ↓
reset() === true
    ↓
Generator #2 → END
~~~

Поэтому GeneratorSequence и GeneratorFactorySequence имеют разную семантику reset().

### Реализации Sequence

Реализация использует специализированные типы Sequence:

~~~
Sequence
├── ArraySequence
├── GeneratorSequence
└── GeneratorFactorySequence
~~~

Один callback может быть представлен как ArraySequence с одним элементом.

ArraySequence поддерживает обычный повторный запуск и режим oneShot. В режиме oneShot после END её reset() возвращает false.

GeneratorSequence оборачивает уже созданный Generator и после END возвращает false из reset().

GeneratorFactorySequence хранит функцию, создающую новый Generator. После END текущего Generator reset() разрешает следующий запуск, но сам новый Generator не должен начинать выполняться в том же animation frame.

### Конец последовательности как граница запуска

END — это не только технический результат Iterator.next():

~~~ts
{ done: true, value: undefined }
~~~

Для AnimationEngine END означает завершение **текущего запуска последовательности**.

Это важное отличие:

~~~
callback completed
    ≠
sequence completed
~~~

После выполнения callback группа может снова участвовать в планировании текущего кадра.

После END текущий запуск группы завершён. Даже если в кадре осталось вычислительное время, новый запуск этой же последовательности в том же кадре запрещён.

### Граница последовательности и бюджет кадра

Основная задача AnimationEngine — выполнить в текущем кадре как можно больше callback'ов, пока это позволяет вычислительный бюджет.

Группы конкурируют между собой. Если одна группа достигает END, она больше не выбирается в текущем кадре. Оставшийся бюджет используется для других групп.

Например:

~~~
Group A: A1 → A2 → END
Group B: B1 → B2 → B3 → ...
Group C: C1 → C2 → ...
~~~

После:

~~~
A1 → A2 → END
             │
             └── Group A больше не запускается
                 в текущем frame
~~~

планировщик продолжает обслуживать Group B и Group C.

Если последовательность повторяемая, её следующий запуск возможен только в следующем animation frame:

~~~
Frame N:
    A1 → A2 → END

Frame N+1:
    A1 → A2 → END

Frame N+2:
    A1 → A2 → END
~~~

Для oneShot после END группа удаляется.

Это правило не позволяет одной повторяемой последовательности бесконечно захватывать оставшийся бюджет одного кадра.

### Ответственность AnimationEngine

AnimationEngine работает только с:

~~~
Group
  ↓
Sequence
  ├── next()
  └── reset()
~~~

AnimationEngine не должен содержать ветвления по конкретному типу источника.

Различия между массивом, Generator и Generator Factory должны быть инкапсулированы в соответствующих реализациях Sequence.


## Асинхронные callback'и

`AnimationCallback` может завершаться синхронно или асинхронно:

~~~ts
export type AnimationCallback =
  (deltaTime: number) => void | Promise<void>;
~~~

В одной группе могут находиться любые комбинации синхронных и асинхронных callback'ов. Более того, один и тот же callback может в одном запуске вернуть `void`, а в другом — `Promise<void>`.

AnimationEngine определяет способ завершения по результату конкретного вызова callback. Для определения асинхронного выполнения используется только:

~~~ts
result instanceof Promise
~~~

Произвольные Promise-like/thenable объекты не являются частью контракта AnimationEngine.

Если callback возвращает Promise, группа переходит в состояние ожидания. Следующий callback этой группы не запускается до завершения Promise. При этом другие группы продолжают конкурировать за вычислительный бюджет:

~~~text
Group A: A1 → waiting ─────────→ A2
                    ↘
Group B:             B1 → B2 → B3
~~~

Ожидание Promise не удерживает `requestAnimationFrame` и не блокирует независимые группы. Если все группы находятся в ожидании, новый animation frame не запрашивается. После завершения Promise соответствующая группа снова становится доступной для планирования.

`lastCompletedAt` для асинхронного callback обновляется после завершения Promise, а не после его запуска. Поэтому `deltaTime` следующего callback группы измеряется от фактического завершения предыдущего callback.

Группа не может выполнять два callback'а одновременно. Пока её callback ожидает Promise, она отсутствует в очереди готовых групп.

Если Promise отклонён, AnimationEngine перехватывает ошибку и удаляет соответствующую группу. Это предотвращает необработанное отклонение и не оставляет неисправную последовательность в планировщике.

Остановка или удаление группы во время ожидания не приводит к её повторной регистрации после завершения Promise. Если AnimationEngine остановлен, завершившийся callback не запускается автоматически; после последующего запуска готовые группы снова ставятся в очередь.

Для `EnginePipeline` это означает, что последовательность алгоритмов остаётся последовательностью callback'ов:

~~~text
Algorithm #1 → await → Algorithm #2 → await → Algorithm #3
~~~

AnimationEngine отвечает только за ожидание завершения конкретного callback и планирование следующей работы. Смысл последовательности и порядок physics остаются ответственностью `EnginePipeline`.
