# AnimationEngine

## Основные идеи

AnimationEngine — инфраструктурный планировщик покадровой работы клиентского приложения.

1. **Единый владелец `requestAnimationFrame`.** Только AnimationEngine управляет animation loop.
2. **Максимальное использование времени кадра.** Планировщик старается выполнить максимум зарегистрированной работы в доступном времени текущего кадра.
3. **Перенос невыполненной работы на следующие кадры.** Не помещающаяся работа продолжается в следующих кадрах.
4. **AnimationEngine не знает смысла работы.** Callback для него — абстрактная функция.
5. **Работа представляется последовательностью шагов.** Большая задача должна быть разделена вызывающей стороной на отдельные callback-операции.
6. **Последовательность может предоставляться callback'ом или группой callback'ов.** Текущий API предоставляет `addCallback` и `addCallbacks`.

AnimationEngine отвечает за **время выполнения и планирование**, а смысл работы остаётся у потребителя.

## Единый requestAnimationFrame

### Почему несколько RAF создают проблему

Разные подсистемы могут самостоятельно создавать циклы `requestAnimationFrame`. Они конкурируют за одно и то же время кадра, не имеют общего бюджета и усложняют согласованное планирование и остановку.

### Почему нужен единый планировщик

AnimationEngine — единственная точка доступа подсистем к animation loop:

    ModelManager ───────┐
    LevenshteinManager ─┼──→ AnimationEngine ──→ requestAnimationFrame
    EnginePipeline ─────┘

Потребители регистрируют работу, а AnimationEngine решает, когда её выполнять.

## Представление работы

### `addCallback`

`addCallback(callback)` добавляет параллельную группу, состоящую из одного callback'а, и возвращает disposer этой группы.

### `addCallbacks`

`addCallbacks(callbacks)` добавляет параллельную группу из нескольких callback'ов и возвращает один disposer для всей группы.

Группа представляет собой **последовательность callback-позиций**. Порядок callback'ов внутри одной группы сохраняется: если зарегистрировано `[A, B, C]`, то эта группа проходит позиции в порядке:

    A → B → C

Но группа **не является атомарной**. Между двумя callback'ами одной группы AnimationEngine может выполнить callback другой группы. Поэтому контракт не требует `A → B → C` как непрерывного участка одного кадра или одного прохода без вмешательства других групп.

Для разных групп текущая реализация использует cooperative round-robin: за один раунд она старается выполнить по одной следующей позиции каждой существующей группы. Если времени кадра недостаточно, оставшиеся позиции переносятся на следующий кадр. Это обеспечивает продвижение независимых групп и не позволяет одной длинной группе полностью вытеснить остальные.

Таким образом, `addCallback(A)` является частным случаем `addCallbacks([A])`.

## Планирование

Планирование — это процесс, который определяет, **какие зарегистрированные callback'и будут выполнены в текущем кадре, а какие продолжат выполнение в следующем**.

AnimationEngine хранит состояние нескольких параллельных групп и использует cursor для продолжения каждой последовательности с нужного callback.

На каждом animation frame происходит примерно следующее:

    requestAnimationFrame
            │
            ▼
       начало кадра
            │
            ├── определить начало вычислительного бюджета
            │
            ├── выбрать следующую группу
            │
            ├── выполнить следующий callback этой группы
            │
            ├── проверить бюджет
            │
            ├── выбрать следующую работу
            │
            └── бюджет исчерпан
                    │
                    ▼
             следующий кадр

Планировщик не пытается выполнить «одну большую коллекцию» как неделимую операцию. Каждый callback является отдельным шагом, между которыми AnimationEngine может остановить текущий проход и продолжить его на следующем кадре.

### Порядок выполнения внутри группы

Если зарегистрирована группа:

    A → B → C

то cursor определяет следующий callback этой группы:

    A → B → C → A → B → C → ...

При этом сама группа не получает эксклюзивный участок времени. Между A и B может быть выполнен callback другой группы.

### Параллельные группы

Рассмотрим три независимые последовательности:

    Group A: A1 → A2 → A3
    Group B: B1 → B2
    Group C: C1

Глобальная конкуренция происходит **между группами**, а не между отдельными callback'ами:

    Group A
    Group B
    Group C

Если AnimationEngine выбирает Group A, она выполняет только следующий callback своей последовательности — например, A1. После этого cursor Group A перемещается на A2, а состояние последнего запуска группы обновляется.

Поэтому возможна последовательность:

    A1 → B1 → C1 → A2 → B2 → A3 → ...

При этом порядок внутри каждой группы никогда не нарушается.

### `addCallback` как группа из одного элемента

Вызов:

```ts
engine.addCallback(A);
```

семантически соответствует:

```ts
engine.addCallbacks([A]);
```

В обоих случаях создаётся группа с одной последовательной позицией:

    Group: A

### Несколько `addCallbacks`

Например:

```ts
engine.addCallbacks([A1, B1, C1]);
engine.addCallbacks([A2, B2, C2]);
```

создаёт:

    Group 1: A1 → B1 → C1
    Group 2: A2 → B2 → C2

Это не означает выполнение первой группы целиком перед второй. Планировщик выбирает группы независимо, сохраняя последовательность callback'ов внутри каждой группы.

### Граница одного прохода

Один вызов планировщика (`step()`) не должен бесконечно повторять одну и ту же группу только потому, что в ней закончилась последовательность.

Если группа:

    A → B

и в текущем кадре успели выполниться оба callback'а:

    A → B

то достижение B означает завершение текущего прохода этой группы.

Даже если после B в кадре осталось время, AnimationEngine не должен немедленно начинать новый проход:

    A → B → A → ...

Следующий проход этой группы может начаться только согласно политике планирования следующей работы.

### Пример с переносом между кадрами

Пусть группа `A → B`, а A оказался настолько долгим, что B не поместился в оставшийся бюджет.

Тогда возможно:

    кадр 1: A
    кадр 2: B
    кадр 3: A
    кадр 4: B
    ...

Если B в кадре 2 выполняется быстро, AnimationEngine не должен из-за этого нарушать порядок группы и запускать A вне принятой политики планирования.

### Ограничение одного прохода и новые callback'и

В начале `step()` фиксируется набор позиций, который участвует в текущем проходе. Callback, добавленный во время выполнения текущего callback, не должен автоматически получать дополнительный слот в том же проходе.

Например:

    начало:
        A → B → C

    A добавляет D

    текущий проход:
        A → B → C

    следующий проход:
        A → B → C → D

Новый callback не должен изменять уже начатый проход задним числом.

### Удаление callback'ов

Callback может удалить себя или другой callback во время выполнения.

Например, если:

    A → B → C → D

и C удаляет D, то D больше не должен выполняться.

Если B удаляет самого себя:

    A → B → C

то оставшаяся последовательность продолжается без B:

    A → C

AnimationEngine корректирует внутреннее состояние планирования так, чтобы удалённый callback не был повторно выбран cursor.

### Один callback — одна неделимая единица планирования

AnimationEngine может перенести **следующий callback** на другой кадр, но не может остановить текущий callback в середине.

Например:

```ts
engine.addCallbacks([A, B, C]);
```

Если C внутри себя выполняет долгую синхронную операцию, AnimationEngine не сможет разделить C между кадрами.

Для планировщика C — одна неделимая операция:

    A → B → C
             │
             └── C должен завершиться целиком

Если C необходимо распределить между кадрами, сама задача должна быть разделена вызывающей стороной:

    C1 → C2 → C3 → C4

### Использование времени кадра

У кадра есть вычислительный бюджет. AnimationEngine автоматически оценивает длительность кадров и использует часть этого времени для выполнения callback'ов.

При этом проверка бюджета происходит **между callback'ами**, а не во время выполнения callback.

Поэтому бюджет следует понимать как **разрешённое время на запуск следующей работы**. AnimationEngine старается не начинать следующий callback после исчерпания бюджета текущего кадра.

Если один callback сам по себе занимает больше доступного бюджета, он всё равно выполняется целиком. Планировщик не может прервать синхронный JavaScript-код. Бюджет ограничивает начало **следующего** callback, а не длительность уже начатого.

### Безопасный запуск callback

Ошибка одного callback не должна останавливать общий планировщик. AnimationEngine выполняет каждый callback через защитную оболочку `safe`: исключение перехватывается и записывается через `console.error`, после чего планировщик продолжает работу со следующей доступной позицией.

Это не означает, что ошибка исправлена или что состояние предметной подсистемы после исключения корректно. `safe` защищает именно жизненный цикл AnimationEngine.

### `deltaTime` в текущей реализации

Текущий вариант `deltaTime` является временным и недостаточно точным для планировщика последовательной работы.

Сейчас все callback'и одного `step()` получают одно и то же значение `deltaTime`, которое фактически означает время между animation frame:

    кадр N:
        A(deltaTime)
        B(deltaTime)
        C(deltaTime)

Это не отражает реальное время ожидания **конкретной группы** между её запусками.

Для задачи планирования важнее другая величина: сколько времени прошло с момента последнего запуска данной группы. Именно эта величина в дальнейшем должна использоваться и как `deltaTime` группы, и как основание для выбора следующей группы.

Текущую реализацию `deltaTime` поэтому следует считать промежуточной и подлежащей переработке.

### Автоматическая оценка времени кадра

AnimationEngine не получает фиксированный `frameBudgetMs`.

Перед началом работы он измеряет реальные интервалы между кадрами и определяет доступный вычислительный бюджет.

Детали калибровки являются внутренней реализацией. Важно, что бюджет:

- определяется автоматически;
- используется при выборе количества работы текущего кадра.

### Остановка

Удаление последнего callback останавливает дальнейшее планирование `requestAnimationFrame`.

`stop()` останавливает engine и сбрасывает измеренный вычислительный бюджет. Следующий запуск проходит калибровку заново.

`clear()` удаляет все callback'и, сбрасывает cursor, останавливает engine и также сбрасывает калибровку.

## Автоматическая оценка времени кадра

AnimationEngine не получает фиксированный `frameBudgetMs`.

Перед началом работы он измеряет реальные интервалы между кадрами и определяет доступный вычислительный бюджет.

Детали калибровки являются внутренней реализацией. Важно, что бюджет:

- определяется автоматически;
- зависит от фактической частоты кадров;
- используется при выборе количества работы текущего кадра.

## deltaTime

Текущая реализация `deltaTime` является временной: это время между текущим и предыдущим animation frame.

Первый кадр после запуска не имеет предыдущего timestamp, поэтому `deltaTime` равен `0`.

Целевая модель `deltaTime` описана в разделе **Дальнейшее развитие**. Переход к ней должен быть отдельным изменением поведения, а не скрытой корректировкой текущей реализации.

## Текущие пользователи

| Пользователь | Назначение |
|---|---|
| `ModelManager` | Выполнение собственной фоновой работы порциями |
| `LevenshteinManager` | Постепенное выполнение вычислений Levenshtein |
| `EnginePipeline` | Регистрация группы callback'ов для physics algorithms |

AnimationEngine не зависит от предметного смысла этих задач.

## Дальнейшее развитие

### Группы как единица планирования

Следующим этапом планирования должна стать модель, в которой конкурируют **группы**, а не отдельные callback'и.

У каждой группы сохраняется последовательность callback'ов и cursor:

    Group A: A1 → A2 → A3
                   ↑
                 cursor

При каждом запуске AnimationEngine берёт следующий callback именно из выбранной группы. Таким образом, callback'и одной группы остаются последовательными, а разные группы могут перемежаться.

Концептуальное состояние группы должно содержать как минимум:

```text
Group
├── callbacks
├── cursor
└── lastStartedAt
```

`lastStartedAt` — момент начала последнего callback'а этой группы.

### Планируемый `deltaTime`

Вместо общего frame-based `deltaTime` группа должна получать время с момента её предыдущего запуска.

Для группы:

    A1 → A2 → A3

если:

    A1 запущен в момент t1
    A2 запущен в момент t2

то для A2:

    deltaTime = t2 - t1

Это значение естественным образом соответствует смыслу последовательной работы: callback получает время, прошедшее с момента предыдущего запуска **его группы**, а не время между двумя глобальными animation frame.

Первый запуск группы не имеет предыдущего момента запуска, поэтому для него `deltaTime` должен быть `0`.

### `lastStartedAt` как основа планирования

Тот же `lastStartedAt` должен использоваться не только для вычисления `deltaTime`, но и для выбора следующей группы.

Если группы имеют:

    Group A: lastStartedAt = 100
    Group B: lastStartedAt = 140
    Group C: lastStartedAt = 120

и текущее время равно 160, то время ожидания групп составляет:

    Group A: 60
    Group B: 20
    Group C: 40

Следовательно, первой для запуска должна рассматриваться Group A — она ждала дольше остальных.

Таким образом, scheduler получает естественный приоритет:

    самая давно запускавшаяся группа
                    ↓
             следующая работа
                    ↓
          обновить lastStartedAt
                    ↓
          выбрать следующую группу

При сравнении групп достаточно сравнивать `lastStartedAt`: текущее время для всех групп одинаково, поэтому меньший timestamp означает большее время ожидания.

Для группы, которая ещё ни разу не запускалась, потребуется отдельное правило приоритета. В частности, она не должна бесконечно оставаться в состоянии `lastStartedAt = null`. При реализации необходимо также обеспечить детерминированное разрешение одинаковых timestamps.

### Почему это лучше согласуется с группами

Такая модель сохраняет главное свойство `addCallbacks`: группа остаётся последовательностью, а не превращается в плоскую очередь:

    Group A: A1 → A2 → A3
    Group B: B1 → B2
    Group C: C1

Планировщик выбирает:

    Group A → Group B → Group C → ...

а выбранная группа самостоятельно определяет следующий callback:

    Group A → A1
    Group B → B1
    Group C → C1
    Group A → A2
    ...

Это позволяет планировать справедливо на уровне независимых последовательностей, не нарушая их внутренний порядок.

### Generator

Generator должен стать естественным расширением той же модели группы.

Обычная группа имеет заранее известный набор callback'ов:

    Group:
        A1
        A2
        A3
        A4

Generator имеет ту же последовательную семантику, но количество будущих шагов заранее неизвестно:

    Generator:
        next() → A1
        next() → A2
        next() → A3
        next() → ...
        next() → завершение

Поэтому Generator следует рассматривать не как отдельный тип конкурирующей работы, а как **динамическую группу**, у которой следующий callback создаётся или выдаётся по мере продвижения.

### Generator и `lastStartedAt`

Именно здесь модель `lastStartedAt` становится особенно полезной.

Generator не обязан заранее создать весь список работы. AnimationEngine может рассматривать его как последовательную группу:

    Generator
        │
        ├── текущий шаг
        │
        ├── lastStartedAt
        │
        └── следующий шаг выдаётся после продвижения группы

Для Generator сохраняются те же правила:

1. у него есть последовательность шагов;
2. одновременно выбирается только следующий шаг;
3. порядок шагов сохраняется;
4. другие группы могут выполняться между его шагами;
5. `lastStartedAt` фиксирует момент запуска последнего шага;
6. `deltaTime` следующего шага определяется относительно предыдущего запуска этого Generator;
7. планировщик может выбирать Generator по тому же принципу ожидания, что и обычную группу callback'ов.

Получается единая модель:

    addCallback(A)
         │
         ▼
    Group [A]

    addCallbacks([A, B, C])
         │
         ▼
    Group [A, B, C]

    Generator
         │
         ▼
    Dynamic Group [next(), next(), next(), ...]

Различается только способ получения следующего callback'а. Механизм конкуренции групп и временная модель остаются общими.

### Generator как источник потенциально бесконечной работы

Generator особенно полезен для задач, количество шагов которых заранее неизвестно или может быть очень большим.

Например:

    Generator
        │
        ├── обработать очередную порцию данных
        ├── построить очередную часть индекса
        ├── обработать следующую порцию
        ├── ...
        └── завершить

AnimationEngine не должен заранее материализовать всю последовательность. Это позволяет держать в памяти только состояние Generator и текущий шаг.

При этом Generator не должен получать исключительное право на время кадра. Он остаётся одной из групп, конкурирующих за выполнение с другими группами.

### Связь `deltaTime` и Generator

Целевая модель позволяет Generator использовать `deltaTime` как естественный интервал между продвижениями его последовательности.

Например:

    t=100  → Generator выдаёт step #1
    t=145  → Generator выдаёт step #2
    t=230  → Generator выдаёт step #3

тогда:

    step #1: deltaTime = 0
    step #2: deltaTime = 45
    step #3: deltaTime = 85

При этом `deltaTime` не зависит напрямую от количества animation frame, прошедших между шагами. Если Generator не запускался несколько кадров, это время всё равно накапливается и отражается в следующем `deltaTime`.

Это особенно важно для динамической работы: Generator получает информацию о том, сколько реального времени прошло с его предыдущего продвижения, а scheduler использует тот же timestamp для определения его приоритета.

### Планируемая архитектура

В дальнейшем желательно прийти к единому понятию **последовательного источника работы**:

    ┌───────────────────────┐
    │       Group A         │
    │ A1 → A2 → A3 → ...    │
    └───────────┬───────────┘
                │
    ┌───────────────────────┐
    │       Group B         │
    │ B1 → B2 → B3 → ...    │
    └───────────┬───────────┘
                │
    ┌───────────────────────┐
    │      Generator C      │
    │ next → next → next... │
    └───────────┬───────────┘
                │
                ▼
        AnimationEngine
                │
                ├── выбрать наиболее ожидающую группу
                ├── получить следующий шаг группы
                ├── выполнить шаг
                ├── обновить lastStartedAt
                └── проверить budget

При такой архитектуре обычная группа callback'ов и Generator используют один и тот же механизм планирования. Generator отличается только тем, что его последовательность не известна заранее.

### Что потребуется изменить при реализации

Переход к этой модели потребует отдельной переработки текущего планировщика:

- заменить frame-based `deltaTime` на group-based `deltaTime`;
- хранить `lastStartedAt` для каждой группы;
- выбирать следующую работу по времени ожидания группы;
- сохранить cursor и последовательность callback'ов внутри группы;
- определить приоритет группы, которая ещё ни разу не запускалась;
- определить детерминированный tie-break при одинаковых timestamps;
- определить правила добавления и удаления групп во время `step()`;
- определить правила для Generator, когда он выдаёт следующий шаг или сообщает о завершении;
- сохранить ограничение вычислительного бюджета: budget определяет, можно ли **запустить следующую работу**, но не может прервать уже выполняющийся callback;
- отдельно покрыть новую модель тестами, особенно взаимодействие нескольких групп и Generator.

Эта переработка должна выполняться как отдельный этап. Текущий frame-based `deltaTime` не следует постепенно усложнять до новой модели: сначала необходимо зафиксировать контракт group-based scheduling и Generator, затем изменить реализацию и тесты.
