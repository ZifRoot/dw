# AnimationEngine

## Основные идеи

AnimationEngine — инфраструктурный планировщик покадровой работы клиентского приложения.

1. **Единый владелец `requestAnimationFrame`.** Только AnimationEngine управляет animation loop.
2. **Максимальное использование времени кадра.** Планировщик старается выполнить максимум зарегистрированной работы в доступном времени текущего кадра.
3. **Перенос невыполненной работы на следующие кадры.** Не помещающаяся работа продолжается в следующих кадрах.
4. **AnimationEngine не знает смысла работы.** Callback для него — абстрактная функция.
5. **Работа представляется последовательностью шагов.** Большая задача должна быть разделена вызывающей стороной на отдельные callback-операции.
6. **Последовательность может предоставляться callback'ом, группой callback'ов, Generator или фабрикой Generator.** Все эти варианты являются источниками одной и той же группы и подчиняются общим правилам планирования.

AnimationEngine отвечает за **время выполнения и планирование**, а смысл работы остаётся у потребителя.

## Единый requestAnimationFrame

### Почему несколько RAF создают проблему

Разные подсистемы могут самостоятельно создавать циклы `requestAnimationFrame`. Они конкурируют за одно и то же время кадра, не имеют общего бюджета и усложняют согласованное планирование и остановку.

### Почему нужен единый планировщик

AnimationEngine — единственная точка доступа подсистем к animation loop:

    ModelManager ───────┐
    LevenshteinManager ─┼──→ AnimationEngine ──→ requestAnimationFrame
    EnginePipeline ─────┘

Потребители регистрируют работу, а AnimationEngine решает, когда её выполнять.

## Представление работы

### `addCallback`

`addCallback(callback)` добавляет параллельную группу, состоящую из одного callback'а, и возвращает disposer этой группы.

### `addCallbacks`

`addCallbacks(callbacks)` добавляет параллельную группу из нескольких callback'ов и возвращает один disposer для всей группы.

Группа представляет собой **последовательность отдельных callback-операций**. Источник этой последовательности может быть массивом callback'ов, Generator или функцией, создающей Generator. Порядок элементов внутри одной группы сохраняется: если зарегистрировано `[A, B, C]`, то эта группа проходит позиции в порядке:

    A → B → C

Но группа **не является атомарной**. Между двумя callback'ами одной группы AnimationEngine может выполнить callback другой группы. Поэтому контракт не требует `A → B → C` как непрерывного участка одного кадра или одного прохода без вмешательства других групп.

Для разных групп планировщик выбирает **группу как единицу конкуренции**. Сначала обслуживаются группы, которые ещё ни разу не запускались, в порядке регистрации. После первого выполнения группы конкурируют по времени последнего завершения callback. Поэтому одна длинная группа не получает приоритет только из-за более раннего старта.

Таким образом, `addCallback(A)` является частным случаем `addCallbacks([A])`.

## Планирование

Планирование — это процесс, который определяет, **какие зарегистрированные callback'и будут выполнены в текущем кадре, а какие продолжат выполнение в следующем**.

AnimationEngine хранит состояние нескольких параллельных групп и использует cursor для продолжения каждой последовательности с нужного callback.

На каждом animation frame происходит примерно следующее:

    requestAnimationFrame
            │
            ▼
       начало кадра
            │
            ├── определить начало вычислительного бюджета
            │
            ├── выбрать следующую группу
            │
            ├── выполнить следующий callback этой группы
            │
            ├── проверить бюджет
            │
            ├── выбрать следующую работу
            │
            └── бюджет исчерпан
                    │
                    ▼
             следующий кадр

Планировщик не пытается выполнить «одну большую коллекцию» как неделимую операцию. Ни массив callback'ов, ни Generator, ни функция, создающая Generator, не являются атомарной единицей планирования. Каждый callback, полученный из любого из этих источников, является отдельным шагом. Между двумя такими шагами AnimationEngine может выполнить работу другой группы или остановить текущий проход и продолжить его на следующем кадре.

### Порядок выполнения внутри группы

Если зарегистрирована группа:

    A → B → C

то cursor определяет следующий callback этой группы:

    A → B → C → A → B → C → ...

При этом сама группа не получает эксклюзивный участок времени. Между A и B может быть выполнен callback другой группы.

### Параллельные группы

Рассмотрим три независимые последовательности:

    Group A: A1 → A2 → A3
    Group B: B1 → B2
    Group C: C1

Глобальная конкуренция происходит **между группами**, а не между отдельными callback'ами:

    Group A
    Group B
    Group C

Если AnimationEngine выбирает Group A, она выполняет только следующий callback своей последовательности — например, A1. После этого cursor Group A перемещается на A2, а timestamp последнего завершения группы обновляется после выполнения callback.

Поэтому возможна последовательность:

    A1 → B1 → C1 → A2 → B2 → A3 → ...

При этом порядок внутри каждой группы никогда не нарушается.

### `addCallback` как группа из одного элемента

Вызов:

```ts
engine.addCallback(A);
```

семантически соответствует:

```ts
engine.addCallbacks([A]);
```

В обоих случаях создаётся группа с одной последовательной позицией:

    Group: A

### Несколько `addCallbacks`

Например:

```ts
engine.addCallbacks([A1, B1, C1]);
engine.addCallbacks([A2, B2, C2]);
```

создаёт:

    Group 1: A1 → B1 → C1
    Group 2: A2 → B2 → C2

Это не означает выполнение первой группы целиком перед второй. Планировщик выбирает группы независимо, сохраняя последовательность callback'ов внутри каждой группы.

### Граница одного прохода

Один вызов планировщика (`step()`) не должен бесконечно повторять одну и ту же группу только потому, что в ней закончилась последовательность.

Если группа:

    A → B

и в текущем кадре успели выполниться оба callback'а:

    A → B

то достижение B означает завершение доступной на этот момент последовательности этой группы. Это не даёт группе специального права немедленно начать новый проход: следующий callback выбирается по тем же общим правилам планирования, что и любой другой callback.

Даже если после B в кадре осталось время, AnimationEngine не должен немедленно начинать новый проход:

    A → B → A → ...

Следующий проход этой группы может начаться только согласно политике планирования следующей работы.

### Пример с переносом между кадрами

Пусть группа `A → B`, а A оказался настолько долгим, что B не поместился в оставшийся бюджет. Это правило одинаково для любого источника группы: массива callback'ов, Generator или фабрики Generator. Сам факт получения callback'а из Generator не делает всю последовательность одной неделимой операцией.

Тогда возможно:

    кадр 1: A
    кадр 2: B
    кадр 3: A
    кадр 4: B
    ...

Если B в кадре 2 выполняется быстро, AnimationEngine не должен из-за этого нарушать общие правила планирования и немедленно выполнять следующий A только потому, что в текущем кадре осталось время.

### Ограничение одного прохода и новые callback'и

В начале `step()` фиксируется набор позиций, который участвует в текущем проходе. Callback, добавленный во время выполнения текущего callback, не должен автоматически получать дополнительный слот в том же проходе.

Например:

    начало:
        A → B → C

    A добавляет D

    текущий проход:
        A → B → C

    следующий проход:
        A → B → C → D

Новый callback не должен изменять уже начатый проход задним числом.

### Удаление callback'ов

Callback может удалить себя или другой callback во время выполнения.

Например, если:

    A → B → C → D

и C удаляет D, то D больше не должен выполняться.

Если B удаляет самого себя:

    A → B → C

то оставшаяся последовательность продолжается без B:

    A → C

AnimationEngine корректирует внутреннее состояние планирования так, чтобы удалённый callback не был повторно выбран cursor.

### Один callback — одна неделимая единица планирования

AnimationEngine может перенести **следующий callback** на другой кадр, но не может остановить текущий callback в середине.

Например:

```ts
engine.addCallbacks([A, B, C]);
```

Если C внутри себя выполняет долгую синхронную операцию, AnimationEngine не сможет разделить C между кадрами.

Для планировщика C — одна неделимая операция:

    A → B → C
             │
             └── C должен завершиться целиком

Если C необходимо распределить между кадрами, сама задача должна быть разделена вызывающей стороной:

    C1 → C2 → C3 → C4

### Использование времени кадра

У кадра есть вычислительный бюджет. AnimationEngine автоматически оценивает длительность кадров и использует часть этого времени для выполнения callback'ов.

При этом проверка бюджета происходит **между callback'ами**, а не во время выполнения callback.

Поэтому бюджет следует понимать как **разрешённое время на запуск следующей работы**. AnimationEngine старается не начинать следующий callback после исчерпания бюджета текущего кадра.

Если один callback сам по себе занимает больше доступного бюджета, он всё равно выполняется целиком. Планировщик не может прервать синхронный JavaScript-код. Бюджет ограничивает начало **следующего** callback, а не длительность уже начатого.

### Безопасный запуск callback

Ошибка одного callback не должна останавливать общий планировщик. AnimationEngine выполняет каждый callback через защитную оболочку `safe`: исключение перехватывается и записывается через `console.error`, после чего планировщик продолжает работу со следующей доступной позицией.

Это не означает, что ошибка исправлена или что состояние предметной подсистемы после исключения корректно. `safe` защищает именно жизненный цикл AnimationEngine.

### deltaTime

deltaTime является свойством **группы**, а не animation frame.

Для последовательности:

    A1 → A2 → A3

если:

    A1 завершился в t1
    A2 запускается в t2

то:

    A2 получает deltaTime = t2 - t1

Первый запуск группы получает deltaTime = 0.

| Пользователь | Назначение |
|---|---|
| `ModelManager` | Выполнение собственной фоновой работы порциями |
| `LevenshteinManager` | Постепенное выполнение вычислений Levenshtein |
| `EnginePipeline` | Регистрация группы callback'ов для physics algorithms |

AnimationEngine не зависит от предметного смысла этих задач.

## Текущая модель планирования

Глобальная единица конкуренции — **группа**, а не отдельный callback.

Состояние группы:

~~~
Group
├── callbacks
├── cursor
├── lastCompletedAt
└── queue node
~~~

lastCompletedAt хранит момент завершения последнего callback этой группы.

### Приоритет новых групп

Для группы, которая ещё ни разу не выполнялась, lastCompletedAt === null.

Такие группы имеют приоритет над уже запускавшимися группами. Между несколькими новыми группами сохраняется порядок регистрации:

    A(null) → B(null) → C(null)

Для этого не требуется отдельный registrationAt.

### Приоритет уже запускавшихся групп

После первого выполнения группа получает lastCompletedAt.

Запущенные группы поддерживаются в FIFO-структуре по времени последнего завершения:

    самая давно завершившаяся
              ↓
          следующая
              ↓
            tail

Когда группа завершает callback, её lastCompletedAt обновляется **после выполнения callback**, а группа помещается в конец очереди.

Это важно для длинных callback'ов: scheduler учитывает момент завершения A, а не момент её старта.

### Почему не нужен полный sort

performance.now() монотонен, а новый lastCompletedAt появляется только после завершения текущего callback.

Поэтому достаточно поддерживать две FIFO-структуры:

    pendingGroups
        ↓
    никогда не запускавшиеся группы

    startedGroups
        ↓
    уже запускавшиеся группы
    в порядке lastCompletedAt

Это позволяет не сортировать все группы на каждом выборе.

### Стабильность одинаковых timestamps

Если несколько групп получили одинаковый lastCompletedAt, сохраняется существующий FIFO-порядок.

Новая группа с тем же timestamp добавляется после уже находящихся в очереди элементов.

То же правило выполняется для null-групп: они обслуживаются в порядке регистрации.

### Бюджет

Бюджет кадра проверяется между callback'ами.

Если следующий callback является первой работой кадра, он запускается даже при уже исчерпанном бюджете: синхронный callback нельзя прервать.

После завершения callback scheduler проверяет бюджет перед запуском следующей работы.

Следовательно, frameBudgetMs — это разрешённое время на запуск **следующей** работы, а не жёсткий лимит длительности callback.

### Изменения во время step

Группа, добавленная во время выполнения текущего step(), получает следующий номер шага и не может быть выбрана в уже начатом step().

Удаление группы снимает её node из соответствующей FIFO-структуры. Самоудаление callback также поддерживается.

### Безопасность callback

Каждый callback выполняется через safe-обёртку. Исключение перехватывается и передаётся в console.error, после чего scheduler продолжает работу.

Safe-обёртка защищает жизненный цикл AnimationEngine, но не отменяет частичные изменения состояния, сделанные самим callback до исключения.

## Дальнейшее развитие

### Generator как источник последовательности

Текущая модель хранит внутри группы:

~~~
Group
├── callbacks
├── cursor
├── lastCompletedAt
└── queue node
~~~

Здесь `callbacks + cursor` уже фактически являются простейшим состоянием генератора: `cursor` указывает, какой элемент последовательности нужно выдать следующим.

Поэтому дальнейшее развитие API должно идти не по пути добавления отдельного механизма планирования для Generator, а по пути выделения **единого источника следующей работы**.

Концептуальная иерархия API:

~~~
addGenerator
    ↑
addCallbacks
    ↑
addCallback
~~~

То есть:

- `addGenerator` — один из вариантов регистрации группы через уже созданный последовательный источник callback'ов;
- `addGeneratorFactory` — вариант регистрации группы через функцию, которая создаёт такой источник;
- `addCallbacks` — частный случай последовательного источника, заданного массивом callback'ов;
- `addCallback` — частный случай `addCallbacks`, создающий группу из одного callback'а.

При этом все варианты являются **группами**. Отличается только способ получения следующего callback. Планировщик не должен превращать Generator или фабрику Generator в отдельную атомарную единицу работы: каждый полученный callback участвует в общей конкуренции групп наравне с остальными.

### Единый интерфейс источника работы

Для совместимости с обычными callback'ами и JavaScript Generator целесообразно опираться на стандартный iterator-протокол:

~~~ts
interface AnimationSequence extends Iterator<AnimationCallback> {}
~~~

Группа в таком случае содержит не массив callback'ов и cursor как обязательную модель, а последовательный источник:

~~~
Group
├── sequence
├── lastCompletedAt
└── queue node
~~~

Для обычных callback'ов создаётся адаптер над массивом.

Для Generator используется его стандартный `next()`.

В обоих случаях планировщик выполняет одну и ту же операцию:

~~~
выбрать группу
    ↓
получить следующий callback из sequence
    ↓
выполнить callback
    ↓
обновить lastCompletedAt
    ↓
поставить группу в конец очереди
~~~

Таким образом, **состояние последовательности принадлежит самому источнику**, а не AnimationEngine. Для массива этим состоянием является индекс/cursor адаптера; для Generator — внутреннее состояние генератора.

### Семантика `addCallbacks`

Текущий `addCallbacks([A, B, C])` представляет циклическую последовательность:

~~~
A → B → C → A → B → C → ...
~~~

Это поведение должно быть сохранено при переходе на Generator API.

Поэтому адаптер `addCallbacks` должен предоставлять AnimationEngine не конечный iterator массива, а циклический источник:

~~~ts
while (true) {
    for (const callback of callbacks) {
        yield callback;
    }
}
~~~

Это важно: обычный конечный Generator имеет состояние `done = true` после последнего элемента, а текущий контракт `addCallbacks` означает долгоживущую группу. Завершение последовательности и создание следующего источника должны быть частью семантики конкретного API, но ни один из этих механизмов не меняет общие правила выполнения отдельных callback-операций.

### Завершение Generator

Для уже созданного Generator стандартный iterator-протокол позволяет представить конечную последовательность:

~~~
next() → A
next() → B
next() → C
next() → done
~~~

Если зарегистрирован именно готовый Generator и источник сообщает `done`, группа считается завершённой и удаляется из планировщика.

Если зарегистрирована **фабрика Generator**, её вызов создаёт источник для той же группы. Завершение созданного Generator означает, что у этого источника больше нет следующего callback. Это не делает саму группу атомарной и не отменяет общие правила планирования. Фабрика создаёт неразрывный источник на **текущий кадр** только в смысле его жизненного цикла: один созданный Generator может выдавать отдельные callback'и в общей очереди планировщика, а между ними могут происходить переключения на другие группы. После завершения этого Generator группа ждёт следующего кадра, в котором фабрика создаст новый Generator для продолжения работы.

При этом Generator может быть и бесконечным:

~~~
next() → A1
next() → A2
next() → A3
...
~~~

Разница между конечным и бесконечным источником определяется самим Generator, а не отдельным режимом AnimationEngine.

### Очередь групп

Наличие двух структур `pendingGroups` и `startedGroups` не является обязательной частью модели.

Логически это **одна очередь групп с двумя состояниями**:

~~~
never-started → started
~~~

Новые группы должны попадать в область never-started в порядке регистрации.

После первого выполнения группа переходит в область started. После каждого следующего callback она помещается в конец started-области.

Таким образом сохраняются оба требования:

1. новая группа имеет приоритет перед уже запускавшимися группами;
2. среди уже запускавшихся групп соблюдается порядок последнего завершения.

Для реализации этого поведения не требуется сортировать все группы на каждом выборе и не требуется обязательно хранить две независимые очереди. Одна связная очередь с границей между never-started и started позволяет сохранить те же свойства с O(1) операциями перемещения.

### `deltaTime`

`deltaTime` также является свойством **последовательности конкретной группы**, а не animation frame.

Для:

~~~
A1 → A2 → A3
~~~

если:

~~~
A1 завершился в t1
A2 запускается в t2
~~~

то:

~~~
deltaTime(A2) = t2 - t1
~~~

То есть точнее `deltaTime` следует понимать как:

> время, прошедшее с момента завершения предыдущего элемента этой группы до момента запуска текущего элемента.

Для первого элемента группы предыдущего завершения нет, поэтому:

~~~
deltaTime = 0
~~~

Это определение сохраняется независимо от того, был ли предыдущий элемент получен из массива callback'ов, адаптера `addCallbacks` или Generator.

### Что потребуется для Generator API

Отдельным изменением потребуется:

- определить публичные методы `addGenerator` и `addGeneratorFactory`;
- определить точный тип источника — стандартный `Iterator<AnimationCallback>` или собственный совместимый интерфейс;
- вынести состояние последовательности из `CallbackGroup` в источник следующей работы;
- реализовать адаптер массива для `addCallbacks`;
- реализовать `addCallback` через `addCallbacks`;
- сохранить циклическую семантику текущего `addCallbacks`;
- определить поведение конечного Generator через `IteratorResult.done`, отдельно для готового Generator и фабрики Generator;
- определить обработку исключений, возникающих внутри Generator при вызове `next()` или при создании Generator фабрикой;
- сохранить общие для всех источников правила планирования, `lastCompletedAt`, `deltaTime`, бюджета и удаления; каждый callback из массива, Generator или Generator, созданного фабрикой, является отдельной неделимой операцией;
- добавить тесты на смешивание обычных групп, конечных Generator и бесконечных Generator.

Главный архитектурный принцип: **Generator не должен становиться вторым планировщиком**. Он является только источником следующего callback, тогда как выбор группы, бюджет кадра и справедливость между группами остаются ответственностью AnimationEngine.
