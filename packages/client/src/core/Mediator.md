## Ретроспективный промт для себя в прошлое (о медиаторе)

**Контекст:**  
В проекте используется медиатор для связи UI (React) и бизнес-логики (PointsScene, физика и т.д.). Изначально медиатор был простым EventTarget с методами on/off/emit, но это привело к просачиванию деталей реализации (CustomEvent, detail) в подписчиков, отсутствию типизации и дублированию кода в компонентах.

**Что нужно было сделать (и почему):**

1. **Разделить медиатор на два уровня: универсальный `BaseMediator` и конкретный `AppMediator`.**
   - **Почему:** Базовый уровень отвечает только за хранение состояния и работу с событиями (set/get/on/once/emit). Он не знает о предметной области. Это позволяет переиспользовать его в других частях приложения или в будущих проектах. Конкретный уровень добавляет типизированные геттеры/сеттеры и методы подписки, скрывая механизм событий от потребителя.

2. **В `BaseMediator` метод `emit` сделать защищённым (`protected`).**
   - **Почему:** Внешний код не должен напрямую генерировать события; это ответственность конкретного медиатора (например, вызов `mediator.temperature = 50` должен сам генерировать событие). Это инкапсулирует механизм отправки событий и предотвращает ошибки.

3. **Методы `on` и `once` в `BaseMediator` должны принимать колбэк с параметром `detail: any`, а внутри преобразовывать `Event` в `CustomEvent` и извлекать `detail`.**
   - **Почему:** Потребители (React-компоненты) не должны знать о существовании `CustomEvent`. Им нужны только чистые данные. Это упрощает код и делает его менее связанным с DOM-спецификой.

4. **В `AppMediator` для каждого события создать типизированный метод подписки, например `onTemperature(callback: (value: number) => void)`.**
   - **Почему:** Типизация на уровне подписки устраняет ошибки (например, передачу строки вместо числа). Это также даёт автодополнение в IDE и делает API явным. Команды (события без данных) могут иметь методы без параметров: `onClearPoints(callback: () => void)`.

5. **Геттеры/сеттеры в `AppMediator` использовать константы для ключей.**
   - **Почему:** Сеттер автоматически вызывает `set`, который генерирует событие, поэтому отдельный метод типа `setAutoZoom` не нужен – достаточно свойства `autoZoom`.

6. **Методы команд (`clearPoints`, `addPoint`, `startRepulsion`) не должны принимать аргументы и вызывать `emit` с соответствующим ключом.**
   - **Почему:** Команды – это события без полезной нагрузки. Их вызов инициирует действие в других частях системы (например, очистку сцены). Это позволяет UI только отправлять сигнал, не зная, кто и как его обрабатывает.

**Итог:**  
Такая архитектура медиатора обеспечивает:
- полную инкапсуляцию механизма событий;
- строгую типизацию (TypeScript);
- простой и удобный API для компонентов;
- лёгкую расширяемость добавлением новых событий.
