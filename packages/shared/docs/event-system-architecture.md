# Архитектура событий: EventTarget, EventEmitter и типизированный слой

## Статус

**Статус решения: обсуждение / решение не принято.**

Этот документ фиксирует архитектурные идеи, возникшие при анализе `ObservableArray`, `BaseMediator` и `AppMediator`, чтобы не потерять их при дальнейшем развитии проекта.

Главный вывод на текущий момент:

> Удобство `EventEmitter` не является доказательством его архитектурного превосходства над стандартным `EventTarget`.

Перед созданием собственного общего `EventEmitter` необходимо проверить, можно ли получить нужный API поверх стандартной модели событий без создания второй конкурирующей event-системы.

## 1. Контекст

В проекте уже существуют две близкие по назначению потребности:

- `ObservableArray` должен уведомлять подписчиков об изменениях массива;
- `BaseMediator` / `AppMediator` используют события для связи частей клиентского приложения.

При разработке `ObservableArray` появился собственный `EventEmitter`. Это подняло вопрос: не является ли такой класс велосипедом, если в платформе уже существует `EventTarget`.

Одновременно `BaseMediator` уже построен поверх `EventTarget` и `CustomEvent`.

Поэтому вопрос следует рассматривать не как выбор «какой класс удобнее», а как выбор единой архитектурной модели событий.

## 2. EventEmitter и EventTarget — разные модели

### EventTarget

`EventTarget` — стандартная событийная модель платформы.

Она предоставляет:

- `addEventListener`;
- `removeEventListener`;
- `dispatchEvent`;
- `Event`;
- `CustomEvent`;
- стандартную семантику DOM/Web API событий.

Преимущество для проекта — отсутствие необходимости изобретать собственную базовую event-инфраструктуру.

Недостаток в TypeScript-коде проекта — типизация payload не является встроенной на уровне `EventTarget`. Например, `CustomEvent<T>` типизирует `detail`, но имя события само по себе не связано с типом payload.

### EventEmitter

Модель `EventEmitter` обычно строится вокруг пары:

- имя события;
- payload события.

Для TypeScript удобно описывать карту событий:

    type EventMap = {
      changed: Change;
      selected: Item;
    };

и связывать имя события с соответствующим типом payload.

Это делает API удобным для application-level событий.

Однако сам по себе такой API не даёт принципиального архитектурного преимущества перед `EventTarget`. Это прежде всего другая форма интерфейса вокруг похожей идеи подписки и уведомления.

## 3. Главный архитектурный риск собственного EventEmitter

Если создать собственный `EventEmitter` только ради удобного typed API, существует риск его постепенной эволюции в копию уже существующей event-системы.

Например, со временем могут понадобиться:

- `on`;
- `off`;
- `once`;
- массовое удаление подписчиков;
- получение списка событий;
- получение количества слушателей;
- порядок подписчиков;
- специальные варианты регистрации;
- обработка ошибок;
- дополнительные правила жизненного цикла.

После нескольких таких расширений собственный класс начинает повторно реализовывать концепции стандартного `EventTarget` или Node.js `EventEmitter`.

Это создаёт две проблемы:

1. появляется собственный framework вместо небольшого utility-класса;
2. разработчикам приходится помнить две похожие модели событий.

Поэтому критерий «API выглядит удобнее» недостаточен для создания новой инфраструктурной абстракции.

## 4. Альтернативная архитектурная идея

Вместо отдельной event-системы стоит исследовать слой:

    EventTarget
        ↑
    TypedEventTarget<TEventMap>
        ↑
    BaseMediator
        ↑
    AppMediator

Идея состоит в том, чтобы сохранить `EventTarget` как базовый механизм, добавив только типобезопасный TypeScript API.

Условная модель:

    type EventMap = {
      selected: Point | null;
      changed: PointChange;
    };

    class TypedEventTarget<TEventMap> extends EventTarget {
      public on<K extends keyof TEventMap>(
        eventName: K,
        callback: (detail: TEventMap[K]) => void,
      ): () => void {
        // typed adapter over EventTarget
      }

      protected emit<K extends keyof TEventMap>(
        eventName: K,
        detail: TEventMap[K],
      ): void {
        // dispatch CustomEvent
      }
    }

Это не готовая реализация, а направление для дальнейшего исследования.

## 5. Что это даёт ObservableArray

Для `ObservableArray` можно рассмотреть ту же модель.

Сейчас ему нужны три типа событий:

- `update`;
- `add`;
- `remove`.

Вместо отдельного самописного event emitter можно использовать общий typed event layer, если его API и семантика подходят для коллекции.

При этом важно сохранить уже определённый контракт `ObservableArray`:

- изменение существующего элемента → `update`;
- создание новых позиций → `add`;
- удаление позиций → `remove`;
- перемещение существующих элементов при `shift`, `unshift`, `splice` не считается `update`;
- `delete array[index]` → `update` со значением `undefined`;
- увеличение `length` → `add` для всех новых позиций.

Архитектура event layer не должна менять эту семантику.

## 6. Что это даёт BaseMediator / AppMediator

`BaseMediator` уже наследуется от `EventTarget`.

Он хранит:

    EventMap
      ↓
    Map<event, value>
      ↓
    CustomEvent(detail)
      ↓
    EventTarget

Поэтому переход к typed adapter поверх `EventTarget` потенциально позволит:

- сохранить текущую основу `BaseMediator`;
- убрать повторяющуюся ручную типизацию event callbacks;
- использовать одну модель событий в разных частях проекта;
- не создавать отдельный event framework.

Особенно важно, что `AppMediator` содержит большой `AppEventMap`. Это хороший реальный пример, на котором можно проверить, насколько typed abstraction действительно улучшает код, а не просто создаёт ещё один слой.

## 7. Важное различие: state и events

`BaseMediator` решает сразу две задачи:

1. хранит состояние через `get/set/has`;
2. доставляет события через `emit/on/off/once`.

При дальнейшем рефакторинге эти обязанности не следует автоматически смешивать.

Event abstraction отвечает только за доставку событий.

Состояние:

    get()
    set()
    has()

является отдельной ответственностью mediator.

Поэтому возможный typed event layer не должен превращаться в универсальный state manager.

## 8. Чего пока не следует делать

Пока не следует:

- объявлять собственный `EventEmitter` стандартом проекта;
- переносить `BaseMediator` на новый emitter только ради единообразия;
- добавлять в emitter API функции «на будущее»;
- копировать API Node.js `EventEmitter`;
- копировать API `EventTarget`;
- менять семантику `ObservableArray` ради выбранной event abstraction.

Сначала необходимо определить минимальный набор требований проекта к событиям.

## 9. Вопросы для следующего этапа

Перед реализацией общего event layer нужно ответить:

1. Нужна ли проекту bubbling/capture semantics `EventTarget`, или события всегда локальные?
2. Нужны ли стандартные `Event` / `CustomEvent` объекты за пределами mediator?
3. Достаточно ли API `on/off/once/emit`?
4. Нужен ли публичный `dispatchEvent`?
5. Должны ли события быть синхронными?
6. Нужна ли отмена события через `preventDefault`?
7. Нужны ли несколько подписчиков с гарантированным порядком вызова?
8. Как должна обрабатываться ошибка callback?
9. Нужно ли поддерживать один и тот же event layer для `ObservableArray`, `BaseMediator` и других будущих компонентов?
10. Есть ли реальные требования, которые `EventTarget` не позволяет реализовать без неудобного обходного кода?

Последний вопрос особенно важен: если таких требований нет, отдельный `EventEmitter` может оказаться ненужной абстракцией.

## 10. Предварительное архитектурное направление

На текущем этапе наиболее безопасно рассматривать следующую гипотезу:

> **Не создавать второй фундаментальный механизм событий. Сначала проверить возможность построить минимальный типизированный слой поверх стандартного `EventTarget`.**

Если исследование покажет, что `EventTarget` принципиально не подходит для требований проекта, тогда можно отдельно обосновать собственный emitter.

Таким образом, решение должно приниматься по требованиям и семантике проекта, а не по субъективному сравнению удобства двух API.

## 11. Связь с текущими компонентами

| Компонент | Текущая роль | Что исследовать |
|---|---|---|
| `ObservableArray` | события изменений коллекции | typed events поверх общей инфраструктуры |
| `BaseMediator` | state + events | typed adapter над `EventTarget` |
| `AppMediator` | application event map | проверка удобства typed API на большом EventMap |
| `EventEmitter` | текущая utility-реализация | не расширять без отдельного архитектурного решения |
| `EventTarget` | стандартная базовая модель | рассматривать как текущую основу |

## 12. Итог

Зафиксированное решение на данный момент отсутствует.

Зафиксирована **архитектурная гипотеза**:

> `EventEmitter` не следует считать архитектурно более высоким уровнем, чем `EventTarget`. Прежде чем создавать или развивать собственный emitter, необходимо исследовать общий типизированный слой поверх стандартного `EventTarget`.

Это позволяет продолжить развитие `ObservableArray` и `AppMediator` независимо от окончательного решения и не потерять текущие аргументы при следующем обсуждении.
