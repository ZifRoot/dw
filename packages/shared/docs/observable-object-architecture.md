# Архитектура ObservableObject

## Статус

**Статус решения: архитектурное обсуждение / реализация не начата.**

Документ фиксирует идею обобщения текущего Mediator в рекурсивную модель наблюдаемого составного объекта. Цель документа — сохранить архитектурные решения и открытые вопросы до начала реализации.

## 1. Основная идея

Текущий Mediator уже можно рассматривать как наблюдаемое составное состояние:

- хранит значения;
- позволяет изменять значения;
- уведомляет подписчиков об изменениях;
- используется как точка координации состояния приложения.

Следующий шаг — отделить эту идею от конкретного UI-контекста и рассмотреть универсальный ObservableObject.

Пример целевого API:

    const mediator = new ObservableObject({
      temperature: 60,
      config: {},
      inputs: [],
    });

При этом внешний API должен оставаться естественным для JavaScript:

    mediator.temperature = 70;
    mediator.config.temperature = 80;
    mediator.inputs[4] = 123;

Внутренняя реализация должна автоматически обеспечивать наблюдаемость соответствующих изменений.

## 2. Рекурсивная структура

ObservableObject представляет не только набор полей верхнего уровня, а дерево наблюдаемых значений.

Концептуально:

    ObservableObject
    ├── temperature -> primitive
    ├── config -> ObservableObject
    └── inputs -> ObservableArray

Для более глубокого состояния:

    ObservableObject
    └── inputs: ObservableArray
        └── [0]: ObservableObject
            ├── id
            └── value

Таким образом, наблюдаемость распространяется на составные значения рекурсивно.

## 3. Правила преобразования значений

При создании ObservableObject исходное значение должно преобразовываться по типу.

Предварительное правило:

| Исходное значение | Представление |
|---|---|
| primitive | остаётся без обёртки |
| Array | ObservableArray |
| plain object | ObservableObject |
| Date | остаётся атомарным объектом |
| Map | остаётся атомарным объектом |
| Set | остаётся атомарным объектом |
| экземпляр пользовательского класса | остаётся атомарным объектом |
| Promise и другие специальные объекты | остаются атомарными |

Ключевое правило:

> Рекурсивно преобразуются только структуры данных, которыми ObservableObject действительно должен управлять как состоянием.

Нельзя автоматически превращать любой объект в ObservableObject, поскольку это затронуло бы сервисы, классы и объекты со своей собственной семантикой.

## 4. Почему нужен ObservableArray

Обычный массив не позволяет надёжно наблюдать изменения элементов через простой getter/setter объекта.

Например:

    mediator.inputs[4] = 123;

Изменение происходит внутри массива и не является присваиванием поля mediator.inputs.

ObservableArray уже решает эту задачу на уровне коллекции:

- update — изменение существующей позиции;
- add — появление новых позиций;
- remove — удаление позиций.

Поэтому ObservableObject не должен дублировать механику наблюдения массива.

Его задача — собрать отдельные наблюдаемые узлы в единое дерево.

## 5. ObservableObject как композиция

Архитектурно ObservableObject должен быть композитным контейнером.

Он не должен заново реализовывать:

- механику массива;
- отдельную систему наблюдения для каждого типа коллекции;
- бизнес-логику;
- UI-логику.

Его ответственность:

1. наблюдать собственные свойства;
2. преобразовывать составные значения в наблюдаемые узлы;
3. связывать дочерние наблюдаемые узлы с родителем;
4. обеспечивать корректное отключение старого ребёнка при замене значения;
5. представлять изменения дерева в контексте текущего узла.

Концептуальная структура:

    ObservableObject
          │
    ┌─────┼───────────────┐
    │     │               │
    ▼     ▼               ▼
  value  ObservableObject  ObservableArray
                  │
                  └── ObservableObject
                      └── ...

## 6. Должен ли ребёнок уведомлять родителя

**Предварительное решение: да.**

Если дочерний наблюдаемый объект изменился, родитель должен иметь возможность узнать об этом.

Пример:

    mediator.config.temperature = 70;

Локальное изменение происходит внутри:

    mediator.config

Но с точки зрения корневого объекта изменилось состояние всего дерева:

    mediator

Поэтому изменение должно иметь направление распространения:

    child
      ↓
    parent
      ↓
    grandparent

Распространение должно быть только вверх.

Родитель не должен передавать собственное событие обратно ребёнку, иначе возникает риск циклов и дублирования уведомлений.

## 7. Локальное изменение и изменение поддерева

Важно различать два понятия.

### Локальное изменение

Изменение непосредственно принадлежит текущему объекту.

Например:

    mediator.temperature = 70;

Событие относится к свойству:

    temperature

### Изменение потомка

Например:

    mediator.config.temperature = 70;

Непосредственное изменение принадлежит:

    config.temperature

Но корневой объект должен иметь возможность получить уведомление о том, что изменилось его поддерево.

Это не означает, что родитель должен просто повторно отправлять тот же объект события.

Концептуально следует различать:

    local change
    descendant change

## 8. Путь изменения

Для уведомления родителя полезно представлять изменение относительно текущего корня.

Например:

    mediator.config.temperature = 70;

Для mediator путь будет:

    ["config", "temperature"]

Для изменения элемента массива:

    mediator.inputs[4] = 100;

путь будет:

    ["inputs", 4]

Для вложенного объекта:

    mediator.inputs[4].value = 100;

путь будет:

    ["inputs", 4, "value"]

Путь позволяет родителю понимать не только факт изменения, но и место изменения в дереве.

## 9. Не дублировать события без необходимости

Не следует автоматически превращать каждое локальное событие ребёнка в независимое публичное событие на каждом уровне дерева.

Например:

    inputs[4].value = 100

не должно концептуально превращаться в цепочку одинаковых событий:

    inputs[4].value changed
    inputs[4].value changed
    inputs[4].value changed

На каждом уровне меняется контекст события.

Более чистая модель:

- дочерний узел сообщает о собственном изменении;
- родитель получает уведомление об изменении поддерева;
- родитель добавляет собственный сегмент пути;
- следующий родитель получает уже расширенный путь.

В результате корень получает единое описание:

    ["inputs", 4, "value"]

## 10. Замена дочернего объекта

Нужно учитывать не только изменение внутри дочернего объекта, но и замену самого дочернего значения.

Например:

    mediator.config = newConfig;

В этом случае ObservableObject должен:

1. перестать слушать старый config;
2. преобразовать новый plain object в ObservableObject, если это требуется;
3. установить связь нового ребёнка с родителем;
4. отправить локальное изменение свойства config.

Это особенно важно для корректного жизненного цикла подписок.

Старый объект после замены не должен продолжать уведомлять родителя.

## 11. Массив объектов

Рекурсивная модель естественным образом приводит к необходимости поддерживать массивы объектов.

Например:

    const state = new ObservableObject({
      inputs: [
        { id: 1, value: 10 },
        { id: 2, value: 20 },
      ],
    });

Целевая структура:

    ObservableObject
    └── inputs: ObservableArray
        ├── [0]: ObservableObject
        │   ├── id
        │   └── value
        └── [1]: ObservableObject
            ├── id
            └── value

Тогда изменение:

    state.inputs[1].value = 30;

должно быть представимо для корня как изменение по пути:

    ["inputs", 1, "value"]

Это выявляет важный вопрос текущей реализации ObservableArray: она сейчас ограничена primitive-элементами. Для полной рекурсивной модели потребуется расширить её типовую и runtime-модель так, чтобы элементами могли быть наблюдаемые объекты.

Это не является частью текущего решения, но должно быть явно учтено при реализации ObservableObject.

## 12. Циклические ссылки

Рекурсивное преобразование plain objects требует определить поведение для циклических структур.

Например:

    const a = {};
    const b = { a };
    a.b = b;

Без специального механизма рекурсивное преобразование может уйти в бесконечную рекурсию.

Поэтому реализация должна либо:

- явно поддерживать циклы через таблицу уже преобразованных объектов;
- либо ограничить входные данные ациклическими структурами.

Это отдельное решение реализации и не должно неявно определяться поведением рекурсивной функции.

## 13. Связь с Mediator

Mediator не обязательно должен оставаться отдельной фундаментальной моделью состояния.

Возможное направление:

    ObservableObject
          ↑
       Mediator
          ↑
     AppMediator

В таком случае:

- ObservableObject отвечает за наблюдаемое составное состояние;
- Mediator может добавлять необходимую application-level семантику;
- AppMediator содержит конкретное состояние и события приложения.

При этом event-механизм остаётся отдельным архитектурным вопросом.

Решение о EventTarget, EventEmitter или typed adapter не должно смешиваться с моделью ObservableObject.

## 14. ObservableObject не является универсальным deep state manager

Рекурсивность не означает, что необходимо сделать универсальную систему управления любыми объектами JavaScript.

Цель гораздо уже:

> Представить состояние приложения как дерево наблюдаемых plain objects и collections, сохранив естественный синтаксис доступа к данным.

Поэтому не требуется автоматически делать наблюдаемыми:

- экземпляры сервисов;
- DOM-объекты;
- Map / Set, если для них не определён отдельный контракт;
- произвольные пользовательские классы;
- внешние ресурсы и инфраструктурные объекты.

## 15. Разделение ответственности

Предлагаемое разделение:

| Компонент | Ответственность |
|---|---|
| ObservableObject | наблюдение свойств и композиция дерева |
| ObservableArray | наблюдение изменений массива |
| Event layer | доставка событий |
| Mediator | mediator/application-level семантика |
| AppMediator | конкретное состояние и события приложения |

Это разделение позволяет не превращать ObservableObject одновременно в state manager, event framework и application mediator.

## 16. ObservableObject содержит состояние и event methods

Для обобщения текущего Mediator недостаточно рассматривать ObservableObject только как контейнер наблюдаемых полей.

Текущий Mediator имеет два вида публичных членов:

1. свойства состояния;
2. методы, которые не содержат прикладной логики, а только отправляют события подписчикам.

Поэтому целевой ObservableObject должен уметь описывать оба вида интерфейса.

### Свойства

Свойство имеет обычный JavaScript getter/setter.

Setter не содержит бизнес-логики. Он передаёт новое значение внутреннему механизму ObservableObject, который:

1. получает старое значение;
2. сравнивает старое и новое значения;
3. если значение не изменилось — ничего не делает;
4. если значение изменилось — сохраняет новое значение;
5. отправляет событие изменения.

Концептуально:

    property setter
          ↓
    ObservableObject
          ↓
    old === new ?
       ↙       ↘
     yes        no
      ↓          ↓
    ничего    сохранить + emit

Это соответствует текущей семантике BaseMediator.set().

### Методы

Метод Mediator не является функцией с бизнес-логикой.

Например:

    mediator.clearPoints();

не означает, что Mediator сам очищает точки.

Метод является именованным каналом события:

    clearPoints()
          ↓
    emit("clear-points")
          ↓
    подписчики

Реальная обработка события находится у подписчиков.

Поэтому в ObservableObject event method не должен хранить прикладную логику. Внутри достаточно event descriptor / event channel и механизма его вызова.

## 17. Event methods как часть конфигурации

Конфигурация ObservableObject должна уметь описывать event methods наряду с начальными значениями состояния.

Концептуально:

    new ObservableObject({
      temperature: 20,

      reset: event(),
      selectPoint: event<Point>(),
    });

Здесь:

- temperature — начальное состояние;
- reset — событие без payload;
- selectPoint — событие с payload типа Point.

При создании ObservableObject реальной реализации reset или selectPoint с собственной логикой не создаётся.

Вместо этого создаётся event channel, который предоставляет:

1. функцию вызова события;
2. API подписки на это событие.

Например:

    object.reset();

только уведомляет подписчиков.

А подписка концептуально выглядит как:

    object.onReset(callback);

Таким образом, event method является виртуальным членом ObservableObject: его нет как самостоятельной бизнес-функции, но он присутствует в публичном API объекта как способ отправить событие.

## 18. Именование методов подписки

Именование должно соответствовать существующему соглашению AppMediator.

В текущем AppMediator используются короткие формы:

    onProgress(...)
    onTargetSize(...)
    onTemperature(...)
    onAutoZoom(...)
    onSelectedPoint(...)
    onPointSelected(...)
    onSelectedEdge(...)
    onClearPoints(...)
    onAddPoint(...)
    onStartRepulsion(...)
    onStartGraph(...)
    onReloadTables(...)

Поэтому для ObservableObject не вводится отдельное соглашение вроде:

    onTemperatureChange(...)

если само событие называется temperature.

Целевой принцип:

    event method:     temperature(...)
    subscription:     onTemperature(...)

или:

    event method:     clearPoints(...)
    subscription:     onClearPoints(...)

То есть префикс `on` обозначает подписку, а имя события сохраняется без дополнительного `Change`, если этого нет в самом имени события.

Регистрозависимость и точный вариант автоматической генерации имён являются деталями API и должны быть единообразными для всего ObservableObject.

## 19. Event methods и payload

Event method может не иметь payload или принимать один типизированный payload.

Примеры:

    clearPoints()
    startGraph()

и:

    selectPoint(point)
    pointChange(detail)

Это соответствует текущему BaseMediator, где события без payload вызываются без аргумента, а события с payload получают один типизированный аргумент.

Целевая типовая модель должна сохранять эту проверку на уровне TypeScript.

## 20. Proxy и внутреннее состояние

Реализация ObservableObject концептуально должна использовать тот же подход, который уже применяется в ObservableArray: публичный объект является Proxy над внутренним состоянием.

В отличие от ObservableArray, где Proxy перехватывает индексы массива, ObservableObject должен перехватывать доступ к свойствам объекта.

Концептуально:

    internal state
          ↓
        Proxy
       ↙     ↘
     get     set
              ↓
        ObservableObject
              ↓
          compare old/new
              ↓
            emit

Внутреннее состояние не обязано совпадать с публичным JavaScript-объектом.

Это позволяет отделить:

- хранение текущего значения;
- публичный getter/setter;
- механизм сравнения;
- генерацию событий;
- рекурсивные связи с дочерними ObservableObject / ObservableArray.

Event channels также не должны становиться частью внутреннего state как обычные значения.

## 21. Операция delete

Удаление свойства не является поддерживаемой операцией изменения состояния ObservableObject.

ObservableObject не должен пытаться интерпретировать:

    delete object.temperature;

как обычное observable изменение.

Предварительное решение:

- Proxy может перехватывать `deleteProperty`;
- попытка удалить управляемое свойство должна приводить к исключению;
- событие удаления не генерируется.

Таким образом, модель ObservableObject ограничивается изменениями существующих свойств через setter и добавлением свойств только в рамках явно определённого контракта.

Это намеренно отличается от универсального Proxy над произвольным JavaScript-объектом: ObservableObject контролирует собственную модель состояния, а не обязан поддерживать все операции языка.

## 22. Общая модель Mediator++

После добавления event methods общая модель становится:

    ObservableObject
    │
    ├── state properties
    │     ├── getter
    │     └── setter → compare → change event
    │
    ├── nested ObservableObject
    │
    ├── ObservableArray
    │
    └── event methods
          └── call → event → subscribers

Mediator++ является частным случаем этой модели.

Его задача не заключается в добавлении бизнес-логики. Он предоставляет конкретный типизированный интерфейс состояния и событий приложения.

Таким образом, текущие конструкции AppMediator вида:

    public get temperature(): number
    public set temperature(value: number)

и:

    public clearPoints(): void {
      this.emit(AppMediator.CLEAR_POINTS);
    }

концептуально сводятся к одной декларативной модели ObservableObject:

    temperature → observable state

    clearPoints → event method

При этом логика обработки остаётся за подписчиками.

## 23. Что ObservableObject не должен делать

ObservableObject не должен:

- выполнять бизнес-логику при изменении свойства;
- выполнять бизнес-логику при вызове event method;
- принимать решения предметной области;
- самостоятельно изменять связанные модели;
- превращаться в application service;
- интерпретировать смысл конкретного события.

Его задача — только механика:

    state + observation + event dispatch + composition

Это является ключевым условием того, чтобы Mediator++ действительно был частным случаем ObservableObject, а не ещё одним специализированным классом с собственной логикой.

## 24. Уточнение разделения ответственности

С учётом event methods разделение ответственности уточняется следующим образом:

| Компонент | Ответственность |
|---|---|
| ObservableObject | хранение/доступ к состоянию, наблюдение свойств, композиция дерева и dispatch event methods |
| ObservableArray | наблюдение изменений массива |
| Event layer | доставка и подписка на события |
| Mediator++ | типизированная mediator-модель состояния и событий без бизнес-логики |
| AppMediator | конкретный контракт состояния и событий приложения |
| Subscribers | фактическая прикладная реакция на события |

Главный принцип:

> Mediator не выполняет действие. Mediator сообщает о намерении выполнить действие или об изменении состояния.

Это одинаково относится к setter и event method: оба только передают изменение/событие в общий механизм наблюдения и доставки.

## 25. Что пока не решено

Перед реализацией необходимо отдельно определить:

1. точный API подписки на локальные изменения;
2. точный API уведомления об изменениях поддерева;
3. формат change/path объекта;
4. нужно ли публичное событие «subtree changed» или достаточно существующего механизма событий;
5. как удаляются связи с заменёнными дочерними объектами;
6. поддержка массивов объектов в ObservableArray;
7. правила циклических ссылок;
8. поведение при удалении свойства;
9. поведение при добавлении нового свойства;
10. нужно ли делать все свойства enumerable/configurable определённым образом;
11. какие объекты считаются plain objects;
12. должна ли мутация дочернего объекта всегда доходить до корня или это должно быть настраиваемым поведением.

Вопросы подписки и конкретного event API рассматриваются отдельно в:

    packages/shared/docs/event-system-architecture.md

## 26. Предварительная архитектурная модель

На текущем этапе зафиксирована следующая гипотеза:

    ObservableObject
          │
          ├── primitive
          │
          ├── ObservableObject
          │       └── ...
          │
          └── ObservableArray
                  └── ObservableObject / value

Изменение распространяется вверх:

    leaf
      ↓
    parent
      ↓
    root

При этом каждый уровень сохраняет собственный контекст пути.

Главная идея:

> ObservableObject — это не новый event framework и не универсальный state manager. Это рекурсивный наблюдаемый контейнер, который композирует наблюдаемые свойства, ObservableArray и другие ObservableObject в единое дерево состояния.

Окончательный API и конкретный механизм событий должны быть определены после отдельного обсуждения event architecture.
