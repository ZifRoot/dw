# Резолюция AUD-002, AUD-003 и AUD-011

## Статус

Документ фиксирует принятое решение по трём связанным пунктам независимого аудита:

- **AUD-002 — Critical:** ошибки скрываются и могут приводить к ложному успешному завершению операций.
- **AUD-003 — High:** обработка завершения `SingleExecution` / `ExecutionGuard` должна исключать появление необработанных rejection.
- **AUD-011 — High:** `Safe` скрывает ошибки отдельных элементов пакетной обработки.

## 1. AUD-002 — семантика ошибок

### Проблема

В проекте используются несколько вариантов обёрток над асинхронными операциями. Для аудита было важно явно разделить два намерения:

1. операция должна сообщить об ошибке вызывающему коду;
2. операция является best-effort и может подавить ошибку после её логирования.

Ранее отсутствие исполняемых тестов не позволяло гарантировать, что эти семантики сохраняются при изменениях.

### Принятое решение

Существующая семантика `logger.ts` сохраняется:

| API | Логирует ошибку | Передаёт ошибку дальше | Возвращает `null` при ошибке |
|---|---:|---:|---:|
| `Log` | Да | Да | Нет |
| `LogParam` | Да | Да | Нет |
| `LogSafe` | Да | Нет | Да |
| `LogParamSafe` | Да | Нет | Да |
| `Safe` | Да | Нет | Да |

Таким образом, `Log` и `LogParam` предназначены для операций, у которых ошибка должна оставаться видимой вызывающему коду, а `Safe`, `LogSafe` и `LogParamSafe` — для явно допускаемого best-effort поведения.

### Проверка

Добавлен исполняемый набор тестов:

`packages/shared/src/utils/logger-singleRunner.test.ts`

Тесты проверяют как логирование, так и фактическое распространение/подавление исключения.

Особенно важен сценарий пакетной обработки: ошибка одного элемента не должна незаметно превращать поведение всей операции в неявно успешное без соответствующего логирования.

## 2. AUD-003 — SingleExecution / ExecutionGuard

### Проблема

При завершении защищённой асинхронной операции необходимо корректно выполнять cleanup независимо от результата Promise. Некорректное использование `finally()` с игнорированием возвращаемого Promise может само породить необработанный rejection.

### Принятое решение

Текущая реализация `single-runner.ts` использует обработчики завершения:

`promise.then(cleanup, cleanup)`

Это обеспечивает вызов cleanup как при успешном завершении Promise, так и при ошибке, без создания отдельного необработанного rejection от проигнорированного Promise цепочки.

Дополнительный тест фиксирует это поведение через обработчик `unhandledRejection`.

Также проверяется возможность повторного запуска после завершения неудачной операции.

### Результат

Поведение `SingleExecution` / `ExecutionGuard` закреплено тестами и не требует изменения production-логики в рамках AUD-003.

## 3. AUD-011 — ошибки отдельных элементов

### Проблема

`Safe` подавляет исключение отдельного вызова, возвращая `null`. Это допустимо для best-effort операции, но без теста легко потерять информацию об ошибках отдельных элементов.

### Принятое решение

Оставить `Safe` как явно best-effort API:

- ошибка отдельного элемента логируется;
- ошибка не отклоняет Promise этого элемента;
- результат неуспешного элемента становится `null`;
- успешные элементы продолжают обрабатываться.

Добавлен тест с пакетной обработкой через `Promise.all`, который проверяет результат вида:

`[успешный результат, null, успешный результат]`

Тем самым зафиксировано, что ошибка одного элемента не приводит к отказу всей партии, но и не исчезает без логирования.

## 4. Изменения в репозитории

В рамках решения добавлены:

- `test/index.ts` — единая точка входа для всех исполняемых тестов; порядок `await import(...)` задаёт порядок регистрации test-модулей;
- `npm test` в корневом `package.json` — единая команда запуска тестов;
- `packages/shared/src/utils/logger-singleRunner.test.ts` — тесты семантики logger и SingleRunner;
- расширенная документация методов и декораторов в `packages/shared/src/utils/logger.ts`;
- исключение `src/**/*.test.ts` из client TypeScript compilation, поскольку shared-тесты используют Node.js API и не должны попадать в браузерную компиляцию клиента.

Production-логика `logger.ts` и `single-runner.ts` для исправления этих трёх аудитов намеренно не переписывалась.

## 5. Проверка CI

Первый запуск GitHub Actions выявил инфраструктурную проблему: client typecheck пытался компилировать shared-тест с импортами `node:test` и `node:assert/strict`.

Проблема устранена исключением тестовых файлов из client TypeScript compilation.

После этого требуется отдельная проверка нового CI-запуска, чтобы различать:

- успешный **typecheck**;
- фактическое выполнение и успешное завершение **unit-тестов**.

Наличие тестового файла само по себе не считается доказательством успешного прохождения тестов.

## 6. Критерии закрытия

AUD-002, AUD-003 и AUD-011 считаются технически закрытыми изменениями данной ветки при выполнении следующих условий:

- [x] семантика `Log` / `LogParam` зафиксирована тестами;
- [x] семантика `Safe` / `LogSafe` / `LogParamSafe` зафиксирована тестами;
- [x] пакетная ошибка отдельного элемента зафиксирована тестом;
- [x] cleanup `ExecutionGuard` проверяется на отсутствие `unhandledRejection`;
- [x] повторный запуск после ошибки проверяется тестом;
- [x] документация logger дополнена;
- [x] shared-тесты исключены из client typecheck;
- [ ] отдельный CI-запуск подтверждает прохождение typecheck;
- [ ] CI или локальный запуск подтверждает фактическое прохождение unit-тестов.

Последние два пункта являются проверочными условиями сборки, а не дополнительной production-логикой аудитов.

## Итог

В рамках AUD-002, AUD-003 и AUD-011 закреплена единая и проверяемая модель обработки ошибок:

**ошибка либо явно передаётся дальше, либо явно подавляется как best-effort — в обоих случаях это поведение покрыто тестами.**

Для `SingleExecution` дополнительно зафиксировано безопасное выполнение cleanup без необработанных rejection.
